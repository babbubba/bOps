# V1.1-F — read-only plugin catalog API and UI

Status: **complete**
Recommended model effort: **medio** (revised to **alto** during implementation: `bOps.Api` never
loaded plugins at all before this task — see `HANDOFF.md` for the gap this closed)
Repository: `bOps`
Depends on: V1.1-E complete; existing V1.0 authentication and PluginManager

## Outcome

Let authenticated operators inspect installed and active plugins from the local Angular UI without
introducing any mutation path.

## API work

- [x] Inventory PluginManager/domain state and define stable API DTOs rather than serializing
      internal objects. (`PluginCatalogModels.cs` — `PluginCatalogEntry`/`PluginCatalogDependency`/`PluginCatalogPage`.)
- [x] Expose a paged catalog and single-plugin detail endpoint.
      (`GET /api/plugins`, `GET /api/plugins/{id}` — `PluginCatalogEndpoints.cs`.)
- [x] Include ID, version, publisher, signature/trust status, enabled/loaded state, compatibility,
      declared capabilities, effective maximum risk, dependencies and sanitized diagnostic codes.
- [x] Omit installation paths, raw exception stacks, trust-store content and signature material not
      needed by the operator. (Verified by an explicit test asserting the serialized response never
      contains the plugin's `InstallPath`.)
- [x] Apply the established authenticated read role and API response/error conventions.
      (`ApiAuthorization.ViewerPolicy`, same as `ToolsEndpoints`.)
- [x] Add deterministic ordering, filtering by state/trust and bounded page size.
      (Ordinal by id; `enabled`/`trust` query filters; `limit` clamped to 1–200.)

## Angular work

- [x] Add a lazy route, typed API client/facade and SignalStore feature consistent with current UI
      architecture. (`app.routes.ts` → `features/plugins`, `PluginsStore`.)
- [x] Build accessible loading, empty, error and partial/degraded states.
- [x] Show trust and activation distinctly; “installed”, “enabled”, “loaded” and “compatible” must
      not be conflated. (Four separate badges in `plugins.html`, never merged.)
- [x] Show declared capabilities and effective risk without presenting declarations as enforcement.
      (Two separate labeled `bops-risk-badge` values: declared vs. effective.)
- [x] Do not render enable, disable or upload controls in this batch. (Asserted by a dedicated test.)

## Tests and documentation

- [x] API authorization, pagination, filtering, projection and sensitive-field absence tests.
      (`PluginCatalogEndpointsTests.cs`, 6 tests.)
- [x] Angular store/component/router tests including large catalogs and sanitized failures.
      (`plugins.store.spec.ts`, `plugins.spec.ts`.)
- [x] OpenAPI generation/TypeScript client alignment if the project uses generated contracts here.
      (N/A — this project hand-writes its TypeScript client against the real endpoints, same as
      every other endpoint; no generated-contract pipeline exists to align with.)
- [x] Release build, non-live .NET tests, Angular production build/headless tests and CI.
      (GitHub Actions run `35266612239` — Windows and Ubuntu both green.)
- [x] README screenshots/text are optional; operator documentation and status are mandatory.

## Definition of Done

- [x] The UI accurately distinguishes installed, trusted, enabled, loaded and incompatible plugins.
- [x] All data is read-only, bounded and authorized.
- [x] No private path, secret or raw exception crosses the API boundary.
