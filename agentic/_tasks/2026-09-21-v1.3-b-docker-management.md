# V1.3-B — Docker lifecycle, image build and volume management

Status: **implemented (2026-09-21); pull request open, CI evidence recorded after it runs**
Recommended model effort: **molto alto**
Repository: `bOps`
Depends on: V1.3-A complete

## Outcome

Complete the first-party Docker package as a practical operations surface while preserving the
existing governed tools. `docker.start`, `docker.stop`, `docker.restart`,
`docker.containers`, `docker.images`, `docker.networks`, `docker.inspect` and
`docker.logs` already exist and must not be reimplemented or renamed.

This batch adds typed image inspection/pull/tag/removal, bounded local image builds and volume
enumeration/inspection/create/remove. It must not expose the Docker Engine API generically, accept
arbitrary daemon JSON, or create a shell/command escape hatch.

## Contract and naming

- [x] Keep the existing eight Docker tool names and semantics source-compatible; strengthen their
      tests where needed rather than replacing them.
- [x] Add read-only `docker.image.inspect`, `docker.volumes` and
      `docker.volume.inspect`. Missing image/volume targets should be represented explicitly
      (for example `exists: false`) so verification can distinguish absence from reader failure.
- [x] Add governed `docker.image.pull`, `docker.image.tag`, `docker.image.remove`,
      `docker.build`, `docker.volume.create` and `docker.volume.remove`.
- [x] Do not add broad `image prune`, `volume prune`, container create/remove, registry
      credential management or Compose orchestration in this batch. A future prune capability
      requires a bounded prepare/manifest/approve/execute design comparable to governed recursive
      filesystem deletion.
- [x] Use deterministic structured output and bounded lists/logs; extend `docker.images` with
      optional limits/output ceilings if required without breaking existing callers.

## Image operations

- [x] `docker.image.inspect` reports id/digests/tags/size/created/platform-relevant metadata in a
      bounded normalized shape.
- [x] `docker.image.pull` accepts a typed image reference and optional platform, streams no
      unbounded daemon output, and returns the resolved local id/digest.
- [x] `docker.image.tag` creates one explicit target tag from one local source image.
- [x] `docker.image.remove` removes only the explicitly named image/tag/id. No implicit prune and
      no force-by-default behavior.
- [x] Every non-Read image mutation declares verification against `docker.image.inspect` (or an
      equally narrow read-only verifier) and implements `IVerifiableTool`.

## Build operations

- [x] `docker.build` builds only from an operator-allowed local context and an existing Dockerfile
      inside that context. Remote Git contexts, inline Dockerfiles and model-supplied Dockerfile
      contents are out of scope.
- [x] Define Docker-specific build-context allowlists/configuration instead of depending on another
      package's internal filesystem service across the plugin boundary.
- [x] Canonicalize context and Dockerfile paths and reject traversal/symlink escapes before sending
      a build context to the daemon.
- [x] Initial scope excludes arbitrary build args, BuildKit secrets/SSH forwarding, host-network
      overrides and privileged builder options. Add them only through a later threat-modelled
      contract if needed.
- [x] Treat build as at least High risk: a Dockerfile executes build instructions and can consume
      network, disk and CPU. It requires explicit policy/approval and verification that the expected
      image/tag/digest exists after completion.
- [x] Bound build duration, context size/file count and daemon progress output. Never place the
      entire build context or unbounded build log in model context, audit or telemetry.

## Volume operations

- [x] `docker.volumes` enumerates volumes with bounded deterministic output; include name, driver,
      mountpoint only when appropriate for the existing information-disclosure policy, labels and
      usage metadata when available.
- [x] `docker.volume.inspect` reports existence and bounded metadata for one named volume.
- [x] `docker.volume.create` creates one explicitly named volume with an allowlisted driver/options
      surface; no arbitrary plugin-specific option bag from the model.
- [x] `docker.volume.remove` is High risk because it can permanently destroy application data.
      It removes only one explicit volume, never prunes, never forces removal by default, requires
      approval and verifies absence afterwards.

## Existing container lifecycle

- [x] Preserve `docker.start`, `docker.stop` and `docker.restart` as the supported typed
      container lifecycle operations and keep their `docker.inspect` verification.
- [x] Add regression coverage for stopped/running/restarted containers, nonexistent targets,
      cancellation/timeouts and daemon unavailability. Do not introduce a generic container
      command/exec tool.

## Security and daemon boundary

- [x] Continue using `Docker.DotNet` through the existing client factory/capability probe; no raw
      HTTP endpoint or arbitrary Engine API path is supplied by the model.
- [x] Registry authentication, if later required, must use secret references and a dedicated
      contract. Credentials never appear in tool arguments, model context, output, audit or
      telemetry in this batch.
- [x] Assign risk levels from actual effects: read-only inspection/listing is `Read`; pull/tag/
      create operations are non-Read; image removal, volume removal and builds receive conservative
      risk and approval semantics. No new non-Read tool registers without verification.
- [x] Explicitly handle daemon conflict/not-found/in-use responses as tool outcomes, not uncaught
      exceptions.

## Validation

- [x] Extend the real-daemon integration suite; no Docker package mocks.
- [x] Create disposable images, tags and volumes owned by the test and prove create/read/mutate/
      remove round trips plus independent verification.
- [x] Build a tiny repository-owned test Dockerfile/context and verify the produced id/tag without
      relying on external mutable source.
- [x] Test context traversal, symlink escape, oversized context, output caps, cancellation,
      nonexistent resources, in-use image/volume refusal and daemon unavailability.
- [x] Preserve the existing start/stop/restart integration test and prove the provider contributes
      the complete expected tool set.
- [x] Release build, non-live suite and Docker-capable CI remain green (CI evidence below).

## Definition of Done

- [x] Existing container start/stop/restart and image enumeration remain compatible and verified.
- [x] Images can be inspected, pulled, tagged, built and explicitly removed through typed governed
      tools.
- [x] Volumes can be listed, inspected, created and explicitly removed through typed governed tools.
- [x] No generic Docker API, shell, exec, unbounded prune or secret-bearing build/registry escape
      hatch has been introduced.

## Evidence (2026-09-21)

- ADR: [ADR-0033](../../docs/architecture/adr/0033-governed-docker-image-build-and-volume-management.md), Accepted. Decision D-029.
  User documentation: [`docs/docker-management.md`](../../docs/docker-management.md).
- Code: nine tools in `bOps.Packages.Docker` next to the eight existing ones (which keep their names, risks and parameters, and now
  also report an unreachable daemon as a failed result); `DockerImageReference` and `DockerNames` for the grammar;
  `DockerBuildContext` for the allowed-directory, link, `.dockerignore` and bounds checks and the archive; `DockerBuildOptions` and
  `DockerVolumeOptions` bound from `Docker:Build` and `Docker:Volumes` in both hosts (`appsettings.json` ships them with no
  build context); the capability `docker.build-contexts` hides `docker.build` until a context is configured.
- Tests, all against a real Docker daemon where a daemon is involved and never mocked: create, read, mutate and remove round trips
  for images (built from a repository-owned `FROM scratch` context, tagged, removed), and volumes, each verified independently;
  daemon-side refusals of an image or volume in use and of a multi-tag removal by id; the removal that never prunes an untagged
  parent; a build that fails inside the daemon; a pull of a missing image and of an image by digest; cancellation of every tool;
  an unreachable daemon for all seventeen tools (no daemon needed); the existing eight tools for a nonexistent container; the
  contract (exact tool set, risk, approval, verification wired by argument name, registry acceptance and the hidden build tool);
  the reference and name grammar; the build context against real directories (traversal, sibling prefix, links, `.dockerignore`,
  file and byte limits at their exact bounds, cancellation, no archive left behind); configuration binding in the API test project;
  and a governed volume lifecycle through the real `AgentRunner` that shows the creation running on the policy and the removal asking
  a human because its manifest says so, both verified `Confirmed`.
- Linux: the symbolic-link tests need a process that can create links, so they skip on an unprivileged Windows session and are
  covered by the Linux runs. A container run of the package tests on Linux (`mcr.microsoft.com/dotnet/sdk:10.0`, no daemon) passed
  apart from the one provider-list test this change updated on purpose.
- Mutation testing: hand-written mutants over the reference and name grammar, the build context, the options, the output shapes
  and the tool decisions. About 68 mutants were run. The survivors are classified as follows.
  Boundary tests were added for the ones that could be pinned (context path length 1024/1025, platform length, blank allowed
  entries, empty image variant, volume list default, digest-tagged build) and each was re-run and killed. Equivalent or not
  coverable: `first == "localhost"` (`Familiar` already carries the host, so the result is identical); the build-log tail size 20 vs 21
  (only the last five lines are ever shown); the image-removal list bound 20 vs 21 (needs an image with more than 20 tags or layers;
  the bound of the shared list writer is tested on its own); the volume-create driver-mismatch comparison (the daemon offers only the
  `local` driver here). Mutants that first failed to compile (`if (false)` is a warning-as-error) were rewritten as inversions.

## Interpretations worth knowing

- **Argument names follow verification.** The runtime carries a verification argument by name, so `docker.image.tag` takes `source`
  and `image` (the new reference), and `docker.build` takes `image` for the tag it creates.
- **`.dockerignore` is refused, not applied.** The daemon does not read it and a partial implementation would send files the
  operator meant to keep out; a context is a plain directory.
- **Every link is refused**, inside or outside the context, which is stricter than "refuse an escape" and simpler to reason about.
- **`docker.build` is hidden, not refused, until configured**, through a second capability, the way `web.search` disappears when
  unconfigured.
- **Volume mount points and driver options are not returned.**
- **The default 30-second tool timeout is short for a pull or a build.** The operator raises it; it is not changed here.
- **`docker.images` is unchanged.** It lists every local image and takes no limit; extending it was optional in the task and would
  change a frozen tool.
- **Residual:** a FIFO or socket inside a build context can make reading it wait until the tool timeout; and the volume driver
  mismatch refusal cannot be exercised against a real daemon, which offers only the `local` driver here.
