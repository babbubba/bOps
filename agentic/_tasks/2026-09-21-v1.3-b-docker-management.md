# V1.3-B — Docker lifecycle, image build and volume management

Status: **future; starts only after V1.3-A**
Recommended model effort: **molto alto**
Repository: `bOps`
Depends on: V1.3-A complete

## Outcome

Complete the first-party Docker package as a practical operations surface while preserving the
existing governed tools. `docker.start`, `docker.stop`, `docker.restart`,
`docker.containers`, `docker.images`, `docker.networks`, `docker.inspect` and
`docker.logs` already exist and must not be reimplemented or renamed.

This batch adds typed image inspection/pull/tag/removal, bounded local image builds and volume
enumeration/inspection/create/remove. It must not expose the Docker Engine API generically, accept
arbitrary daemon JSON, or create a shell/command escape hatch.

## Contract and naming

- [ ] Keep the existing eight Docker tool names and semantics source-compatible; strengthen their
      tests where needed rather than replacing them.
- [ ] Add read-only `docker.image.inspect`, `docker.volumes` and
      `docker.volume.inspect`. Missing image/volume targets should be represented explicitly
      (for example `exists: false`) so verification can distinguish absence from reader failure.
- [ ] Add governed `docker.image.pull`, `docker.image.tag`, `docker.image.remove`,
      `docker.build`, `docker.volume.create` and `docker.volume.remove`.
- [ ] Do not add broad `image prune`, `volume prune`, container create/remove, registry
      credential management or Compose orchestration in this batch. A future prune capability
      requires a bounded prepare/manifest/approve/execute design comparable to governed recursive
      filesystem deletion.
- [ ] Use deterministic structured output and bounded lists/logs; extend `docker.images` with
      optional limits/output ceilings if required without breaking existing callers.

## Image operations

- [ ] `docker.image.inspect` reports id/digests/tags/size/created/platform-relevant metadata in a
      bounded normalized shape.
- [ ] `docker.image.pull` accepts a typed image reference and optional platform, streams no
      unbounded daemon output, and returns the resolved local id/digest.
- [ ] `docker.image.tag` creates one explicit target tag from one local source image.
- [ ] `docker.image.remove` removes only the explicitly named image/tag/id. No implicit prune and
      no force-by-default behavior.
- [ ] Every non-Read image mutation declares verification against `docker.image.inspect` (or an
      equally narrow read-only verifier) and implements `IVerifiableTool`.

## Build operations

- [ ] `docker.build` builds only from an operator-allowed local context and an existing Dockerfile
      inside that context. Remote Git contexts, inline Dockerfiles and model-supplied Dockerfile
      contents are out of scope.
- [ ] Define Docker-specific build-context allowlists/configuration instead of depending on another
      package's internal filesystem service across the plugin boundary.
- [ ] Canonicalize context and Dockerfile paths and reject traversal/symlink escapes before sending
      a build context to the daemon.
- [ ] Initial scope excludes arbitrary build args, BuildKit secrets/SSH forwarding, host-network
      overrides and privileged builder options. Add them only through a later threat-modelled
      contract if needed.
- [ ] Treat build as at least High risk: a Dockerfile executes build instructions and can consume
      network, disk and CPU. It requires explicit policy/approval and verification that the expected
      image/tag/digest exists after completion.
- [ ] Bound build duration, context size/file count and daemon progress output. Never place the
      entire build context or unbounded build log in model context, audit or telemetry.

## Volume operations

- [ ] `docker.volumes` enumerates volumes with bounded deterministic output; include name, driver,
      mountpoint only when appropriate for the existing information-disclosure policy, labels and
      usage metadata when available.
- [ ] `docker.volume.inspect` reports existence and bounded metadata for one named volume.
- [ ] `docker.volume.create` creates one explicitly named volume with an allowlisted driver/options
      surface; no arbitrary plugin-specific option bag from the model.
- [ ] `docker.volume.remove` is High risk because it can permanently destroy application data.
      It removes only one explicit volume, never prunes, never forces removal by default, requires
      approval and verifies absence afterwards.

## Existing container lifecycle

- [ ] Preserve `docker.start`, `docker.stop` and `docker.restart` as the supported typed
      container lifecycle operations and keep their `docker.inspect` verification.
- [ ] Add regression coverage for stopped/running/restarted containers, nonexistent targets,
      cancellation/timeouts and daemon unavailability. Do not introduce a generic container
      command/exec tool.

## Security and daemon boundary

- [ ] Continue using `Docker.DotNet` through the existing client factory/capability probe; no raw
      HTTP endpoint or arbitrary Engine API path is supplied by the model.
- [ ] Registry authentication, if later required, must use secret references and a dedicated
      contract. Credentials never appear in tool arguments, model context, output, audit or
      telemetry in this batch.
- [ ] Assign risk levels from actual effects: read-only inspection/listing is `Read`; pull/tag/
      create operations are non-Read; image removal, volume removal and builds receive conservative
      risk and approval semantics. No new non-Read tool registers without verification.
- [ ] Explicitly handle daemon conflict/not-found/in-use responses as tool outcomes, not uncaught
      exceptions.

## Validation

- [ ] Extend the real-daemon integration suite; no Docker package mocks.
- [ ] Create disposable images, tags and volumes owned by the test and prove create/read/mutate/
      remove round trips plus independent verification.
- [ ] Build a tiny repository-owned test Dockerfile/context and verify the produced id/tag without
      relying on external mutable source.
- [ ] Test context traversal, symlink escape, oversized context, output caps, cancellation,
      nonexistent resources, in-use image/volume refusal and daemon unavailability.
- [ ] Preserve the existing start/stop/restart integration test and prove the provider contributes
      the complete expected tool set.
- [ ] Release build, non-live suite and Docker-capable CI remain green.

## Definition of Done

- [ ] Existing container start/stop/restart and image enumeration remain compatible and verified.
- [ ] Images can be inspected, pulled, tagged, built and explicitly removed through typed governed
      tools.
- [ ] Volumes can be listed, inspected, created and explicitly removed through typed governed tools.
- [ ] No generic Docker API, shell, exec, unbounded prune or secret-bearing build/registry escape
      hatch has been introduced.
