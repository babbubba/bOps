# V1.2-F — durable state, step journal and reconciliation

Status: **implemented** (2026-09-20, pull request 16)
Recommended model effort: **alto**
Repository: `bOps`
Depends on: V1.2-E complete
Governing ADR: `docs/architecture/adr/0030-privilege-reducing-multi-agent-delegation.md`

## Outcome

Persist delegation runs and resume without repeating side effects (ADR-0030 section 7). The ADR fixes the state machine, so this is implementation, not design; if a state cannot be expressed, stop and amend by a new ADR.

## Checklist

- [x] Failing tests first, including a crash test at every durable state transition (between intent and execution, between execution and outcome, between roles, during approval, during verification).
- [x] (F1) `SqliteDelegationStore` in `bOps.Memory`: transactional replace of the whole aggregate; restrictive file permissions on both platforms; `TaskState` and `ITaskStore` unchanged.
- [x] Journal intent before and outcome after, only for side-effecting steps; read-only roles restart from their beginning against remaining budget; bounded resume count.
- [x] Approvals are never persisted: resume requires a fresh human approval of the same plan hash. D returns a `DelegationRun` from memory (`Journal` empty, nothing stored) and asks the human through `IPlanApprovalProvider`; a resumed run asks again through the same provider.
- [x] An ambiguous step is reconciled by its declared `VerificationSpec`; `Refuted` or `Inconclusive` ends as `RequiresReconciliation`; no automatic retry.
- [x] Operator reconcile (accept as done, or abandon) is administrator-only and audited.
- [x] Start is idempotent on a caller-supplied key.

## Definition of Done

- [x] No completed side effect is repeated after any injected crash.
- [x] Every ambiguous state fails closed and is visible.

## Interpretations made in F

Where ADR-0030 section 7 leaves a detail open, F chose as follows. None changes an ADR.

1. **The store is optional.** A `DelegationRunner` built without an `IDelegationStore` keeps a run in memory, as D and E did,
   and has no journal. With one, every transition is saved and the journal is kept.
2. **The run carries its own request.** The Diagnostic role's stored report holds the plan, but not what the operator asked
   for, so `DelegationRun` gains `Authority` and `Remediation`. Both are optional, so a run stored earlier still loads.
3. **What is resumable is `Running`.** A run that ended (`Cancelled` and `DeadlineExceeded` included), or that waits for an
   operator, is returned unchanged by `ResumeAsync`. A run cancelled while a step ran keeps that step's outcome in its journal
   as cancelled (unknown), and its error says so, but resuming it would be a retry, and a retry is a new objective.
4. **Where a resume continues is decided by what is stored.** No completed Discovery: run Discovery. No completed Diagnostic: run
   it. Otherwise the stored plan and the journal decide, not a role's status, so a crash at any point in Remediation or
   Verification lands in the same place. A stored plan whose hash is not the recorded one is not run.
5. **An interrupted role is charged everything it was granted.** What it spent before the crash is not durable, so a restart
   cannot know it; charging the whole grant is the only choice that can never hand a budget back.
6. **Journaled means side-effecting, and only when there is a store.** Read steps are not journaled, and neither is a step of a
   run that is not stored. The outcome is written after the step's own post-action verification, so a crash between the two is
   ambiguous and settled by verification again.
7. **A step reported as failed is done.** A tool that ran and said it failed is not ambiguous and is never run again; the
   plan's verification decides what that means, as before.
8. **Settling an ambiguous step is done by a Verification role.** Each is read by its own recorded role, with its own identity
   and budget, over a plan that holds only that step. Approval is not asked for it: it only reads. Approval is asked only when
   steps are left to run.
9. **Accepting a step does not resume the run.** `ReconcileAsync` marks the unsettled steps done and returns the run to
   `Running`; the caller resumes it, which then puts any steps left to a human. Abandoning ends it as `Abandoned`.
10. **The administrator role is enforced by the surface.** The runtime checks that the decider is a human identity (not an
    agent, the runtime or one of the run's own agents) and audits who it was; that they hold the administrator role is for the
    API and the CLI to authenticate (V1.2-I and V1.2-J).
11. **A repeat start returns the earlier run and nothing else.** With the same operator and key it returns the stored run,
    whatever state it is in, without a delegation id of the caller's own: the run keeps the id it was created with.
12. **Persistence is never cancelled by the caller's token.** A write that records progress or an ending uses no token, so a
    cancellation cannot leave a run half recorded. A write that fails stops the run as failed, except the last one, which is
    logged: the run is returned with how it ended, and the store holds the last state it did save, which a resume treats as
    interrupted.
