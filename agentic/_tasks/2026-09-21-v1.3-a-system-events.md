# V1.3-A — bounded cross-platform system event/log reader

Status: **implemented (2026-09-21); pull request #32, CI green on Windows and Linux**
Recommended model effort: **alto**
Repository: `bOps`
Depends on: V1.2 complete

## Outcome

Restore the system-log capability that existed in the original design but disappeared during the
V0.11 consolidation. Add one read-only, cross-platform `system.events` tool that gives the agent
bounded, structured evidence from Windows Event Log and Linux journald without exposing a generic
shell or an OS-specific command surface.

This capability belongs to the System packages, not Service: it must support service failures but
also kernel, disk, driver, OOM, networking, application-crash and other host events.

## ADR and contract

- [x] Write and accept an ADR for the cross-platform event model and collection strategy before
      implementation.
- [x] Keep one public manifest shape on Windows and Linux. The first contract should cover a bounded
      time window plus optional severity, source/provider-or-unit, event identifier and text filter,
      with explicit `limit` and `maxOutputBytes` ceilings.
- [x] Use UTC timestamps and a normalized result shape containing at least timestamp, severity,
      source, event identifier when present, channel/category when meaningful, message and process
      identity when available.
- [x] Return deterministic newest-first structured JSON with explicit `truncated` /
      `complete` metadata. Permission denial or an unavailable source is never reported as an
      empty healthy result.
- [x] Do not add `service.logs`, `journalctl.*`, `eventlog.*` or other competing public tool
      names in this batch. Service-specific diagnosis is expressed by filtering `system.events`.
- [x] Do not expose raw Windows event XML, the complete journald field bag or unbounded native
      metadata through the tool boundary.

## Windows implementation

- [x] Implement the Windows collector in `bOps.Packages.System.Windows` using the Windows Event
      Log APIs (`EventLogQuery` / `EventLogReader`), not PowerShell or `wevtutil`.
- [x] Query only channels visible to the current host identity; do not elevate privileges or
      silently switch identity to read protected logs.
- [x] Translate Windows levels/providers/event ids/channels into the normalized contract and keep
      unknown values explicit rather than guessing.

## Linux implementation

- [x] Implement the Linux collector in `bOps.Packages.System.Linux` against journald. If
      `journalctl` is selected, invoke the executable directly with
      `ProcessStartInfo.ArgumentList`, fixed switches and separately supplied values: never
      `UseShellExecute`, never a composed command string and never a model-provided switch.
- [x] Compare the direct `journalctl` strategy with a maintained libsystemd binding in the ADR;
      choose the smaller reliable surface for V1.3-A and keep it isolated behind the Linux tool.
- [x] Map priority, unit/syslog identifier, message id, PID and boot/time metadata into the same
      normalized result used on Windows.

## Safety, privacy and bounds

- [x] Default to a narrow recent window and conservative item/output limits; reject out-of-range
      requests rather than silently widening them.
- [x] Treat event messages as untrusted data. They may contain attacker-controlled text and never
      become instructions.
- [x] Keep raw event messages out of audit and telemetry. Audit only the normalized query summary,
      counts, truncation/completeness and outcome; normal bounded tool-result persistence keeps the
      same semantics as every other read tool.
- [x] Do not add a privilege requirement to bOps merely so more channels can be read.
- [x] Cancellation and timeout must stop native enumeration promptly and return the normal bounded
      tool outcome.

## Validation

- [x] Add conformance tests proving Windows and Linux expose the same manifest name, parameters,
      risk and normalized result schema.
- [x] Test severity/source/id/text/time filtering, deterministic order, limits, byte truncation,
      cancellation, inaccessible sources and malformed native records.
- [x] Exercise the Windows implementation against a real Windows Event Log target and Linux against
      a real journald target. If a hosted CI runner does not provide journald, provision a real
      systemd/journald integration target; do not replace platform integration with mocks.
- [x] Add end-to-end agent cases for: recent service failure, OOM/memory-pressure evidence, disk or
      filesystem error, and "errors in the last N minutes".
- [x] Release build, non-live suite and Windows/Linux CI remain green.

## Definition of Done

- [x] `system.events` is registered on Windows and Linux as a bounded `Read` tool.
- [x] A diagnosis can correlate current service/process/system state with recent native OS events
      without a shell or platform-specific public tool.
- [x] Permission gaps and truncation are explicit, and event payloads do not enter audit/telemetry.

## Evidence (2026-09-21)

- ADR: [ADR-0032](../../docs/architecture/adr/0032-bounded-cross-platform-system-events.md), Accepted. Decision D-028.
  User documentation: [`docs/system-events.md`](../../docs/system-events.md).
- Code: shared contract, arguments, filter, formatting and tool base in `bOps.Packages.System.Core`;
  `WindowsSystemEventsTool` (`EventLogQuery`/`EventLogReader`, XPath from validated values) and
  `LinuxSystemEventsTool` (`journalctl` through `ArgumentList`, fixed switches, fixed environment).
- Tests: the shared contract (arguments, filter, ordering, byte and message limits, audit summary, hostile
  message text, manifest parity between the two platforms) and end-to-end agent cases (service failure,
  out-of-memory evidence, disk error, "errors in the last N minutes") run through the real `AgentRunner`.
  The Windows collector runs against this machine's real Event Log (31 tests, including a missing channel and a
  protected one, which must be read or reported unavailable). The Linux collector runs against fake `journalctl` scripts for failure modes and against a
  real journald in the `mcr.microsoft.com/dotnet/sdk:10.0` container (`logger` writes, `journalctl` reads;
  78 Linux tests, all passing).
- Mutation testing: 85 hand-written mutants over the limits, argument validation, filter, formatting, tool
  base, journal parser and arguments, and the Windows XPath. Survivors were closed with boundary tests
  (names with parentheses, the exact 2000/2001-character message limit, a result that fits the byte budget
  exactly, a failed result that still carries output, the latest representable journal timestamp). One
  survivor is equivalent and kept on purpose: `SystemEventFilter` tests `Severity == Unknown` explicitly
  although `Unknown` is the last enum value and `Severity > minimum` would already exclude it; the explicit
  test states the rule and survives a reordering of the enum.
- Local gate: Release build with 0 warnings, non-live suite passing on Windows.
- CI, pull request #32, run `35650105818`: `build-and-test` passed on ubuntu-latest and windows-latest, and `dependency-review` passed.
  Whether the hosted Ubuntu runner exercised a real journald was not separately checked; the container run above remains the
  evidence for that.

## Interpretations worth knowing

- **Linux verification is partly container-based.** A hosted Linux runner may not run journald, so the
  real-journald tests need one; the container run above is the evidence that they pass against a real one,
  and CI confirms the rest.
- **`unit` was added** to the result (the task listed no field for the systemd unit), because on Linux the
  unit is the natural handle for "why did this service stop".
- **Windows records no process name**, so `processName` is `null` there; `processId` is filled when the event has it.
- **The scan ceiling** (10,000 records per source) bounds Linux work; source and text are filtered after the
  scan, so a rare source in a long window is reported as truncated rather than silently missed.
