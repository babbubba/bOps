## Objective

A browser refresh or normal navigation no longer loses authentication, without putting the long-lived
API key in browser storage: the UI exchanges the key once for a bounded, revocable, server-side browser
session carried in a hardened cookie. Bearer access for CLI and API clients is unchanged.

## Confirmed defects addressed

**C-21**: `AuthService` stores token and identity only in in-memory signals
(`auth.service.ts:18`); the login page says the key stays only in the page's memory; the server supports
only `Authorization: Bearer` (`ApiKeyAuthenticationHandler`). After F5 the operator must re-enter the
key and the task watcher is lost (Case E, Case C).

## Source finding IDs

F-16. Documents F-26 (SPA hosting) constraints.

## Scope

Phase 0 — **ADR (mandatory before any code)**: new ADR "Browser web session", amending ADR-0018's
authentication: trust boundary, lifecycle, storage, CSRF, revocation, relation to Bearer. Stop for
operator acceptance.

Phase 1 — implementation per plan §9:
1. `POST /api/session` with `{ "apiKey": "…" }` in the JSON body (never a query string); rate-limited;
   validates exactly like the Bearer handler; returns identity only; sets cookie
   `__Host-bops_session`: opaque 256-bit random, `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`,
   no `Domain`.
2. Server-side session store keeping only an HMAC/hash of the token, credential id, roles snapshot or
   re-resolution rule, key-version fingerprint, created/last-seen/expiry; SQLite so sessions survive API
   restarts. Idle timeout ≈ 60 min, absolute ≈ 12 h (configurable). Removing or rotating the API key
   invalidates its sessions at the next request.
3. Default browser-session cookie (no `Max-Age`); explicit "keep me signed in on this device" sets
   `Max-Age` up to the absolute limit.
4. `DELETE /api/session` revokes server-side and expires the cookie; `GET /api/session/me` works with
   either scheme.
5. New authentication handler accepting the cookie; for unsafe methods (POST/PUT/PATCH/DELETE) a cookie-
   authenticated request must also carry `X-bOps-Request: 1` and a same-origin `Origin` (or `Referer`)
   header; otherwise 403. No CORS policy is added.
6. Bearer handler unchanged; if both are present, Bearer wins.
7. Angular: `AuthService` restores the session via `GET /api/session/me` on boot; login posts to
   `/api/session`; logout calls `DELETE`; the interceptor sends `X-bOps-Request: 1` and no bearer
   header when cookie-authenticated; the raw key is dropped from memory after login; update the login
   page text accordingly.
8. 401 anywhere → "Session expired — sign in" and restore the task watch after re-login (with HARDEN-4).
9. Document the dev-proxy/same-origin requirement and the absence of production SPA hosting (F-26,
   deferred).

## Phase 0 — resolved architecture (ADR-0043, Accepted 2026-10-05)

[ADR-0043](../../docs/architecture/adr/0043-browser-web-session.md) is normative; where it refines the Phase 1 list
above (for example "HMAC/hash", "same-origin `Origin`"), the ADR wins. Summary for the implementation agent:

| Topic | Decision (ADR section) |
|---|---|
| Dev topology hard stop | **Not triggered.** Measured 2026-10-04 with the real `ng serve` + `proxy.conf.json`, Chrome 154 and Firefox 150: the `__Host-` `Secure` `HttpOnly` `SameSite=Strict` cookie is accepted on `http://localhost:4200`, sent through the proxy, survives reload, deletes cleanly. The proxy rewrites `Host` to `localhost:5080` and adds no `X-Forwarded-*`; a page on another `localhost` port is same-site and **does** receive the cookie on simple POSTs (Context) |
| Credential authority | One internal `ApiCredentialAuthority` shared by Bearer and login; Bearer behaviour identical (§2) |
| Token | 32 CSPRNG bytes, unpadded base64url (43 chars, canonical), no rotation during a session, fresh per login (§3) |
| Stored digest | Plain `SHA-256(token)`, 32-byte BLOB primary key; no pepper (§3) |
| Key-version fingerprint | `HMAC-SHA256(key = token, "bops-session-binding-v1" ‖ len ‖ credentialId ‖ SHA-256(secret))`, constant-time compared; removal/rotation/empty secret → 401 and row deleted; the candidate must also be the entry current Bearer resolution selects for its secret, else 401 and row deleted (§2, §4) |
| Roles | Re-resolved from configuration on every request; never snapshotted (§4) |
| Store | `IBrowserSessionStore` / `SqliteBrowserSessionStore` in `bOps.Api`, own file `sessions.db`, `user_version` 1, WAL, `synchronous=FULL`, no cache (§5) |
| Lifetime | Idle 60 min, absolute 12 h; equality is expired; absolute never slides; idle touched at most once per 60 s, only by requests that reach the endpoint (§6) |
| Cookie | `__Host-bops_session`, `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`, no `Domain`; no `Max-Age` by default; `keepSignedIn: true` → `Max-Age` = remaining absolute lifetime (§7) |
| Scheme precedence | Policy scheme: any `Authorization` header → Bearer (valid wins, invalid = 401, never downgrade); else session cookie; else unchanged anonymous (§8) |
| CSRF | Cookie-authenticated unsafe methods (all but GET/HEAD/OPTIONS/TRACE): `X-bOps-Request: 1` exactly **and** `Origin` (or, only when `Origin` is absent, `Referer`) equal to a configured `BrowserSession:Origins` tuple; else 403; `Host`/forwarded headers never read (§9) |
| Login | `POST /api/session`: origin gate always → JSON only (415) → ≤ 4 KiB (413) → strict shape (400) → key (401) → viewer role (403) → create + supersede presented session atomically → 200 identity + cookie (§10.1) |
| Logout | `DELETE /api/session`: cookie → delete row + delete cookie + 204; Bearer → 204 no-op (§10.3) |
| Rate limit | `bops.session-login`: fixed window 10/min per remote IP, queue 0, 429 + `Retry-After` (§11) |
| Configuration | `BrowserSession:Origins` (comma-separated, default `http://localhost:4200`), `IdleTimeout`, `AbsoluteTimeout`, `FilePath`; invalid → startup fails; no insecure switch (§12) |
| Secret leakage | Negative contract; explicit exception handler in every environment so the developer exception page cannot echo cookies (§13) |
| UI | `initializing → authenticated / unauthenticated / unavailable`, `session-expired`; boot via app initializer + `GET /api/session/me`; no `token` signal; interceptor sends `X-bOps-Request` on unsafe relative `/api/` requests and never `Authorization`; one 401 → `session-expired` path in the interceptor (§14) |
| Refresh + watch | Selected task in the dashboard URL `?task=<uuid>`; dashboard re-selects after boot and resumes the HARDEN-4 watch with the snapshot's attempt (§15) |

### Security matrix (abridged; full table ADR-0043 §16)

| Threat | Mitigation |
|---|---|
| Key in browser persistence / URL / logs | Never stored; JSON body only; field cleared after every attempt; no request logging |
| Token theft by script | `HttpOnly`; exception page cannot echo cookies |
| Token / key at rest | Only token digest and token-keyed binding |
| Fixation | Fresh token per login; presented session superseded atomically |
| CSRF cross-site and same-site (other `localhost` port) | `SameSite=Strict` + custom header + configured-origin check |
| Cross-origin reads | No CORS |
| Brute force | Login limiter + global limiter; uniform 401 |
| Replay after logout | Server-side delete; no cache |
| Key removal / rotation | Binding check → 401, row deleted; startup sweep |
| Stale privileges | Roles re-resolved per request |
| Session authority ≠ Bearer authority (same secret under an earlier entry) | Bearer-equivalence check → 401, row deleted |
| Unbounded lifetime / DB growth | Idle + absolute; bounded cleanup |
| Bearer regression / downgrade | Bearer unchanged; any `Authorization` header selects Bearer |
| Residual | Shared `localhost` cookie jar across ports; open polling tab lives to the absolute limit |

### Authentication/CSRF matrix (abridged; normative table ADR-0043 §17, 30 rows)

| Bearer | Cookie | Method | CSRF headers/origin | Expected |
|---|---|---|---|---|
| valid | none | GET | none | Bearer 200 |
| valid | valid | POST | absent | Bearer wins; no CSRF check; cookie untouched |
| invalid / malformed | valid | GET | n/a | 401 (no downgrade) |
| none | valid | GET | n/a | Cookie 200 |
| none | valid | POST | valid | Cookie success |
| none | valid | POST | missing custom header | 403 |
| none | valid | POST | foreign `Origin` / `null` / none at all | 403 |
| none | expired / revoked / rotated | GET | n/a | 401 + cookie deletion |
| none | secret now resolves via Bearer to an earlier credential | GET | n/a | 401, row deleted (later duplicate secret: still valid) |
| none | none | protected | n/a | 401 (unchanged) |

## Out of scope

- Production SPA hosting (deferred, plan §15).

## Architecture constraints

- The raw API key never enters browser storage, URLs, logs or responses.
- Sessions are bounded and revocable; no refresh tokens in the browser.
- Authorization policies (`ViewerPolicy`, `OperatorPolicy`, …) apply identically to both schemes.

## Public contract impact

Additive endpoints (`POST/DELETE /api/session`), additive cookie authentication scheme, additive
configuration (timeouts). No change for Bearer clients.

## Security implications

High sensitivity: CSRF (SameSite=Strict + custom header + Origin check), session fixation (new random
token per login), token theft (HttpOnly, hashed at rest), brute force (rate limit on `POST /api/session`),
revocation on logout and key rotation, no credential echo. Review must cover each explicitly.

## Dependency gates

Browser-session ADR accepted. Canonical order: after HARDEN-8. Interacts with HARDEN-4's 401 handling.

## Acceptance criteria

- [x] F5 on any page keeps the operator signed in within idle/absolute bounds (E2E-8 session part; fake-clock API tests).
- [x] Logout revokes: replaying the old cookie returns 401 (API tests, E2E-8).
- [x] Rotating/removing the API key invalidates existing sessions (API tests, including B-1 cases).
- [x] A cross-origin POST with the cookie (no custom header or foreign `Origin`) is rejected (API CSRF matrix, E2E-8).
- [ ] No response body, log line or browser storage contains the API key — tests pass (API leak scans, Angular storage

- [x] A running task's watch resumes after refresh (Angular URL specs, E2E-8).
