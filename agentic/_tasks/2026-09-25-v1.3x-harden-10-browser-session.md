## Objective

A browser refresh or normal navigation no longer loses authentication, without putting the long-lived
API key in browser storage: the UI exchanges the key once for a bounded, revocable, server-side browser
session carried in a hardened cookie. Bearer access for CLI and API clients is unchanged.

## Confirmed defects addressed

**C-21**: `AuthService` stores token and identity only in in-memory signals
(`auth.service.ts:18`); the login page says the key stays only in the page's memory; the server supports
only `Authorization: Bearer` (`ApiKeyAuthenticationHandler`). After F5 the operator must re-enter the
key and the task watcher is lost (Case E, Case C).

## Source finding IDs

F-16. Documents F-26 (SPA hosting) constraints.

## Scope

Phase 0 — **ADR (mandatory before any code)**: new ADR "Browser web session", amending ADR-0018's
authentication: trust boundary, lifecycle, storage, CSRF, revocation, relation to Bearer. Stop for
operator acceptance.

Phase 1 — implementation per plan §9:
1. `POST /api/session` with `{ "apiKey": "…" }` in the JSON body (never a query string); rate-limited;
   validates exactly like the Bearer handler; returns identity only; sets cookie
   `__Host-bops_session`: opaque 256-bit random, `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`,
   no `Domain`.
2. Server-side session store keeping only an HMAC/hash of the token, credential id, roles snapshot or
   re-resolution rule, key-version fingerprint, created/last-seen/expiry; SQLite so sessions survive API
   restarts. Idle timeout ≈ 60 min, absolute ≈ 12 h (configurable). Removing or rotating the API key
   invalidates its sessions at the next request.
3. Default browser-session cookie (no `Max-Age`); explicit "keep me signed in on this device" sets
   `Max-Age` up to the absolute limit.
4. `DELETE /api/session` revokes server-side and expires the cookie; `GET /api/session/me` works with
   either scheme.
5. New authentication handler accepting the cookie; for unsafe methods (POST/PUT/PATCH/DELETE) a cookie-
   authenticated request must also carry `X-bOps-Request: 1` and a same-origin `Origin` (or `Referer`)
   header; otherwise 403. No CORS policy is added.
6. Bearer handler unchanged; if both are present, Bearer wins.
7. Angular: `AuthService` restores the session via `GET /api/session/me` on boot; login posts to
   `/api/session`; logout calls `DELETE`; the interceptor sends `X-bOps-Request: 1` and no bearer
   header when cookie-authenticated; the raw key is dropped from memory after login; update the login
   page text accordingly.
8. 401 anywhere → "Session expired — sign in" and restore the task watch after re-login (with HARDEN-4).
9. Document the dev-proxy/same-origin requirement and the absence of production SPA hosting (F-26,
   deferred).

## Out of scope

- Production SPA hosting (deferred, plan §15).
- OAuth/SSO, user accounts, password login.
- Switching the UI to native `EventSource` (possible later; keep polling).

## Architecture constraints

- The raw API key never enters browser storage, URLs, logs or responses.
- Sessions are bounded and revocable; no refresh tokens in the browser.
- Authorization policies (`ViewerPolicy`, `OperatorPolicy`, …) apply identically to both schemes.

**New browser-session ADR, accepted before implementation** (hard gate).

## Public contract impact

Additive endpoints (`POST/DELETE /api/session`), additive cookie authentication scheme, additive
configuration (timeouts). No change for Bearer clients.

## Security implications

High sensitivity: CSRF (SameSite=Strict + custom header + Origin check), session fixation (new random
token per login), token theft (HttpOnly, hashed at rest), brute force (rate limit on `POST /api/session`),
revocation on logout and key rotation, no credential echo. Review must cover each explicitly.

## Dependency gates

Browser-session ADR accepted. Canonical order: after HARDEN-8. Interacts with HARDEN-4's 401 handling.

## Acceptance criteria

- [ ] F5 on any page keeps the operator signed in within idle/absolute bounds (E2E-8 session part).
- [ ] Logout revokes: replaying the old cookie returns 401.
- [ ] Rotating/removing the API key invalidates existing sessions.
- [ ] A cross-origin POST with the cookie (no custom header or foreign `Origin`) is rejected.
- [ ] No response body, log line or browser storage contains the API key (tests + manual check).
- [ ] CLI and Bearer API clients behave exactly as before.
- [ ] A running task's watch resumes after refresh.

## Required tests

API tests for login, logout, expiry (idle/absolute with a fake clock), rotation invalidation, CSRF
matrix, rate limiting, both schemes on every policy; UI tests for boot restore, logout, 401 flow;
Playwright E2E-8.

## Required platform evidence

Angular production build and headless tests; API tests on Windows and Linux CI; a manual browser check
of cookie attributes (screenshot of devtools cookie row with value redacted).
