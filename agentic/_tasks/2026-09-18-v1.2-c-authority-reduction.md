# V1.2-C — authority reduction and envelope enforcement

Status: **implemented — ADR-0031 accepted; C1 (profile contracts, reduction), C2 (enforcement) and C3 (`policy.yaml`) implemented; V1.2-D next**
Recommended model effort: **molto alto**
Repository: `bOps`
Depends on: V1.2-B complete
Governing ADRs: `docs/architecture/adr/0030-privilege-reducing-multi-agent-delegation.md`, amended in §3 by
`docs/architecture/adr/0031-per-role-envelope-requirements.md`

## Outcome

Implement envelope reduction and enforce it before policy in the single execution path (ADR-0030 section 3).

## Read first

`2026-09-18-v1.2-b-contracts.md`, sections "Interpretations made while writing the contracts" and "Open
question for V1.2-C" (now resolved by ADR-0031), then ADR-0031 in full.

## Decisions taken (2026-09-19, D-027)

The operator chose, and `agentic/06-decisions.md` D-027 records:

1. **A per-role requirement table.** Each envelope dimension is required (empty is `DelegationDenied`),
   optional (empty means nothing permitted) or not applicable (forced to empty or zero) for each role.
   Least privilege by construction, and an exhausted token budget cannot block an approved plan.
2. **A new ADR-0031** amends ADR-0030 §3, because `agentic/05-workflow.md` forbids editing an accepted ADR to
   change its meaning. ADR-0030 gets an `Amended by ADR-0031` pointer on acceptance.
3. **Profile contracts in the SDK.** A role profile, the operator's authority request and a read-only source
   interface go in `bOps.Abstractions` (`1.2.0-preview.2`); `bOps.Policy` implements the source from
   `policy.yaml`, so `bOps.Runtime` still does not reference `bOps.Policy`.

Two things ADR-0031 makes explicit beyond the table, which the operator reviewed when accepting it:
grant versus exhaustion (§3: a budget granted as zero is a denial, running out mid-run is
`BudgetExceeded`/`DeadlineExceeded` as in ADR-0030 §6), and what an envelope can enforce per step (§4: tools
declare no target, so targets and environments are matched only for steps that carry a skill scope, and a
non-Read step without one is denied in a delegated run).

## Interpretations made in C1

Where ADR-0030 and ADR-0031 leave a detail open, C1 chose as follows. None changes an ADR; each can be
revisited in review.

1. **The root envelope.** ADR-0030 §3 says the root is derived "in the same way", but there is one profile per
   role. C1 derives it as the most the delegation, as configured, could ever exercise: each set is the union of
   the four profiles' sets, each ceiling the highest any role may reach (a read-only role counting as `Read`),
   and each budget the sum across the roles, because they run in sequence and each reserves from the run's total.
   The request then only narrows it. The root is therefore never a source of authority: every role's own
   envelope is inside it and inside its profile.
2. **Fail at the start.** Deriving the root also derives every role's envelope once. A role that would be
   refused later (for example Remediation under a request capped at `Read`) refuses the whole delegation before
   any role has spent a token or the operator has approved a plan. A window that has already ended is refused
   there too.
3. **The table lives in `bOps.Abstractions`, internal.** A profile must refuse a grant in a not-applicable
   dimension when it is built, and the policy loader (which cannot see the runtime) learns of a malformed profile
   from that constructor. So `RoleRequirements` is internal to the SDK and shared with the runtime through
   `InternalsVisibleTo`; the published SDK gains exactly the three types ADR-0031 names.
4. **`EnvelopeDimension.Profile` (13), appended.** A missing, mismatched or malformed profile has no envelope
   dimension to blame. Appending a value keeps every persisted value fixed; the alternative, making the
   dimension of a denial optional, would have changed a B contract.
5. **A read-only role's risk above `Read` is capped, not malformed.** ADR-0031 §1 fixes the ceiling; §2 calls
   only a grant in a not-applicable dimension malformed.
6. **Request budgets are ceilings on the total and on each role.** They are minimums, so both readings agree.
7. **A role's deadline** is the earliest of its parent's, the request's and its start plus its profile's maximum
   duration, added without overflow. The root's is the request's, or the start plus the sum of the durations.
8. **Denial reasons** name the role, the dimension and which of the parent, the profile or the request granted
   nothing. They never carry a member name.
9. **The contracts are snapshots.** The envelope, a profile and a request copy the sets they are built from, so a
   list the caller edits afterwards cannot widen what was validated. This also hardens the B envelope.
10. **`EnvelopeReducer` is internal** and visible only to `bOps.Runtime.Tests`, so nothing outside the runtime
    can derive an envelope. The property test uses its own deterministic generator: `System.Random` does not
    promise its sequence across .NET versions, and it is a security-analyzer finding.

## Interpretations made in C2

Where ADR-0030 and ADR-0031 leave a detail open, C2 chose as follows. None changes an ADR; each can be
revisited in review.

1. **A step is delegated because of the entry point it came through.** The scope (`DelegatedExecutionScope`)
   is a parameter of three internal entry points, `RunDelegatedAsync`, `PrepareDelegatedSkillAsync` and
   `ExecuteDelegatedPreparedSkillAsync`, which cover the three paths that reach `ExecuteStepAsync` (the
   model loop, a Capability's evidence calls, an approved plan). The public methods are unchanged and never
   delegated. "A delegated step without an envelope is rejected" is therefore about the scope: its correlation
   (delegation, agent, envelope hash) and its envelope are separate halves, and a scope that names an agent but
   carries no envelope, or one whose envelope does not hash to the recorded value, refuses every step. C2
   cannot catch an orchestrator that calls a public, non-delegated method for a role by mistake; that is a
   discipline for V1.2-D, which has a checklist item and a test for it.
2. **The check comes right after the tool resolves, before argument validation.** ADR-0030 says before
   `IPolicyEngine.Evaluate`. Putting it before validation as well means a tool the agent may not use never
   answers with an argument error, and the refusal counts as a denial (the repeated-denial stop) instead of
   letting the model fix arguments for a tool it can never call.
3. **A refusal is a Forbidden decision.** It is audited as a `PolicyDecisionAuditEvent` with mode `Forbidden`
   and a reason that starts "Authority envelope:", followed by a `ToolCallAuditEvent` with outcome `Denied` and
   authorization `PolicyDenied`. No new `AuthorizationKind` value: ADR-0030 §3 says the effective decision is the
   more restrictive of envelope and policy, and every caller that already treats a policy denial as a dead end (the
   repeated-denial stop, the replan trigger, the stop of a plan, the refusal of an evidence call) then treats an
   envelope refusal the same way. The reason names the role and what the step asked for; it never lists what the
   envelope allows, because it reaches the model as a tool observation.
4. **The scope is checked as well as the step:** an agent that acts, the recorded envelope, depth exactly 1 (ADR-0030
   §2 rejects any other), and an originator equal to the operator the step runs for (kind and id; the display name is
   cosmetic, as in the envelope hash).
5. **Two structural limits are enforced again at execution.** A read-only role is held to `Read` even by an
   envelope that says otherwise (`RoleRequirements.RiskCap`), and `Critical` never passes whatever the ceiling says.
   The reduction never builds such an envelope; the check exists so a value handed in by mistake cannot turn a role
   that only looks into one that acts.
6. **`PolicyContext` gains `Delegation` and `Envelope`.** ADR-0030 §3 says "the same envelope fields" go into the
   contextual `PolicyContext`, and ADR-0031 §4 says the targets and environments are placed there. C2 reads that as the
   correlation block (delegation, agent and role, envelope hash) and the envelope itself, both `null` outside
   delegation, so a policy rule can see who acts and what the agent may reach. The runtime has already refused
   anything outside the envelope, so it is context for the decision and never a way to widen it. The SDK moves to
   `1.2.0-preview.3`.
7. **Preparing is checked before the Capability's code runs, and a plan is checked whole before its first step.**
   The Skills and Capabilities dimensions are about what an agent may prepare, and a Capability that makes no evidence
   call would never meet the per-step check. A plan whose step the envelope would stop halfway is refused before
   any step runs, mirroring `ValidateExecutionRequest`. Each step is still checked again when it executes, because
   the window can close in between.
8. **Every audit event the runner writes for a delegated role carries the correlation block,** through one write
   helper, `WriteAuditAsync`: tool call, policy decision, approval, model call and Skill run. V1.2-H keeps the
   orchestrator's own events and the read surfaces.
9. **Budgets and the deadline are not checked in the step path.** Using up a granted budget or reaching the deadline
   is `BudgetExceeded` or `DeadlineExceeded`, not a denial (ADR-0031 §3), and the orchestrator decides it (V1.2-E).
   Until E lands the delegated entry points do not stop a role at its deadline.
10. **Post-action verification is not checked against the envelope.** It runs directly, like it bypasses policy
    (rule S4), and is named by the manifest of a tool the envelope already allowed, never by the agent. The
    independent Verification role of V1.2-G reads through the envelope like any other step.
11. **`RunDelegatedAsync` shows the model every registered tool.** It enforces the envelope but does not narrow the
    tool view, which is V1.2-D's checklist item, so a role may be offered tools it will be refused.

## Interpretations made in C3

Where ADR-0030 and ADR-0031 leave a detail open, C3 chose as follows. None changes an ADR; each can be
revisited in review.

1. **A malformed section fails the whole load.** ADR-0031 §2 says a malformed profile denies delegation as a
   whole and §5 says a malformed section yields no profile. The loader throws `PolicyConfigurationException`, as it
   already does for a bad `skills` entry, so both hosts fall back to `AllForbidden`, which ships no profile.
   Delegation is denied, and so is everything else until the file is fixed. The alternative, a policy that loads
   without its broken `delegation` section, would half-load a file the operator got wrong, which is the case the
   hosts' `LoadPolicyEngine` already refuses to treat as more permissive than the operator meant.
2. **The section is read strictly.** The rest of the loader ignores keys it does not know. Inside `delegation` an
   unknown key is an error at every level, because a misspelt `window` would otherwise load as no restriction, and
   the parser reads the YAML representation so it can name the line and the path of each problem. A misspelt
   section name itself (`delegaton:`) is still ignored, like any unknown top-level key, and configures nothing.
3. **Absent grants nothing where "nothing" exists.** An absent list is empty, absent steps or tokens are zero, an
   absent window is no restriction beyond the deadline (ADR-0031 §1). `maxRisk`, `maxBlastRadius` and
   `maxDuration` must be written: a ceiling always permits its lowest value and a duration must be positive, so
   there is no "nothing" to default to. A blank value (`tools:`) is an error and `[]` says none, because a blank
   could as easily be "forgot to fill in".
4. **Names only for enums.** `Enum.TryParse` also reads `3` and `low, medium` (as a flag set), which the section
   refuses. The older sections keep `Enum.TryParse` unchanged; that is outside C3 and is noted below.
5. **A duration writes the time of day.** The .NET constant format reads a bare `10` as ten days, and a duration is
   a security limit that an operator far more likely means as ten minutes, so `maxDuration` is `hh:mm:ss` or
   `d.hh:mm:ss` (`00:10:00`, `1.02:00:00`).
6. **A window instant carries its zone.** `Z` or an offset such as `+02:00`, converted to UTC. An instant without
   one is refused: it means a different moment on every machine, and a window is a security boundary.
7. **The table has one definition.** The loader does not restate which dimensions a role cannot use. The profile
   constructor refuses them, and the parser reports that refusal against the key that caused it
   (`delegation.roles.verification.skills: Skills is not applicable to the Verification role...`). A test restates
   the ADR-0031 table and checks all 32 combinations (role by Skills, Capabilities, tokens) against the loader and
   against the constructor, so the loader cannot drift from either.
8. **A zero budget is well-formed.** ADR-0031 §3: granting a required budget as zero is a denial when delegation
   starts (C1's reduction), not a malformed file. The loader refuses only what cannot be built.
9. **`PolicyRoleProfileSource` is a separate type over `PolicyConfig`,** as `PolicyEngine` is. The config stays a
   plain data holder that copies its profiles, refuses two for one role and a null, and the source keys them by the
   profile's own role, so a profile is only ever returned for the role it is for.
10. **Nothing is wired into a host.** Cli and Api build an `IPolicyEngine` and drop the config. Nothing consumes
    profiles until D, so registering an `IRoleProfileSource` now would be an unused service. D composes
    `PolicyRoleProfileSource` over the same loaded config.

### The `delegation` section

For the operator guide (V1.2-L). Every role is optional and a role with no entry has no profile, which refuses the
delegation. Role names and enum values are case-insensitive; keys are exact.

```yaml
delegation:
  roles:
    discovery:                      # discovery | diagnostic | remediation | verification
      tools: [host.info]            # exact names; absent or [] permits nothing; no wildcards
      maxRisk: read                 # required: read | low | medium | high | critical
      maxBlastRadius: single        # required: single | multiple | fleet
      targets: [host-a]
      environments: [staging]
      maxSteps: 12                  # absent is 0
      maxTokens: 20000              # absent is 0; must be 0 or absent for remediation and verification
      maxDuration: 00:10:00         # required: hh:mm:ss or d.hh:mm:ss
      window:                       # optional; both instants need a zone
        start: 2026-09-20T02:00:00Z
        end: 2026-09-20T04:00:00+00:00
    diagnostic: { ... }             # skills and capabilities are optional here
    remediation: { ... }            # skills and capabilities are used here; maxTokens must be 0
    verification: { ... }           # skills, capabilities and maxTokens must be empty or 0
```

`skills` and `capabilities` are refused for Discovery and Verification, and `maxTokens` above zero for Remediation
and Verification (ADR-0031 §2), by name, with the line.

### Found in passing

**Resolved.** `PolicyConfigLoader`'s `ParseEnum`, used by `defaults`, `tools`, `packages` and `skills`, called
`Enum.TryParse`, which also reads a number or a comma list: `read: "approval, forbidden"` and `read: 3` both loaded as
`PolicyMode` 3, which is not a defined value. `PolicyEngine` returned the mode unvalidated and `AgentRunner` treated
anything that was neither `Forbidden` nor `Approval` as automatic, so that call ran unattended: a fail-open against
rule S3 reachable from configuration text (it needed a deliberate comma or number in an operator-authored file). Fixed
on branch `fix/policy-undefined-mode-fails-closed`: the loader parses names only and names the section and key of a
refused value, and `AgentRunner` turns any mode outside the enum into a Forbidden decision. The `delegation` section
never had it (interpretation 4).
