## Outcome

Implement envelope reduction and enforce it before policy in the single execution path (ADR-0030 section 3).

## Read first

`2026-09-18-v1.2-b-contracts.md`, sections "Interpretations made while writing the contracts" and "Open

## Decisions taken (2026-09-19, D-027)

The operator chose, and `agentic/06-decisions.md` D-027 records:

1. **A per-role requirement table.** Each envelope dimension is required (empty is `DelegationDenied`),
   optional (empty means nothing permitted) or not applicable (forced to empty or zero) for each role.
   Least privilege by construction, and an exhausted token budget cannot block an approved plan.
2. **A new ADR-0031** amends ADR-0030 §3, because `agentic/05-workflow.md` forbids editing an accepted ADR to
   change its meaning. ADR-0030 gets an `Amended by ADR-0031` pointer on acceptance.
3. **Profile contracts in the SDK.** A role profile, the operator's authority request and a read-only source
   interface go in `bOps.Abstractions` (`1.2.0-preview.2`); `bOps.Policy` implements the source from
   `policy.yaml`, so `bOps.Runtime` still does not reference `bOps.Policy`.

Two things ADR-0031 makes explicit beyond the table, which the operator reviewed when accepting it:
grant versus exhaustion (§3: a budget granted as zero is a denial, running out mid-run is
`BudgetExceeded`/`DeadlineExceeded` as in ADR-0030 §6), and what an envelope can enforce per step (§4: tools
declare no target, so targets and environments are matched only for steps that carry a skill scope, and a
non-Read step without one is denied in a delegated run).

## Interpretations made in C1

Where ADR-0030 and ADR-0031 leave a detail open, C1 chose as follows. None changes an ADR; each can be
revisited in review.

1. **The root envelope.** ADR-0030 §3 says the root is derived "in the same way", but there is one profile per
   role. C1 derives it as the most the delegation, as configured, could ever exercise: each set is the union of
   the four profiles' sets, each ceiling the highest any role may reach (a read-only role counting as `Read`),
   and each budget the sum across the roles, because they run in sequence and each reserves from the run's total.
   The request then only narrows it. The root is therefore never a source of authority: every role's own
   envelope is inside it and inside its profile.
2. **Fail at the start.** Deriving the root also derives every role's envelope once. A role that would be
   refused later (for example Remediation under a request capped at `Read`) refuses the whole delegation before
   any role has spent a token or the operator has approved a plan. A window that has already ended is refused
   there too.
3. **The table lives in `bOps.Abstractions`, internal.** A profile must refuse a grant in a not-applicable
   dimension when it is built, and the policy loader (which cannot see the runtime) learns of a malformed profile
   from that constructor. So `RoleRequirements` is internal to the SDK and shared with the runtime through
   `InternalsVisibleTo`; the published SDK gains exactly the three types ADR-0031 names.
4. **`EnvelopeDimension.Profile` (13), appended.** A missing, mismatched or malformed profile has no envelope
   dimension to blame. Appending a value keeps every persisted value fixed; the alternative, making the
   dimension of a denial optional, would have changed a B contract.
5. **A read-only role's risk above `Read` is capped, not malformed.** ADR-0031 §1 fixes the ceiling; §2 calls
   only a grant in a not-applicable dimension malformed.
6. **Request budgets are ceilings on the total and on each role.** They are minimums, so both readings agree.
7. **A role's deadline** is the earliest of its parent's, the request's and its start plus its profile's maximum
   duration, added without overflow. The root's is the request's, or the start plus the sum of the durations.
8. **Denial reasons** name the role, the dimension and which of the parent, the profile or the request granted
   nothing. They never carry a member name.
9. **The contracts are snapshots.** The envelope, a profile and a request copy the sets they are built from, so a
   list the caller edits afterwards cannot widen what was validated. This also hardens the B envelope.
10. **`EnvelopeReducer` is internal** and visible only to `bOps.Runtime.Tests`, so nothing outside the runtime
    can derive an envelope. The property test uses its own deterministic generator: `System.Random` does not
    promise its sequence across .NET versions, and it is a security-analyzer finding.
