## Objective

Tool argument bounds are part of the typed contract, not prose: the runtime enforces them generically
before policy, both provider adapters emit them as native JSON Schema, and tool results carry a
structured failure kind and evidence completeness the runtime can reason about without knowing any
package.

## Confirmed defects addressed

- Step 0 of task 88f97dda: the model asked `system.crashes {"sinceMinutes":43200}`; the bound
  `1..10080` existed only in the parameter description (`SystemToolManifests.cs`: "Crash window in
  minutes (1-10080, default 1440)") and in package code; the schema sent to the model had no
  `minimum`/`maximum`.
- `ToolParameter` has only `Name, Type, Description, Required, Sensitive, AllowedValues`
  (`Tools.cs:67-116`); `ValidateArguments` checks names, required and JSON types only.
- `ToolCallResult` carries only `Outcome, Output, ErrorMessage`: validation failure, environment
  failure, partial collection, internal failure, timeout and authorization failure are not
  distinguishable structurally.

## Scope

1. **Additive `ToolParameter` constraints** as **init-only properties** (not new constructor
   parameters — a constructor change breaks compiled plugins): `Minimum`, `Maximum` (numeric),
   `MinLength`, `MaxLength` (string/path), `MinItems`, `MaxItems` (`PathList`). Validation at
   manifest registration: constraints must match the parameter type and be consistent
   (`Minimum ≤ Maximum`), otherwise registration fails.
2. **Runtime enforcement** in `ValidateArguments`: out-of-range values are **rejected** with a precise,
   model-readable message (`Argument 'sinceMinutes' = 43200 exceeds maximum 10080.`) — never clamped.
   Existing package-level validation stays as defence in depth.
3. **Schema emission** in both adapters: `minimum`, `maximum`, `minLength`, `maxLength`, `minItems`,
   `maxItems`, `enum`, and `additionalProperties: false`.
4. **Migrate every manifest** whose description states a range ("1..N", "1-N", "between") to real
   constraints; keep descriptions human-readable. An architecture test fails if a description states a
   numeric range and the parameter has no matching constraint.
5. **`ToolCallResult.FailureKind`** (init-only, default `Unspecified`): `Validation`, `Environment`,
   `Internal`, `Timeout`, `Authorization`. The runtime tags its own failures automatically
   (argument validation → `Validation`, tool timeout → `Timeout`, policy/envelope/entitlement denial →
   `Authorization`, thrown exception → `Internal`); packages may set `Environment` (provider missing,
   access denied, unsupported).
6. **`ToolCallResult.Completeness`** (init-only, default `Unspecified`): `Complete`, `Partial`,
   `Unavailable`. Packages that already emit `complete`/`truncated`/`status` in their JSON set it;
   start with `system.crashes`, `system.events`, `storage.*`, `process.list`, and document the rule for
   the rest. The runtime records it on the step and in the audit summary.
7. Model-facing observation for a failure includes the kind: `ERROR (validation): …`.

## Out of scope

- Aggregation/stability evidence (HARDEN-7), prompt rules (HARDEN-9).
- Changing tool names or risk levels.

## Architecture constraints

- Additive-only changes to `bOps.Abstractions` (ADR-0022): binary compatibility for plugins built
  against 1.x must be preserved; add a compatibility test that a manifest built with the old constructor
  still loads.
- The core names no package or tool; completeness is read from the typed result, never by parsing
  package JSON in the runtime.
- Validation still runs before policy, approval and execution (rule S2).

## ADR prerequisite

**ADR-0022 amendment**: additive constraint properties, `FailureKind`, `Completeness`; binary
compatibility rule. Accepted before implementation.

## Public contract impact

Additive `ToolParameter` init properties; additive `ToolCallResult` init properties; schema output
stricter (`additionalProperties:false`). No breaking change.

## Security implications

- Stricter validation reduces the attack surface of model-supplied arguments.
- `additionalProperties:false` must match runtime behaviour (unknown arguments are already rejected).
- No clamping, ever.

## Dependency gates

HARDEN-1 complete (adapters already alias names; schema emission builds on them). HARDEN-7 and
HARDEN-9 depend on this packet.

## Acceptance criteria

- [ ] `system.crashes` schema sent to the model contains `"minimum":1,"maximum":10080` for
      `sinceMinutes` (both adapters).
- [ ] `sinceMinutes=43200` is rejected before policy with the precise message and `FailureKind=Validation`.
- [ ] Every range stated in a manifest description has a constraint (architecture test green).
- [ ] Old-constructor manifests still register (compatibility test).
- [ ] `system.crashes` partial output yields `Completeness=Partial` on the step and in audit.
- [ ] E2E-2 passes: invalid numeric argument → validation failure → model corrects → task completes.
