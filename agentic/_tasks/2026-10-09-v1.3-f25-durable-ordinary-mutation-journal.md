ADR-0051 is the specification. This packet restates what F-25B must build and prove; where the two differ, ADR-0051
wins and the difference is a defect in this packet to be reported, not resolved silently.

## 1. Problem

A process death, a cancellation or a timeout while an ordinary task executes a non-`Read` tool can leave the task in a
state where the mutation may have happened but nothing persisted says so. A later resume rebuilds the model history
without it, and the model can propose — and, under `Automatic` policy, execute — the same mutation again. Stable V1.3
must never let an unknown prior outcome look like a safe retry.

## 2. Existing behaviour (baseline `9707803`)

- `AgentRunner.ExecuteStepAsync` (`src/core/bOps.Runtime/AgentRunner.cs:3407`) gates every call (resolution, envelope,
  validation, policy, approval/binding, entitlement) and then, at `:3635`, journals only delegated non-`Read` calls:
  `var journal = manifest.Risk != RiskLevel.Read ? delegation?.Journal : null;`. Ordinary non-`Read` calls have no
  durable record until the loop's per-step `SaveOwnedAsync` (`:1147ff`).
- Delegated runs (ADR-0030, `IStepJournal`, `StepJournalEntry`, `StepOutcome`, `StepReconciliation`,
  `DelegationRunner.SettleJournalAsync` / `ReconcileAsync`) already implement intent-before / outcome-after,
  ambiguous → declared verification → `RequiresReconciliation`, administrator accept/abandon, no retry.
- Ordinary cancellation during a non-`Read` call propagates without a step (`:3670` handles only the delegated case);
  the launcher writes `Cancelled`, which ADR-0040 makes resumable.
- An ordinary non-`Read` timeout is recorded and verified, then the loop replans (`:1130-1133`) and the model may call
  it again.
- ADR-0040: a persisted `Running` task is never ordinarily resumable, and there is no recovery path for an orphaned one.
- `SqliteTaskStore` implements `ITaskStore` + `ITaskTransitionStore`; single `tasks` table.

## 3. Chosen architecture (ADR-0051 §2)

1. New table `task_mutation_journal` in `tasks.db`, behind the additive capability
   `ITaskMutationJournalStore : ITaskTransitionStore`. Every write fenced on the task row `(Running, ExecutionAttempt)`
   in the same statement/transaction.
2. Intent at one point: after entitlement allowed, before `ExecuteWithTimeoutAsync`. Identity `(TaskId,
   ExecutionAttempt, StepIndex)` + per-task `Sequence`. Contents: tool, redacted-canonical arguments hash, risk,
   declared verifier name, plan revision / planned index, time. No arguments, no output.
3. Outcome kinds `NotInvoked` / `Returned` / `TimedOut` / `Cancelled` / `Interrupted`; journal states `Pending` /
   `Settled` / `Ambiguous` / `Escalated` / `ReconciledDone` / `Abandoned`. A settled outcome is committed atomically with
   the step that records it.
4. In-process unknown (timeout, cancellation, attempt-duration interruption) that verification does not confirm ends the
   attempt; never a replan or retry.
5. Orphaned `Running`: administrator-only fenced recovery `(Running,N) → (Failed,N)`, `TerminalKind.ExecutionInterrupted`,
   executes nothing.
6. Reconciliation: administrator `verify` / `acceptDone` / `abandon`; no retry. Resume refused while any entry is
   unsettled or abandoned; the acquisition appends `Mutation reconciled` history steps; identical calls to reconciled
   mutations are escalated to approval.
7. New ordinary tasks record `MutationJournalMode` (`Journaled` or, without the capability, `MutationsDisabled`);
   pre-F-25 rows are `Absent` and are neither resumable nor recoverable.
8. Nothing at startup.

## 6. Persistence contract

### 6.1 `bOps.Abstractions` (additive; bump the preview version)

- `TaskMutationJournalMode { Absent = 0, Journaled = 1, MutationsDisabled = 2 }`; `TaskState.MutationJournalMode`
  (init-only, default `Absent`; written for every new ordinary task).
- `MutationOutcomeKind { NotInvoked = 0, Returned = 1, TimedOut = 2, Cancelled = 3, Interrupted = 4 }`.
- `TaskMutationState { Pending = 0, Settled = 1, Ambiguous = 2, Escalated = 3, ReconciledDone = 4, Abandoned = 5 }`.
- Records: `TaskMutationKey(TaskId, ExecutionAttempt, StepIndex)`; `TaskMutationIntent` (key, tool, arguments hash,
  risk, verification tool name?, plan revision?, planned step index?, intent time); `TaskMutationOutcome` (kind, tool
  outcome?, tool failure kind?, verification?, time); `TaskMutationJournalEntry` (intent fields, `Sequence`, outcome?,
  `State`, `StepReconciliation?`, `HistoryRecordedInAttempt?`); `TaskMutationResolution` (key, expected state, new
  state, `StepReconciliation`); `TaskJournalSnapshot` (task, entries).
- `ITaskMutationJournalStore : ITaskTransitionStore` with exactly the five methods of ADR-0051 §11.
- `TaskTerminalKind.MutationOutcomeUnknown = 14`, `ExecutionInterrupted = 15`.
- `TaskLifecycleStage.RecoveryAccepted = 5`, `RecoveryRejected = 6`.
- `TaskMutationAuditEvent` (discriminator `taskMutation`) and `TaskMutationAuditStage { IntentCommitted,
  IntentNotCommitted, OutcomeCommitted, OutcomeNotCommitted, AmbiguityDiscovered, VerificationAttempted, Reconciled,
  ReconcileRejected }` with explicit values.
- Reused unchanged: `ReconciliationAction`, `StepReconciliation`, `DelegationHasher.ComputeArgumentsHash`,
  `ToolArguments.Redact`.
- Round-trip serialization tests for every new type; an old `TaskState` JSON without the new member loads `Absent`.

### 6.2 `SqliteTaskStore` (`bOps.Memory`)

- Schema of ADR-0051 §6.2, created idempotently in `EnsureSchema`; nothing in `tasks` changes.
- Each write per ADR-0051 §6.3: one statement or one `BEGIN IMMEDIATE` transaction, `PRAGMA synchronous=FULL` on the
  connection, no load/check/save in process.
- `TryTransitionAsync` additionally refuses an acquisition (`task.ExecutionAttempt == expected + 1`) while the task has a
  `Pending`, `Ambiguous`, `Escalated` or `Abandoned` entry.
- `LoadWithJournalAsync` reads task and entries in one read transaction.

## 7. Resume / reconciliation rules

- Resume: ADR-0040 §3 rows 1–6, then ADR-0051 §9.4 rows 6a–6e, then ADR-0040 rows 7–9. Acquisition through
  `TryAcquireAsync` when the store has the capability, carrying one `Mutation reconciled` synthetic step per
  `ReconciledDone` entry with `HistoryRecordedInAttempt == null`.
- Recovery: ADR-0051 §8.3, administrator, body `{ executionAttempt }`, `TryTransitionAsync((Failed,N) + "Execution
  interrupted" step + TerminalReason ExecutionInterrupted + materialized accounting, Running, N)`.
- Reconcile: ADR-0051 §9.1–§9.3, administrator, human identity, task not `Running`, per-entry CAS.
  `verify` never invokes anything but the declared verifier through the post-action verification path, and only when
  the task's persisted step for `(attempt, stepIndex)` exists with matching tool and redacted-arguments hash.
- Approvals: never carried. Duplicate guard: `(ToolName, ArgumentsHash)` equal to a `ReconciledDone` entry of the same
  task escalates `Automatic` → `Approval` with a fixed reason marker; never relaxes. The runner reads the
  `ReconciledDone` set from the journal snapshot loaded when the attempt starts (no entry can become `ReconciledDone`
  while the task is `Running`).

## 8. API / CLI / UI impact

- API (`src/core/bOps.Api`): view fields (`mutationJournal`, `recoverable`, `recoveryBlockedReason`; extended
  `resumeBlockedReason`; PRE-4 `executionPlan` status `OutcomeUnknown`); `/events` also emits when the journal summary
  (count per state) changes; `POST /{id}/recover` and `POST /{id}/reconcile` under `ApiAuthorization.AdministratorPolicy`;
  resume returns the new codes. Codes and bodies exactly as ADR-0051 §8.3, §9.4, §14.2.
- CLI (`src/core/bOps.Cli`): `bops recover <id> --attempt <N>`, `bops reconcile <id> verify|accept|abandon [--note]`.
- UI (Angular dashboard): ADR-0051 §14.4 — Recover (admin, with the confirmation text), unsettled-mutation banner,
  Verify again / Accept as already applied / Abandon (admin), no retry control, status qualifier "outcome unknown",
  plan-panel state, EN/IT, 375/768/1024/1440 px without overflow.

## 9. Security impact

- Fail-closed additions only: a non-`Read` call cannot run without a committed, fenced intent; a task cannot resume past
  an unknown mutation; no stale executor can settle or replay; no startup action.
- New administrator operations (recover, reconcile) execute no mutating tool; `verify` runs only the declared `Read`
  verifier, with fresh entitlement.
- The journal stores no arguments, output, credentials or provider material; the arguments hash is computed over
  redacted values. Audit events carry no payloads; the administrator note is bounded and audit-only.
- Threat-model / API authorization matrix entries for the two endpoints must be added (`docs/` security pages that list
  task endpoints).

## 10. Backward compatibility

- Additive public surface and an additive table; `ITaskStore` unchanged; third-party stores compile.
- Behaviour changes (documented in CHANGELOG and operator docs): unconfirmed mutation timeout/cancellation ends the
  attempt and blocks resume; duplicate-of-reconciled escalation; pre-F-25 ordinary tasks not resumable
  (`mutation_journal_absent`); stores without the capability cannot run non-`Read` tools in new tasks; downgrade to a
  pre-F-25 binary unsupported.
- Existing tests that assert the old timeout → replan behaviour for **non-`Read`** tools, or ordinary resume of a
  `Cancelled` task cancelled mid-mutation, encode the defect: update them to the ADR, never weaken the ADR to keep them.
  `Read` timeout → replan behaviour is unchanged and its tests must stay green unmodified.

### 12.4 The core property: execution count never becomes 2

`NeverExecutesAnAmbiguousMutationTwice` — a theory over every injection of §12.2 that leaves a durable intent
(T2b–T10b) × reconciliation outcome (`verify` where available, `acceptDone`, `abandon`, none) × policy (`Automatic`,
`Approval` with an approver that rejects requests carrying the duplicate marker). Each case runs the full
restart → recover → reconcile → resume flow with a model that, on resume, proposes the identical call first and a
different read second. Assert: `CountingMutatingTool.Executions` ≤ 1 for that intent in every case; no recovery,
reconciliation or startup path invoked the mutating tool; where the task stayed blocked, no new execution attempt was
created. (An approver who knowingly approves a request naming the reconciled duplicate is an informed human decision;
the test asserts the marker is present in that request.)

## 14. Stop conditions (F-25B)

Stop and report — do not work around — if:

- ADR-0051 is not **Accepted** by the operator, or is accepted with amendments this packet does not reflect.
- Any requirement can be met only by persisting arguments, a projection of them, or tool output in the journal.
- Any executor, cancellation, backstop, recovery or reconciliation write cannot be fenced as ADR-0051 §6.3 requires, or
  the outcome cannot be committed atomically with its step.
- SQLite cannot provide a required write as one statement or one `BEGIN IMMEDIATE` transaction.
- The change would require touching the delegation journal (`IStepJournal`, `DelegationRunner` journal/reconcile) or
  ADR-0030 behaviour.
- PRE-4's projection would need a second state machine instead of a journal input.
- An existing test outside §10's list contradicts the ADR (it may encode a different accepted ADR).
- A package or tool name would have to appear in `bOps.Runtime`, `bOps.Memory` or `bOps.Abstractions` (rule A1).
- Anything would execute at process startup.
