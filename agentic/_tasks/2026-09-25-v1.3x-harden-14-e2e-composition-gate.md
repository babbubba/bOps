## Objective

Prove that the hardened components compose into a reliable troubleshooting product: every scenario
E2E-1 … E2E-14 of plan §17 runs deterministically and green, and the Definition of Done A–D of plan
§18 is evidenced — not merely that each unit passes its own tests.

## Confirmed defects addressed

Composition failures of the whole review: individually green components (provider adapter, runner,
launcher, watcher, normalizers, delegation reducer, UI) failed together in real operator use (Cases A–E,
plan §2.1). This packet adds no product behaviour; it closes gaps found while composing and reports
anything that cannot be closed.

## Source finding IDs

All findings F-01 … F-24 as verified by their owning packets; F-25/F-26 remain deferred (plan §15).

## Deferred from HARDEN-1 review

**N-3 (full registered-tool catalog test).** A HARDEN-1 review note asking for an end-to-end test that
exercises the complete registered-tool catalog (not a representative subset) through the strict fake
provider. Does not reopen HARDEN-1. Fold into this gate's composition test suite.

## Scope

1. Consolidate the scenario suite: deterministic scripted fake model(s), the strict fake provider from
   HARDEN-1, fake backends for UI runs, and real-platform conformance for HARDEN-5/HARDEN-7.
2. Implement the scenarios not owned by earlier packets: **E2E-1** (diagnose a stopped Docker service —
   Linux CI with Docker, Windows where available) and **E2E-11** (mutation → approval → execution →
   verification).
3. Run every scenario E2E-1 … E2E-14 and record results.
4. Evidence the Definition of Done A–D with concrete artifacts (test names, logs, screenshots,
   real-host excerpts).
5. Separate, non-gating live smoke (`Category=LiveModel`) with the configured default model; record,
   never gate on it.
6. Update README/CHANGELOG/HANDOFF and this plan's status table (§20) with verified results only.
7. Document production SPA hosting as still deferred (F-26) and the dev-proxy requirement.

## Out of scope

- New product features; a failing scenario is fixed only if the fix is small and inside an already
  completed packet's scope — otherwise report it as a blocker with a proposed packet.
- Deferred items (plan §15).

credentials or machine configuration.
