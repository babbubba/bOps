## Outcome

Run the fixed Discovery, Diagnostic, approval, Remediation, Verification pipeline over the existing paths (ADR-0030 sections 2 and 4).

## Checklist

- [x] Failing tests first with a fake model and fake tools: happy path, malformed delegation, no plan (diagnosis only), approval rejected, denied step.
- [x] `DelegationRunner` in `bOps.Runtime`; roles are profiles from configuration, not hard-coded products; the core names no package or tool (A1).
- [x] Discovery and Diagnostic reuse the existing loop and restricted invoker through a tool view filtered by the envelope; no second loop or second authorization path. V1.2-C2 added the delegated entry points (`RunDelegatedAsync`, `PrepareDelegatedSkillAsync`, `ExecuteDelegatedPreparedSkillAsync`), which enforce the envelope but still offer the model every registered tool: narrowing `GetAvailableManifests()` by the role's envelope is D's.
- [x] Remediation executes exactly the approved plan hash with no model call; a plan/approval mismatch stops before the first step.
- [x] Inter-agent values are structured Evidence/Finding/ExecutionPlan/VerificationReport only, delivered as delimited data (S5); every Finding cites Evidence.
- [x] Roles cannot request delegation; depth is fixed and any other depth is rejected.
- [x] Build each role's scope with `DelegatedExecutionScope.For(delegationId, agent, envelope)` and reach the runner only through the delegated entry points. The public `RunAsync`, `PrepareSkillAsync` and `ExecutePreparedSkillAsync` are never delegated, so a role that used one would run unrestricted: the C2 enforcement cannot catch that, so a test must show every event of every role carries the correlation block.
- [ ] Compose `PolicyRoleProfileSource` (V1.2-C3) over the same loaded `PolicyConfig` the policy engine is built from, and register it as the `IRoleProfileSource`, in both hosts. **Moved to V1.2-I and V1.2-J:** a host can only register the `DelegationRunner` together with the `IPlanApprovalProvider` its own channel implements (a console prompt, an API queue), and those are the surfaces' work. D shows the behaviour that matters with the profile source as an interface: a role with no profile ends the run as `Denied` on the `Profile` dimension before any model call, and `AllForbidden` has none (C3). The host-level test that the broken-policy case reaches `Denied` belongs with the wiring.
- [x] Derive the root envelope with the V1.2-C1 reduction at the start and each role's envelope from it, write a `DelegationEnvelopeAuditEvent` for every reduction and every refusal, and end a refused delegation as `DelegationStatus.Denied` before any model call. The reduction only returns the result; the orchestrator audits it.
- [x] Before asking for a role's envelope, check the run's deadline and end the run as `DeadlineExceeded` (ADR-0031 §3). Never hand the reduction an exhausted parent to be refused as a denial. **Steps and tokens are not counted here**: a role's consumption stays empty until V1.2-E, which counts them and reserves each role's budget from the parent's remaining amount; a model loop that uses up the runner's own step limit already ends the run as `BudgetExceeded`.
- [x] Before asking the operator to approve a prepared plan, check that Remediation's envelope would allow every step (tool, risk, blast radius, target, environment). A plan that is certain to be denied is rejected up front instead of being approved and then refused.

## Interpretations made in D

Where ADR-0030 and ADR-0031 leave a detail open, D chose as follows. None changes an ADR; each can be revisited in
review.

1. **Plan approval is a new host-facing contract in the SDK.** The existing `IApprovalProvider` asks about one tool
   call; nothing asked a human about a plan's hash. `IPlanApprovalProvider` and `PlanApprovalRequest` join
   `bOps.Abstractions` (`1.2.0-preview.4`, additive). The request's constructor refuses a hash that is not the plan's own,
   and the runtime, not the provider, binds the decision to the hash (`ExecutionPlanApproval`), so the provider cannot
   approve one plan and authorize another.
2. **A decision must come from a human identity.** It is refused, and the run ends as `Rejected`, when the approver's
   kind is `agent` or `system` or its id is one of the run's own agents. This is the minimum D needs to keep an approval
   human-only; V1.2-G states the separation of duties as its own guarantees. The decision is audited either way.
3. **`DelegationStage.PlanDecided` and `DelegationLifecycleAuditEvent.PlanHash`** are appended to the audit contracts, so a
   human's decision has an event: its actor is who decided and its hash is what they decided on. Appended after the values
   persisted since `1.2.0-preview.1`.
4. **The operator names the change; the model never picks a Capability.** `DelegationRequest.Remediation` carries the
   Skill, the Capability and its input, target, environment and blast radius. Without it the run is a diagnosis only. With
   it, both the Diagnostic role (to prepare) and the Remediation role (to run) must be allowed that Skill, Capability,
   target, environment and blast radius, or delegation is `Denied` before any role starts, like C1's fail-at-the-start.
5. **Role envelopes are derived when each role starts,** from the root, the profile and the request with the current
   time, so a role's duration counts from its start. The derivation at the start of the run only proves each role can be
   derived. One `DelegationEnvelopeAuditEvent` is written per role at that moment, with the root's hash as the parent.
6. **A denial is attributed to a role.** The audit event has a required role, and the reduction did not say which role a
   refusal was about, so `EnvelopeReducer.DeriveRootAttributed` reports it (`DeriveRoot` is unchanged). A refusal of the
   request itself, its deadline or window, belongs to no role and is audited under the first role of the pipeline. A run
   refused before any root exists is correlated to the hash of an envelope that grants nothing.
7. **Evidence ids are predictable:** `{role}-{index of the step}` for a Read call, and `verification-{index of the plan
   step}`, so a later role can cite exactly what it was shown. Every item is stamped with who gathered it, including the
   Capability's own evidence, which is the Diagnostic agent's.
8. **The Diagnostic role answers in JSON findings,** and a finding is kept only if it has a summary and every id it cites was
   recorded in the run. A reply that is not that JSON yields no finding, never a guessed one. Findings a Capability builds
   are kept as they are: the runner already validates them.
9. **Evidence reaches the next role as one delimited block in its goal,** through the same wrapper every tool result
   uses (now `internal`), which neutralizes a delimiter inside the data. It is not a synthetic tool-result turn, which
   would need a fake assistant call. The consequence is that the goal, which the task store persists, contains that data.
10. **The approved plan is copied when it is prepared,** and its hash recomputed, so a list a Capability keeps and edits
    while the human decides cannot change what runs. The plan that runs is exactly the plan that was shown.
11. **How a run ends, decided here.** A model loop that stops short maps `MaxStepsReached` and `BudgetExceeded` to
    `BudgetExceeded`, `PolicyBlocked` to `PolicyBlocked`, `Cancelled` to `Cancelled` and the rest to `Failed`. A plan the
    envelope would refuse is `PolicyBlocked` before a human is asked; a step denied by policy or the envelope is
    `PolicyBlocked`; a human rejecting a single step is `Rejected`; a plan refused for another reason is `Failed`, and it is
    told from an envelope refusal by checking the envelope again, not by reading a message. Remediation's role report stays
    empty, as the contract says: what it did is in the audit trail, under the plan hash.
12. **The Verification role exists in a first, deterministic form.** For each step of the approved plan that declares a
    verification it reads the system through its own envelope, in the one step pipeline, and asks the tool's own evaluator what
    that fresh reading means. Refuted beats Inconclusive beats Not applicable beats Confirmed; a read it may not take is
    Inconclusive, and a plan with nothing to verify is Not applicable, neither of which is success. The runtime's own check
    right after a step (rule S4) still runs inside Remediation; the Verification role does not use its result, and a test
    shows the two readings differ. G states these as separation-of-duties guarantees and covers what construction does not.
13. **Only the deadline is checked before a role.** Steps and tokens are not counted and a role's `Consumed` stays empty
    (V1.2-E). Cancellation propagates as an exception; ending the run as `Cancelled` is E's.
14. **The run is in memory.** `StartAsync` returns a `DelegationRun` with an empty journal and stores nothing (V1.2-F). It
    takes an optional id for a caller that must hand it out first.
15. **The tool view is narrowed by the envelope:** a delegated role is offered only the tools its envelope allows and no
    more than its risk ceiling (`Read` for a read-only role). This narrows what is offered and grants nothing: the envelope is
    still enforced on every call.
16. **Nothing is wired into a host.** Registering `PolicyRoleProfileSource`, the `DelegationRunner` and an
    `IPlanApprovalProvider` belongs with the CLI (V1.2-I) and the API (V1.2-J), which implement the human approval channels.
