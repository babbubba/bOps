## Objective

A fresh, configured installation can run a diagnosis-only delegation after an explicit, safe, read-only
profile setup; the operator sees readiness per role **before** submitting; remediation remains
fail-closed and requires all four roles; profiles cannot silently drift; capability input has a
schema-driven form.

## Confirmed defects addressed

- Case B: diagnosis-only delegation `Denied` with *"Discovery role: no usable profile is configured.
  Delegation stays off until the operator configures one for every role."*
- `EnvelopeReducer.DeriveRootAttributed` iterates all of `RoleRequirements.Pipeline` (Discovery,
  Diagnostic, Remediation, Verification) regardless of `Request.Remediation`
  (`EnvelopeReducer.cs:63-78`); Remediation Skills/Capabilities are `Required`
  (`RoleRequirements.cs:62-67`); ADR-0030 §1 mandates "a role without a profile denies delegation".
  An operator must therefore author mutation-capable grants to diagnose.
- No readiness/preflight in API, CLI or UI; the Delegations page looks usable and fails after submit.
- No skills/capabilities catalog endpoint; the UI has no capability-input field although
  `CapabilityManifest.InputSchema` exists.
- Profiles enumerate explicit tools; new diagnostic tools are silently absent (drift).
- Guard complement to HARDEN-3: role tasks resume only through the delegation run.

## Scope

Phase 0 — **ADR work (mandatory before any code)**: amend **ADR-0030 §1/§3** and **ADR-0031** so the
required role set depends on the request: diagnosis-only (`Remediation == null`) requires Discovery and
Diagnostic; a remediation request requires all four, unchanged and fail-closed; the root envelope is
derived from the required roles only. Amend **ADR-0018** for the new endpoints. Stop for operator
acceptance.

Phase 1 — implementation:
1. Request-dependent role requirements in the reducer and orchestrator; `DiagnosisCompleted` path
   unchanged; remediation path unchanged.
2. `GET /api/delegations/readiness?remediation=false|true` (Viewer policy): runs the runtime's own
   reducer against a synthetic request and returns per role `ready | missing | malformed | notRequired`
   with the reducer's reason and dimension, plus a profile drift count. No policy logic in Angular.
3. CLI `bops delegate readiness [--remediation]`.
4. CLI `bops delegate profiles init --read-only`: writes (or prints for review) an explicit YAML with
   Discovery and Diagnostic profiles listing the currently registered **Read** tools by name (expanded
   at generation time — no runtime wildcards), finite token/step budgets, `targets: [local]`,
   `environments: [local]`, a deadline, no Skills/Capabilities, and **never** a Remediation profile.
   Refuses to overwrite an existing policy file without an explicit flag.
5. CLI `bops delegate profiles check`: reports drift (registered Read tools absent from read-only
   profiles, unknown tool names, malformed dimensions).
6. `GET /api/skills`: activated Skills and Capabilities with `CapabilityManifest.InputSchema` and risk.
7. UI Delegations page: readiness panel (four roles with state and reason), Submit disabled with the
   reason when not ready, re-query when "prepare a change" toggles; schema-driven capability-input form
   generated from `InputSchema` (+ HARDEN-6 constraints), raw JSON only as an advanced fallback;
   Skill/Capability chosen from the catalog instead of free text.
8. Documentation: `docs/agents/delegation-policy.md` safe setup path for a fresh install.

## Out of scope

- Automatic creation of any profile at startup.
- Wildcard or category grants evaluated at runtime.
- Changing envelope enforcement, plan approval, journal or verification of the remediation path.

## Architecture constraints

- Never silently grant mutation authority; generated profiles are read-only and explicit.
- Envelope enforcement still applies to every delegated step; `child ⊆ parent ∩ profile ∩ request`.
- Delegation readiness is computed server-side only.

## Public contract impact

Behavioural authority change (documented by ADR; no API break); additive endpoints

## Security implications

Authority semantics change: review must prove that a diagnosis-only run can never reach a non-Read
tool, that remediation still requires all four roles, and that generated profiles contain only Read
tools. Property/negative tests are mandatory.

## Dependency gates

ADR-0030/ADR-0031 amendments accepted. Canonical order: after HARDEN-10. Requires HARDEN-3's role-task
guard to be in place.

## Acceptance criteria

- [ ] E2E-9: after `profiles init --read-only`, a diagnosis-only delegation completes
      `DiagnosisCompleted`.
- [ ] E2E-10: with no profiles, the UI shows per-role reasons and blocks Submit; the API readiness
      endpoint returns the same reasons.
- [ ] A remediation request with only read-only profiles is `Denied` naming the missing roles.
- [ ] Generated profiles contain only `RiskLevel.Read` tools and no Skills/Capabilities.
- [ ] `profiles check` reports a newly registered Read tool as drift.
- [ ] Capability input form generated from `InputSchema` validates constraints client-side and
      server-side.

## Required tests

Reducer tests for both request shapes; property tests (diagnosis-only envelope never exceeds Read);
policy loader tests for generated YAML; API readiness/skills tests; CLI tests; UI tests and Playwright
E2E-9/E2E-10.

## Required platform evidence

Windows and Linux CI; a real run on a fresh configuration directory showing readiness before and after
`profiles init --read-only`.
