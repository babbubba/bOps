## Purpose

The human calibration of R01 (B02 rerun at cd00e81, 118 claims) showed what the P1 evaluator measures and what it does not:

| What the P1 evaluator did | Claims |
|---|---|
| Emitted no negative result at all | — |
| Missed a numeric error | C100 |
| Missed an impossible recommendation | C113 |
| Could not classify two contradictions | C05, C63 |
| Scored any number in the claim | 34 of 118 |

Zero alarms did not establish its detection precision. V2 adds the deterministic dimensions the calibration found missing, stays offline, never calls a model, and can be compared claim by claim and run by run with the frozen P1 baseline.

## Hard boundaries

- **Test-side only, as P1.** `tests/bOps.DiagnosticEvaluation`: never shipped, no `src/` project references it. Microsoft Agent Framework stays at the exact pin. No runtime, CLI, API, prompt, policy or contract change.
- **No model judge.** No LLM call of any kind (P2 stays a separate, unauthorized decision).
- **Read-only on evidence.** The campaign evidence and the agent's answers are never modified. Output goes to a new folder (`auto-evaluation-v2/`) beside the P1 `auto-evaluation/`, which is never overwritten.
- **Blind and private.** Results keyed by blind code; no evidence or answer text in any output, report or repository file.
- **Human verdicts are not used to tune or rewrite past evaluations.** Calibration sheets are used only to measure V2 after V2's rules are frozen for a measurement round.

## Requirements

**R1 — Value, unit and scale.**
- Parse number + unit (B, KB, MB, GB, TB, KiB…GiB, %, s/min/h, days).
- Compare against typed facts or numeric output fields in a declared unit, with an explicit scale factor.
- Verdicts: `exact`, `rounded` (within the declared rounding of the unit), `scale-error` (correct digits, wrong order of magnitude), `wrong`, `untraced`.
- Thousands separators of the answer locale (`1.769`, `1 232`) are understood.

**R2 — Binding to the right typed fact.**
- Each number binds to a typed fact or to a keyed output field, not to "any number of the output". This replaces P1's `inEvidence`, which accepts a number found anywhere.
- The binding records fact id/key, step and source.
- A number equal to a value of an unrelated fact or field is `untraced`, not accepted.
- Family terms are specific per key, so that "gruppi" of events is not "gruppi" of crashes. String event ids (`"eventId":"19"`) and dates with month names (`28-set`) are identifiers, not counts.

**R3 — Source completeness.**
- Every bound value carries its source state: `complete`, `partial` or `unavailable`, read from the tool's `Completeness` and coverage fields.
- A claim that presents a value from a partial source as complete, without coverage wording in the same sentence or table row, gets the dimension `coverage-undisclosed`.
- A value of an unavailable or `notCollected` source is never treated as 0. A claim stating 0 for it is `absence-as-zero`.

**R4 — Time window.**
- Each bound value carries the effective window: the requested window cut to the source's oldest retained record.
- Dates and periods in the claim are compared with that window.
- A claim that extends one source's window to another source is `window-mismatch`. Example: System/Application log coverage applied to the WER archive.

**R5 — Deduplication across sources.**
- The key declares equivalences for events that record the same occurrence through different providers. Examples: EventLog 6008 ≡ Kernel-Power 41; WER 1001 bugcheck ≡ Kernel-Power 41 with the same code; `displayFault` 0x193 ≡ `system.crashes` kernel-live-dump 0x193.
- Each equivalence has a matching rule: time tolerance and code.
- A claim that sums equivalent groups, or counts them as distinct phenomena, is `double-count`.
- An "N episodes" claim that cannot be shown by event-level pairing is `pairing-unverified`.

**R6 — Sample message versus group property.**
- When the tool marks a group's message as a sample (newest event only) and the group has more than one distinct message, a claim that attributes the sample's content to the whole group is `sample-generalised`.
- The claim's count stays checkable separately under R1–R2.

**R7 — Model visibility.**
- From the persisted observations and the audited EvidenceRead ranges, rebuild which character ranges of each tool output the model saw.
- Every bound value and fact is tagged `seen` or `unseen`.
- Per run: share of facts and groups never seen. Per claim: `claims-about-unseen-evidence`.
- Omissions caused by unseen evidence are reported as `retrieval-gap`, separately from grounding errors.

**R8 — Temporal feasibility of recommendations.**
- Recognise recommendations (imperative and next-check sections) that name artefacts and their target events, for example "analyse the 5 minidumps for bugchecks 0xa/0xd1".
- Check the target events' dates against the artefacts' available dates.
- Verdicts: `feasible`, `partially-feasible`, `infeasible`, `not-assessable`.

**R9 — Read-only versus mutating operations.**
- Classify each recommended action:
  - `read-only-acquisition`;
  - `offline-dump-analysis`;
  - `version-config-check`;
  - `system-modification` (updates, restore or reset of services, enabling monitoring, stress or diagnostic tests that change state or need a reboot).
- A modification listed among checks without a separation or approval wording is `mutation-not-flagged`.
- The vocabulary is declared in the key, never derived from tool names in the core.

**R10 — Hypotheses apart from facts.**
- Claims are classified as `fact`, `hypothesis`, `limitation`, `recommendation` or `formatting`.
- Hypotheses are evaluated only on:
  - whether they are marked as hypotheses;
  - whether their supporting numbers are bound (R1–R2);
  - whether a causal connective asserts more than the evidence. The deterministic markers come from the key, e.g. "→ perdita di corrente" from a 0x0 code.

  They are never scored as supported or unsupported facts.
- Limitations are checked for being true (R3–R4), not for being "supported".

**R11 — Output and comparability.**
- Per run `auto-evaluation-v2/<code>.json`. Each claim records its dimensions separately:
  - value;
  - binding;
  - completeness;
  - window;
  - dedup;
  - sample;
  - visibility;
  - feasibility;
  - operation class;
  - claim class.
- A `retro/` comparison against the frozen P1 baseline joins by blind code and sentence. Every P1 verdict is classified as `confirmed`, `refined` (same number, new dimension) or `overturned` (P1 accepted, V2 rejects), with its reason.
- Deterministic: two executions give identical bytes. The manifest records commit, key hashes, evaluator hash and input hashes.

**R12 — Report.** `maf_cli_analysis.py` gains per-dimension `v2*` metrics (class C/H). P1 `auto*` metrics stay unchanged, so old reports remain reproducible.

## Operator refinements (2026-10-27b) — they override the requirements above where they differ

**Outcome vocabulary.**
- Every check returns exactly one of:
  - `verified` (the evidence positively supports the dimension);
  - `violation`;
  - `inconclusive` (the evidence needed exists but does not settle it);
  - `not-evaluated` (out of the check's scope, or input missing).
- The verdict names of R1–R9 (`exact`, `scale-error`, `double-count`, …) are **reasons** attached to one of these four outcomes.
- The absence of a detected violation is **never** reported as correctness: a claim with no violation and no `verified` check is `not-evaluated`, not "ok".

**R5, deduplication by correlation only.**
- Events of different providers are never deduplicated by family alone.
- An equivalence of the key applies only when a correlation succeeds on the available evidence: shared identifiers or references (report id, dump reference, bucket), timestamps within the declared tolerance, and the same code.
- Without sufficient evidence the outcome is `inconclusive`, not `double-count` and not `verified`.

**Separate metrics, no aggregate score.**
- Reported for each of seven dimensions, never combined:
  - accuracy and units of values;
  - grounding;
  - time coverage;
  - causality;
  - diagnostic completeness;
  - recommendation feasibility;
  - coverage of the evaluator itself.
- For each dimension, report the counts of the four outcomes and, where human verdicts exist, the agreement on the claims both judge.

**Datasets.**
- R01 is the development and regression set, not an independent test of V2.
- R02–R04 calibrate.
- R05–R06 are the holdout: V2's rules (keys, vocabularies, thresholds) are frozen and hashed **before** the final comparison with R05–R06, and R05–R06 are never used to set or tune a rule.

The protocol and the sample with its inclusion probabilities are private (`Documents\bOps-MafBenchmarks\calibration\diag-eval-20261027\`).

## Metrics and acceptance criteria

**A1 Offline tests.** Synthetic captures cover every R1–R10 verdict, at least one positive and one negative case each. They include a reconstruction of each R01 calibration case from synthetic data:
- C100 (wrong value bound by a generic term);
- C63 (scale error);
- C113 (infeasible recommendation);
- C05 (inverted window);
- C54 (sample generalised);
- C72 (double count);
- C42 / C45 (retrieval gap);
- C70 / C84 (mutation not flagged).

Each must be detected. Mutation checks: disabling R1, R2, R5 or R8 makes at least one test fail.

**A2 Determinism and comparability.** Two executions are byte-identical. The `retro/` comparison runs on the frozen baseline and classifies 100% of P1 findings; none is left unclassified.

**A3 No regression of P1.** The P1 tests and the P1 `auto*` metrics are unchanged. P1 output is not overwritten.

**A4 Measured on the human calibration (R01 + the R02–R06 sample), with V2 rules frozen before the human verdicts are read.** Reported per dimension, never as one aggregate:
- **Numeric errors** (value, unit, scale): detection recall over human-identified numeric errors, and precision over V2's numeric alarms (now defined, because V2 emits alarms).
- **Infeasible recommendations:** recall.
- **Coverage, window and dedup:** agreement with the human value / coverage / interpretation dimensions on the claims both judge.
- **Hypotheses and limitations:** reported separately, never mapped to supported or unsupported.
- **Claims V2 cannot assess:** count and share.

Thresholds are set by the operator **after** the R02–R06 calibration and before V2 is used for decisions. Proposed starting points:
- numeric precision ≥ 0.9 and numeric recall ≥ 0.8 on human-identified numeric errors;
- infeasible-recommendation recall ≥ 0.8;
- no `exact` / `confirmed` on a claim the human contradicted on its value.

**A5 Privacy.** No evidence or answer text in outputs, tests or repository; synthetic fixtures only.
