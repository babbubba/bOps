## Objective

The agent reasons like a competent operator about evidence quality, generically: it distinguishes
current-state from historical evidence, correlated evidence from coincidence, absence of evidence from
evidence of absence, and incomplete from complete evidence — and its final answer states the
limitations of what it saw.

## Confirmed defects addressed

- In task 88f97dda the agent sampled current CPU (0 %), RAM (59.5 %) and disk free space — real but weak
  evidence about months of intermittent freezes — and was never prompted to weigh it against historical
  evidence or to disclose partial/truncated sources.
- The system prompt (`AgentRunner.cs:57-68`) contains only the tool-output-is-data rule.
- `system.events` output was dominated by the bOps dev host's own `.NET Runtime`/Aspire errors
  (self-noise, H-6).

## Source finding IDs

F-22 (reasoning and disclosure part). Hypothesis H-6.

## Scope

1. **Generic evidence rule** appended to the system prompt, phrased without any OS, product or symptom
   specifics: classify evidence as current-state vs historical; prefer historical evidence for
   intermittent or past problems; treat a single current sample as weak for a historical question;
   seek correlation in time between independent sources; distinguish "not found" from "not collected /
   not available / outside retained history"; never state a cause the evidence does not support.
2. **Final-answer requirement**: the final response contains a short "Evidence limitations" section when
   any step reported `Completeness` ≠ `Complete`, a coverage shorter than requested, a failed tool, or a
   truncated observation.
3. **Runtime completeness digest**: before the model's final turn (or when it proposes a final answer),
   the runtime supplies a runtime-authored, delimited digest listing steps with `Partial`/`Unavailable`
   completeness, failures by `FailureKind`, and coverage mismatches — built only from typed
   `ToolCallResult` fields (HARDEN-6/7), never by parsing package JSON in the core.
4. **Self-noise control in `system.events`**: an aggregate mode (group by source/event id with counts,
   first/last seen) and an `excludeSources` filter (bounded list), so the agent can remove the bOps
   host's own noise without hiding it (the exclusion is echoed in the output).
   *Reconciled with HARDEN-7 (2026-10-02):* the aggregate mode already exists as the HARDEN-7 contract
   `mode` = `raw` | `aggregate` of `system.events` (default `raw`; ADR-0032 HARDEN-7 amendment, D-037).
   HARDEN-9 uses that contract and introduces no `aggregate` parameter or any second aggregation
   switch; the `excludeSources` filter remains in this packet's scope.

## Out of scope

- Windows-freeze-specific or any symptom-specific reasoning in the universal prompt.
- Automatic post-processing that rewrites the model's conclusions.
- Context compaction (HARDEN-8).

## Architecture constraints

- The prompt stays product- and platform-neutral; the core names no package or tool.
- Tool output remains data; the digest is runtime-authored and clearly delimited from tool output.

## Acceptance criteria

- [x] E2E-3: a scripted run with partial/truncated evidence produces a final answer containing an
      "Evidence limitations" section naming the partial sources and coverage.
      *Made precise (ADR-0042 §5, §6, §17 rows 23–24):* the run's step prompts carry the evidence-limitations digest,
      a scripted final answer without a heading triggers exactly one disclosure re-ask, and the persisted final answer
      is the re-ask's answer with the heading; the sources and coverage are named by the (scripted) model from the
      tools' own results, never by the runtime.
- [x] A run where all evidence is complete produces no limitations section.
      *Made precise:* no digest in any request and no re-ask; the runtime never adds or removes text. With an empty
      digest no section is required; the model is not forbidden to disclose a limitation it judges material.
- [x] The system prompt contains no OS-, product- or symptom-specific terms (test asserts a deny-list).
      *Made precise:* the evidence rule states clauses E1–E8 of ADR-0042 §4 in at most 2,000 characters, contains no
      identifier-shaped token and nothing from the fixed deny-list, and may use ordinary words such as `complete`,
      `partial`, `coverage`, `truncated` and "not visible".
- [x] `system.events` `excludeSources` works on Windows and Linux in both `mode: raw` and the HARDEN-7
      `mode: aggregate`, and echoes the exclusion; no second aggregation parameter exists.
- [x] The digest is built only from typed `ToolCallResult` fields and persisted step data, is deterministic, bounded
      (16 entries, 4,608 characters), identical after resume, lists uncorrected validation failures and never an
      unresolved tool name, and cannot be forged by tool output (ADR-0042 §5).
- [x] The disclosure re-ask never executes a tool and never loses the original final answer: a tool call, empty reply,
      heading-less answer or model failure keeps the original; no new step, replan or status change — including at the
      step cap (ADR-0042 §6, §17 row 17).
- [x] The heading detector accepts only the headings of ADR-0042 §6 and rejects prose, inline code, fenced and indented
      code.
- [x] HARDEN-7 N-2: the `system.crashes` description states the `BlueScreen`/`kernel-bugcheck` `reported` exception;
      `schemaVersion` unchanged.

### Reconciliations of this packet's text

1. **Scope 3, "coverage mismatches".** There is no typed coverage field; HARDEN-7 folds a coverage gap into
   `Completeness.Partial`. The digest lists `Partial` and points the model to the tool's own `coverage`; it never parses
   the JSON (ADR-0042 §5).
2. **Scope 2, "a truncated observation".** Covers both a tool's own truncation (`Partial`) and the runtime's rule-C3
   shortening of the observation, detected by `Observation.StartsWith(Output, Ordinal)` on persisted data; the digest
   lists both.
3. **Scope 2, "a failed tool".** Every non-`Validation` failure is listed and never superseded; a `Validation` failure is
   listed unless a later step on the same resolved tool succeeded; an unknown tool appears as `(unknown tool)`.
4. **Scope 3, "before the model's final turn (or when it proposes a final answer)".** Both: the digest is in every step
   prompt once non-empty, and one tool-free disclosure re-ask runs when a final answer has no valid heading
   (ADR-0042 §6).
5. **Scope 4, "bounded list".** `excludeSources` is a comma-separated `String` (≤ 8 entries), because the only list
   parameter type is `PathList`; the echo is an array (ADR-0032 HARDEN-9 amendment §1, §4).
6. **Scope 1, "seek correlation in time"; "never state a cause the evidence does not support".** Correlation forms
   hypotheses only; ordering between different events is a derived fact only under the clock preconditions of
   ADR-0042 §8; a cause is only ever reported as a record's own attribution (§2); no code correlates.

### HARDEN-8 interface (no HARDEN-8 work here)

The digest is built from persisted steps and is unaffected by compaction; steps are referenced by index, which HARDEN-8's
evidence ids must resolve to; the evidence rule and digest are fixed prompt costs. HARDEN-9 detects and discloses
observations shortened by the 4,000-character budget and does not change it; the budget against 32–64 KiB typed evidence
results and the full typed-evidence projection strategy belong to HARDEN-8 (recorded in the HARDEN-8 packet). HARDEN-9
does not touch `ReplanAsync`, compaction, evidence retrieval or `ContextOverflow`. Order: HARDEN-7 → HARDEN-9 → HARDEN-8.
