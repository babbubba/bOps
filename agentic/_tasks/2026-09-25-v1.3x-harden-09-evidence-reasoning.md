## Objective

The agent reasons like a competent operator about evidence quality, generically: it distinguishes
current-state from historical evidence, correlated evidence from coincidence, absence of evidence from
evidence of absence, and incomplete from complete evidence — and its final answer states the
limitations of what it saw.

## Confirmed defects addressed

- In task 88f97dda the agent sampled current CPU (0 %), RAM (59.5 %) and disk free space — real but weak
  evidence about months of intermittent freezes — and was never prompted to weigh it against historical
  evidence or to disclose partial/truncated sources.
- The system prompt (`AgentRunner.cs:57-68`) contains only the tool-output-is-data rule.
- `system.events` output was dominated by the bOps dev host's own `.NET Runtime`/Aspire errors
  (self-noise, H-6).

## Source finding IDs

F-22 (reasoning and disclosure part). Hypothesis H-6.

## Scope

1. **Generic evidence rule** appended to the system prompt, phrased without any OS, product or symptom
   specifics: classify evidence as current-state vs historical; prefer historical evidence for
   intermittent or past problems; treat a single current sample as weak for a historical question;
   seek correlation in time between independent sources; distinguish "not found" from "not collected /
   not available / outside retained history"; never state a cause the evidence does not support.
2. **Final-answer requirement**: the final response contains a short "Evidence limitations" section when
   any step reported `Completeness` ≠ `Complete`, a coverage shorter than requested, a failed tool, or a
   truncated observation.
3. **Runtime completeness digest**: before the model's final turn (or when it proposes a final answer),
   the runtime supplies a runtime-authored, delimited digest listing steps with `Partial`/`Unavailable`
   completeness, failures by `FailureKind`, and coverage mismatches — built only from typed
   `ToolCallResult` fields (HARDEN-6/7), never by parsing package JSON in the core.
4. **Self-noise control in `system.events`**: an aggregate mode (group by source/event id with counts,
   first/last seen) and an `excludeSources` filter (bounded list), so the agent can remove the bOps
   host's own noise without hiding it (the exclusion is echoed in the output).
   *Reconciled with HARDEN-7 (2026-10-02):* the aggregate mode already exists as the HARDEN-7 contract
   `mode` = `raw` | `aggregate` of `system.events` (default `raw`; ADR-0032 HARDEN-7 amendment, D-037).
   HARDEN-9 uses that contract and introduces no `aggregate` parameter or any second aggregation
   switch; the `excludeSources` filter remains in this packet's scope.

## Out of scope

- Windows-freeze-specific or any symptom-specific reasoning in the universal prompt.
- Automatic post-processing that rewrites the model's conclusions.
- Context compaction (HARDEN-8).

## Architecture constraints

- The prompt stays product- and platform-neutral; the core names no package or tool.
- Tool output remains data; the digest is runtime-authored and clearly delimited from tool output.

## Public contract impact

`system.events` additive parameter `excludeSources` and its echo in the output; the aggregate view is the
existing HARDEN-7 `mode: aggregate` (no new aggregation parameter). No Abstractions change.

*Made precise by the architecture gate (ADR-0042 §14):* `excludeSources` is a comma-separated `String` (no list type
exists outside `PathList`), echoed as an always-present array; `system.events` stays at `schemaVersion` 2; one additive
runtime option `Agent:EvidenceDisclosureRetries` (default 1); the runtime system prompt gains the evidence rule; step
prompts carry the digest; the final-response path gains one bounded re-ask. No change to `bOps.Abstractions`,
`system.crashes`, `system.stability`, provider projection, persistence or the audit schema.

## Security implications

The digest must not be injectable by tool output (it is built from typed fields only). Source exclusion
is bounded and echoed so evidence is never silently hidden.

## Acceptance criteria

- [ ] E2E-3: a scripted run with partial/truncated evidence produces a final answer containing an
      "Evidence limitations" section naming the partial sources and coverage.
      *Made precise (ADR-0042 §5, §6, §17 rows 17–18):* the run's step prompts carry the evidence-limitations digest,
      a scripted final answer without the section triggers exactly one disclosure re-ask, and the persisted final
      answer is the re-ask's answer containing the section; the sources and coverage are named by the (scripted) model
      from the tools' own results, never by the runtime.
- [ ] A run where all evidence is complete produces no limitations section.
      *Made precise:* no digest in any request and no re-ask; the runtime never adds or removes text.
- [ ] The system prompt contains no OS-, product- or symptom-specific terms (test asserts a deny-list).
      *Made precise:* the evidence rule states clauses E1–E8 of ADR-0042 §4 in at most 2,000 characters; the deny-list
      also covers tool, package and provider names and name-shaped tokens.
- [ ] `system.events` `excludeSources` works on Windows and Linux in both `mode: raw` and the HARDEN-7
      `mode: aggregate`, and echoes the exclusion; no second aggregation parameter exists.
- [ ] The digest is built only from typed `ToolCallResult` fields and persisted step data, is deterministic, bounded
      (16 entries, 4,608 characters), identical after resume, and cannot be forged by tool output (ADR-0042 §5).
- [ ] A disclosure re-ask that fails, returns nothing, or is disabled never loses the original final answer
      (ADR-0042 §6).

### HARDEN-7 contracts verified against the code

`system.events` schema 2 (`mode` `raw` default, explicit `aggregate`, `windowDays` 1–180 aggregate-only, record times);
`system.crashes` schema 2 (`mode` `aggregate` default, explicit `raw`, `sinceDays` 1–180 aggregate-only, GUID-only merge,
`timestampKind`, `BlueScreen` `EventTime` `reported`); `system.stability` schema 1 (eight categories, applicability and
status, `null` for unknown, timeline per kind); `coverage` and the stricter `complete` on all three, folded into the typed
`Completeness` by `EvidenceCompleteness` inside System.Core; `ToolCallResult` and `ToolCallAuditEvent` carry `Outcome`,
`FailureKind` and `Completeness`; the runtime prompt holds only the tool-output-is-data rule; observations are cut to
`MaxObservationCharacters` (4,000). Details: ADR-0042 Context.

### Reconciliations of this packet's text

1. **Scope 3, "coverage mismatches".** There is no typed coverage field; HARDEN-7 folds a coverage gap into
   `Completeness.Partial`. The digest lists `Partial` and points the model to the tool's own `coverage`; it never parses
   the JSON (ADR-0042 §5).
2. **Scope 2, "a truncated observation".** Covers both a tool's own truncation (`Partial`) and the runtime's rule-C3
   shortening of the observation, which only the runtime knows; the digest lists both.
3. **Scope 2, "a failed tool".** Every non-`Validation` failure is listed; contract errors (bad arguments, unknown tool)
   are not evidence limitations.
4. **Scope 3, "before the model's final turn (or when it proposes a final answer)".** Both: the digest is in every step
   prompt once non-empty, and one disclosure re-ask runs when a final answer lacks the section (ADR-0042 §6).
5. **Scope 4, "bounded list".** `excludeSources` is a comma-separated `String` (≤ 8 entries), because the only list
   parameter type is `PathList`; the echo is an array (ADR-0032 HARDEN-9 amendment §1, §4).
6. **Scope 1, "seek correlation in time".** Correlation forms hypotheses only; the causality rule of ADR-0042 §2 and the
   time rules of §8 bound it; no code correlates.

### HARDEN-8 interface (no HARDEN-8 work here)

evidence ids must resolve to; the evidence rule and digest are fixed prompt costs; the 4,000-character observation budget
