## Objective

Implement the resume state machine of master plan §8: resume either makes real progress from a
coherent, persisted, audited transition, or is refused with a reason. Budgets have explicit per-attempt
and lifetime semantics; tokens are never reset; delegated role tasks are never resumed outside their
envelope; orphaned `Running` tasks are distinguishable from executing ones.

## Confirmed defects addressed

- **C-04** resume returns 202 before persisting `Running`.
- **C-05 (backend part)** SSE `/events` stops on the first non-`Running` snapshot, including the stale
  pre-resume one.
- **C-06** `MaxStepsReached` resumes with zero steps (`15 < 15`); task `8747e59a`.
- **C-07** zero-plan `Failed` tasks: 202, then `InvalidOperationException` in detached execution; five
  such tasks in the store.
- **C-08** resume accepted for any status including `Completed`; duplicate resume → body-less 503.
- **C-09** `ResumeAsync` resets `totalTokens` to 0; resume not audited.
- **C-10** synthetic failure steps consume step indices; `MaxSteps` is an undocumented lifetime cap.
- **C-11** delegated role tasks resumable via `/api/agents/tasks/{id}/resume` with `delegation: null`.
- **C-12** orphaned `Running` indistinguishable from executing.

## Scope

1. **Task model (additive):** `TaskState.Attempt`, `TokensUsed` (cumulative), `LifetimeSteps` (or
   derived), `ReplansUsed`, `TerminalReason` (kind + sanitized text, from HARDEN-2), `Origin`
   (`Direct` | `DelegatedRole` with `DelegationId` and role); `PlanStep.Attempt`. Old rows deserialize
   with defaults (attempt 1, origin `Direct` unless a delegated marker exists).
2. **Delegated role marker:** `RunDelegatedAsync` persists `Origin=DelegatedRole` and the delegation id
   on the role task.
3. **Resumability rules** exactly as master plan §8, computed by one runtime function returning
   `(resumable, reason)`; used by the API and the CLI.
4. **Atomic transition:** a store compare-and-set (`version`/`updated_at` precondition) that writes
   `Running`, `Attempt+1`, `resumedBy`, `resumedAt` **before** the 202; the detached run starts from
   the persisted snapshot. Two concurrent resumes: exactly one wins, the other gets 409.
5. **HTTP semantics** for `POST /api/agents/tasks/{id}/resume`: 202 with the new snapshot; 409 with
   `{ code, message }` for non-resumable status, already executing, role task, lifetime cap reached;
   503 with body and `Retry-After` when the launcher is at capacity (also for `POST /tasks`).
6. **Budget semantics:** `MaxSteps` per attempt; new `Agent:MaxLifetimeSteps` (default keeps
   single-attempt behaviour documented); tokens cumulative against `MaxTotalTokens` and never reset;
   `MaxReplans` per attempt plus a lifetime replan cap; synthetic failure steps do not count against
   the step budget.
7. **Zero-plan resume** re-enters planning as the new attempt instead of throwing.
8. **Resume note:** on resume the runtime appends one runtime-authored user turn: "Previous attempt
   <n> ended: <kind>: <reason>. Continue toward the original goal." (runtime text, not tool output).
9. **Lifecycle audit:** new `TaskLifecycleAuditEvent` with stages `Started`, `Resumed`, `Terminal`;
   carries actor, attempt, prior status, terminal reason, budget snapshot (tokens used, lifetime steps,
   caps).
10. **Executing vs orphaned:** the task view gains `executing` (launcher holds the task in this host),
    `resumable`, `resumeBlockedReason`, `attempt`, `tokensUsed`. "Interrupted" is a view label for
    `Running && !executing`; no new `AgentTaskStatus`.
11. **SSE `/events`:** continues across the attempt boundary (does not stop on a snapshot whose attempt
    is lower than the attempt current when the stream opened, or when a resume is pending).
12. **CLI `bops resume`** uses the same rules and messages.
13. **Cancel** endpoint behaviour unchanged but returns the updated snapshot; cancellation remains
    audited via the lifecycle event.

## Out of scope

## Architecture constraints

- No new `AgentTaskStatus` value.
- Resume never runs a role task without its envelope; the only resume path for a role task is the
  delegation run resume (`POST /api/delegations/{id}/resume`).
- Everything audited, including refusals (log + audit where an actor is known).
- Test-first on the core (`agentic/04-testing-rules.md`).

## Public contract impact

Additive `TaskState`/`PlanStep` fields; additive `TaskLifecycleAuditEvent`; additive view fields;
behavioural change of `POST /resume` status codes (409/503 bodies); semantic change of `Agent:MaxSteps`
to per-attempt plus additive `Agent:MaxLifetimeSteps`. See plan §13.

## Security implications

- Role-task guard closes an envelope bypass (F-05).
- Token budget can no longer be bypassed by repeated resume; any cap increase is a visible configuration
  act, and every resume is audited with a budget snapshot.
- Compare-and-set prevents two executors on one task in one host.

## Acceptance criteria

- [ ] For every row of plan §8, a test proves the specified resumability, transition and response code.
- [ ] After a 202, `GET /api/agents/tasks/{id}` immediately returns `Running` with the incremented
      attempt.
- [ ] `MaxStepsReached` with lifetime headroom progresses ≥ 1 step; at the lifetime cap it returns 409.
- [ ] Zero-plan `Failed` resume re-plans and progresses.
- [ ] Tokens used are cumulative across attempts; `BudgetExceeded` is resumable only when the configured
      cap exceeds tokens used.
- [ ] Resume of a role task returns 409 and does not execute anything.
- [ ] Two concurrent resumes: one 202, one 409.
- [ ] Every start, resume and terminal transition writes a `TaskLifecycleAuditEvent`.
- [ ] The view reports `executing=false` for a persisted `Running` task with no executor.
- [ ] SSE does not end on the stale pre-resume snapshot.
- [ ] E2E-6 and E2E-7 pass at the API level.
