# V1.3 pre-release stabilization — real-run findings and stable-release gate

**Status:** Planned — promoted by operator on 2026-10-08  
**Scope:** OSS V1.3 only. This packet starts after HARDEN-14 and after PRs #88, #89, #90, #91 and #92 are merged.  
**Goal:** close the concrete gaps found by real Qwen/KD runs before tagging a stable V1.3. Do not start V1.4 work from this packet.

## Why this packet exists

The deterministic HARDEN train is closed, but real Qwen/KD runs on 2026-10-08 exposed defects that the synthetic gates did not:

1. `system.dump_analyze` is correctly registered, prerequisite-gated and dynamically becomes Available after installing Microsoft Debugging Tools while bOps is running, but the first real execution is cancelled by the runtime-wide `Agent:DefaultToolTimeout = 00:00:30` before DumpChk/KD can finish. The tool itself already has bounded internal limits (DumpChk 60 s, KD 10 min).
2. ADR-0046 binds an execution step to `ExpectedTool`, but that is not enough when several consecutive plan steps use the same tool for different diagnostic intents. In task `8cc482b5-3ac3-4de5-af07-1d1f334bf80b`, several `system.events` steps advanced even though the query no longer matched the semantic purpose of the current step.
3. The same run showed that newly discovered evidence does not reliably cause the plan to include a specific available follow-up such as `system.dump_analyze`. Runtime must not hard-code package/tool names, but planning needs a bounded, generic way to preserve conditional diagnostic follow-ups or request a replan when evidence changes the useful next action.
4. `EvidenceRead/v1` worked for the first exact JSON request, then Qwen emitted an XML/native-tool-like `runtime_evidence_read` fragment. Runtime did not recognize it as EvidenceRead, and the fragment became a candidate final response. The disclosure corrective re-ask then timed out twice and the task was still persisted as `Completed` with the protocol artifact as its answer.
5. A previous real diagnostic run showed that a model can contradict persisted evidence in final synthesis (for example, collected WHEA Event 19 evidence later described as absent). The evidence/tool layer was correct; the final synthesis was not sufficiently grounded.
6. The execution plan and its revisions are persisted but not visible enough to the operator. With ADR-0046/0047 the plan is now execution authority, so current step, correction and replan history are operational state, not hidden model reasoning.

The fixes below are pre-release stabilization. They are not permission to redesign the agent loop broadly.

## Canonical order

```text
PRE-1 per-tool bounded timeout policy
  -> PRE-2 planned-step semantic integrity + evidence-driven follow-up design
  -> PRE-3 EvidenceRead/control-plane + terminal-response hardening
  -> PRE-4 execution-plan visibility UI
  -> PRE-5 evidence-grounded final synthesis guard
  -> PRE-6 real-model / real-KD release evidence
  -> PRE-7 production install/upgrade + soak gate
  -> PRE-8 final V1.3 release gate
```

PRE-2 must precede PRE-4: the UI must not label a step Completed merely because the same tool name was called for a different semantic purpose.

## PRE-1 — Per-tool bounded execution timeout

**Priority:** BLOCKER for stable V1.3  
**Implementation:** Sonnet High  
**Review:** Opus Medium/High

### Problem

Runtime applies one `AgentRunnerOptions.DefaultToolTimeout` (30 s) to every tool. This is safe as a default but wrong for deliberately long, bounded operations. `system.dump_analyze` internally permits DumpChk for 60 s and KD for 10 min, yet the caller cancels it at 30 s. Raising the global default to 10–12 min would weaken containment for every other tool.

### Required architecture

- Keep the host authoritative over the maximum permitted tool duration.
- Add a generic, additive per-tool timeout declaration to the tool contract or equivalent package-owned metadata.
- A tool may request a longer timeout but may never exceed a host-owned hard ceiling.
- No `if (tool.Name == ...)` or package/tool names in `bOps.Runtime`.
- Existing tools without an override retain today's 30 s behaviour.
- Effective timeout must be deterministic and visible in audit/diagnostic state.
- Configuration validation must reject incoherent values, for example default > host ceiling.
- Cancellation, attempt-duration limits and explicit operator cancellation continue to win over the per-tool timeout.
- `system.dump_analyze` must have enough caller budget for its bounded internal sequence. Its package already enforces DumpChk <= 60 s and KD <= 10 min; choose an outer declaration with bounded overhead, target 12 min unless review proves a smaller safe value.
- The same mechanism may later be used by bounded Docker build/pull; do not broaden this packet into changing them unless tests show it is required.

### Acceptance

- Ordinary hanging tool still times out at the default.
- A long-running test tool with a declared longer timeout runs past the default but not past its declared/host ceiling.
- A malicious/excessive declaration can never defeat the host ceiling.
- `system.dump_analyze` real run is no longer cancelled at 30 s.
- Timeout reason reported to model/UI distinguishes caller/runtime timeout from KD's own bounded timeout where the existing typed result permits it.
- Windows/Linux CI remains green.

## PRE-2 — Planned-step semantic integrity and evidence-driven follow-up

**Priority:** BLOCKER for stable V1.3  
**Implementation:** Opus High  
**Review:** Opus High  
**ADR gate:** amend ADR-0046/0047 or add a focused ADR before implementation.

### Problem A — ExpectedTool equality is not semantic completion

A plan can legitimately contain several consecutive uses of `system.events`. In the real Qwen run, a call to the same tool but with arguments for a different diagnostic question consumed the current step. Runtime therefore lost alignment between plan intent and cursor while reporting no replan.

### Requirements

- Preserve ADR-0046 exact tool visibility and ADR-0047 bounded validation correction.
- Do not pretend that tool-name equality alone proves the semantic objective of the current step was satisfied.
- The model-facing execution request must make the current plan step unambiguous: index/revision, concise objective, exact expected tool, and any accepted typed execution constraint introduced by the ADR.
- Choose one generic mechanism for distinguishing repeated uses of the same tool. It must not embed package-specific argument knowledge in Runtime.
- If the emitted call cannot be proven to belong to the current planned step, it must not silently advance the cursor. It should either receive one bounded correction path or cause a typed replan, according to the accepted ADR.
- Resume must derive exactly the same cursor/semantic state from persisted data as the live loop.

Possible designs to evaluate, not pre-decide:
- a bounded typed expected-call/argument constraint captured in the plan;
- a stable step-intent token echoed by the execution response;
- another generic contract that proves the call belongs to the current planned step without exposing chain-of-thought.

### Problem B — useful follow-ups discovered only after evidence

The planner saw `system.dump_analyze` in the available catalog but did not schedule it. If a discovery step later exposes a concrete dump path, bOps currently has no generic bounded mechanism to represent "run this follow-up only if the artifact is discovered" or to trigger a useful replan solely because new evidence changed the best next action.

### Requirements

- Design a bounded generic solution; Runtime must not know `system.dump_analyze`, dump paths, WHEA, etc.
- Prefer an explicit conditional/follow-up plan concept or a bounded evidence-triggered replan protocol over re-planning after every read step.
- No unbounded "reflect after every observation" loop.
- Conditional steps must be visible/persisted so PRE-4 can render them.
- A skipped condition is distinct from Completed and from Failed.
- Real regression: a discovery step exposing an artifact can lead to the appropriate already-authorized follow-up tool without requiring the original user to name that tool.

### Acceptance

- Regression with four consecutive plan steps using the same tool but different intents cannot silently consume the wrong step.
- Live and resume cursor/state agree.
- First ADR-0047 validation failure still retries the same exact planned step once.
- Newly discovered evidence can cause a bounded conditional follow-up/replan without a package name in Runtime.
- Existing first-call-wins and `UnexecutedToolCalls` behaviour remains intentional and tested.

## PRE-3 — EvidenceRead control-plane and terminal-response hardening

**Priority:** BLOCKER for stable V1.3  
**Implementation:** Opus High  
**Review:** Opus High  
**ADR gate:** amend ADR-0042 / HARDEN-8 evidence retrieval semantics before implementation.

### Problem

`EvidenceRead/v1` is currently a text protocol. Qwen successfully emitted the first exact JSON request but later emitted an XML/native-tool-like `runtime_evidence_read` fragment. Runtime treated that text as a final-answer candidate. When the disclosure re-ask timed out, the protocol artifact became the persisted final answer and the task ended `Completed`.

### Requirements

- Make evidence retrieval a typed runtime/control-plane operation that is harder for native-tool models to confuse with prose. Evaluate a native internal function/control call that is distinct from operational package tools.
- If an internal native function is exposed alongside ADR-0046's expected operational tool, explicitly amend the one-tool visibility invariant: internal runtime control functions are not operational tools and must not expand package authority.
- Keep evidence reads task-local, bounded by source/offset/length and audit them as today.
- Preserve compatibility with existing persisted EvidenceRead rows where necessary.
- Detect protocol/control artifacts (`EvidenceRead/v1`, malformed evidence-read shapes, internal tool-call markup) as not valid final user answers.
- If correction/re-ask cannot produce a valid final answer, end in an appropriate failed/model-unavailable state rather than `Completed` with internal protocol text.
- A disclosure re-ask failure may preserve a valid original prose answer, but never an invalid control/protocol artifact.
- Add Qwen-shaped regression fixtures for exact JSON, XML-style `runtime_evidence_read`, malformed tool call and timeout.

### Acceptance

- Multiple sequential evidence reads work without asking the model to manually imitate a fragile JSON text protocol.
- Malformed evidence-read intent never becomes final output.
- Two timed-out disclosure re-asks cannot produce `Completed` with `<tool_call>...` or an EvidenceRead control object.
- Existing ADR-0042 limitation disclosure and HARDEN-8 prompt bounds remain intact.

## PRE-4 — Read-only execution plan visibility in the Dashboard

**Priority:** MUST before stable V1.3  
**Implementation:** Sonnet High  
**Review:** Sonnet/Opus Medium

### Product behaviour

Add a compact read-only "Execution plan" panel to the task view, preferably on the right at desktop widths and naturally stacked on narrow screens.

Show:
- active plan revision;
- each step's concise objective and `ExpectedTool`;
- Pending / Running / Completed / Failed / Skipped / Superseded;
- the current step distinctly;
- ADR-0047 "argument validation failed — correcting" as a state of the same step, not a replan;
- replan boundaries: `revision N -> N+1`, with the already executed prefix preserved and the replaced suffix visibly superseded;
- conditional steps introduced by PRE-2 and whether they were skipped or activated;
- no hidden reasoning, chain-of-thought, prompt bodies, tool arguments/output or secrets.

### Backend

- Project the persisted plan revisions + persisted steps; do not create a second execution state machine.
- Prefer an additive field on the existing task view/stream or a focused read endpoint.
- Derive state deterministically from persisted task data so refresh/reconnect/resume show the same history.
- Current execution must update through the existing watch/poll/stream mechanism.
- Replan history must survive restart.

### Acceptance

- A running task visibly advances step by step.
- One ADR-0047 correction stays on the same step.
- A replan visibly preserves completed history and supersedes only the replaced suffix.
- Refresh/reconnect reproduces exactly the same plan panel.
- EN/IT, 375/768/1024/1440 px, accessible state labels; no horizontal overflow.
- No editable plan controls in V1.3.

## PRE-5 — Evidence-grounded final synthesis / contradiction guard

**Priority:** MUST before stable V1.3  
**Implementation:** Opus High  
**Review:** Opus High

A prior real Qwen diagnostic collected WHEA Event 19 evidence and later contradicted that evidence in the final prose. Do not attempt to "fix hallucinations" with package-specific rules.

Design a small generic evidence ledger/fact projection from persisted typed results:
- distinguish `Observed`, `Inferred`, `Unknown/Unavailable`;
- make high-salience observed facts and source limitations available to final synthesis within existing prompt bounds;
- reject or correct direct contradictions against deterministic typed facts when a bounded generic comparison is possible;
- never claim that absence in partial/unavailable evidence proves zero;
- do not expose raw unbounded tool output or create a general knowledge graph.

Acceptance includes a deterministic regression reproducing the WHEA-style contradiction and proving the final answer cannot state the opposite of an exact persisted fact without an explicit uncertainty qualifier.
