## Objective

A fresh installation deliberately defaults to `OpenRouter` / `openrouter/free` as a zero-cost
bootstrap for getting started, evaluation and non-critical exploration. That router mode is explicitly
non-deterministic; important troubleshooting, reproducible analysis and especially remediation should
use a specifically selected model. The approved-in-principle, explicitly configured ordered fallback
list recovers from transient/capacity failures without embedding vendor semantics in `bOps.Runtime`.
Settings-driven provider, model and profile changes become effective for newly admitted executions
without restarting the API, while each running or resumable ordinary task/delegated run remains pinned
to one coherent non-secret configuration. Credential rotation/removal is intentionally late-bound and
affects the next attempt, including in an already-running execution.

## Architecture gate (Block A — 2026-10-06)

[ADR-0045](../../docs/architecture/adr/0045-execution-pinned-provider-configuration-and-fallback-chain.md)
is **Proposed** and D-042 is recorded as **Proposed**. It defines persisted/effective/pinned state,
atomic publication, environment shadowing, top-level task/delegation pinning, deterministic restart
resume through a durable non-secret snapshot plus per-attempt current-credential resolution, the
host-level fallback chain, sticky execution semantics, audit additions and future tests. ADR-0029 has
a forward reference; its current restart-required behavior remains authoritative until ADR-0045 is
accepted and implemented.

Operator decisions incorporated:

1. shipped bootstrap default: `OpenRouter` / `openrouter/free`;
2. ordered host-level fallback chain: approved in principle;
3. credential pinning correction: pin no secret or historical credential; resolve the current
   provider credential on every attempt.

No design choice remains open. Independent architecture review, followed by final operator acceptance
of the Proposed ADR, is the only remaining Block A gate.

Block A contains architecture/docs only. No H13 production code, configuration default, UI or runtime
behavior has changed.

## Confirmed defects addressed

**C-20**: `src/core/bOps.Api/appsettings.json` ships `"Model": "openrouter/free"`. In task 88f97dda,
12 successful calls were served by 7 different actual models (`ling-3.0-flash-sante`,
`nex-n2.5-pro`, `ling-3.0-flash-fin`, `lfm-2.5-2.6b`, `nex-n2.5-mini`, `dots-3-note-preview`, …), the
free tier returned `429 free-models-per-min` seven times before the failing upstream was chosen, and one
router-selected upstream enforced a stricter tool contract (C-01).

The operator deliberately retains this free-router mode as the bootstrap default. C-20 is mitigated
through explicit disclosure, actual-model visibility, easy live provider/model selection and a clear
recommendation to select a specific model for serious work—not by claiming the bootstrap is
deterministic.

## Scope

1. Live Settings: provider/model/profile mutations publish atomically for new executions; the durable
   top-level task or delegated run pins one complete non-secret configuration across calls, approval
   waits and resume/restart. Credential mutations atomically update the current secret authority and
   are resolved per attempt, so rotation/removal affects active executions without changing their
   provider/model pin. Persisted, effective and pinned state are distinct and visible without
   exposing plaintext secrets.
2. Default configuration: retain `OpenRouter` / `openrouter/free` as the zero-cost bootstrap and
   document it as intentionally non-deterministic. Recommend a specifically selected model for
   important troubleshooting, reproducible analysis and remediation.
3. Settings UI: show effective source/shadowing accurately; when a router model is configured, show a clear notice ("the actual model may change on
   every call; not recommended for troubleshooting sessions"); the step model-info already shows
   `requested → actual`.
4. Getting Started/operator documentation: an OpenRouter API key is required; show how to configure
   it through Settings; disclose per-call actual-model variation; recommend a specific model for
   serious work; explain where the actual model appears in model-call/audit information; document
   free-tier rate-limit implications.
5. **Approved in principle** (implementation only after ADR acceptance): host-level ordered **fallback chain**
   (`ModelProvider:Fallbacks: [{Provider, Model}]`) implemented as an execution-scoped `IChatModel` in
   `bOps.Hosting`/`bOps.Api`, switching only on HARDEN-2 kinds `Transient`, `RateLimited`, `Timeout`,
   `Unreachable` after same-provider retries are exhausted; never on `Authentication`, `InvalidRequest`,
   `MalformedResponse`, `QuotaExceeded`, `ContextOverflow` or `Unknown`; each attempt audited with the
   pinned primary, actual candidate/model and fallback ordinal.
6. E2E-4 fallback variant plus the no-restart A→B live-settings scenario.

## Out of scope

- Removing router support.
- Any provider-name or router logic in `bOps.Runtime`.
- Cost accounting beyond what providers report.
- Wiring `ProviderProfile.ExtraParameters` into `ChatModelOptions` or a first-party provider. It
  remains persisted and returned but unconsumed; it is not a HARDEN-13 acceptance criterion.

## Architecture constraints

The Runtime sees one `IChatModel`; composition happens in the host. All calls audited. No fallback on
permanent/unknown errors. The execution scope is one ordinary task or one entire delegated run, not a
call, role or execution attempt. No network call is required merely to save a syntactically valid
configuration.

## Public contract impact

Bootstrap default documentation/contract clarification; additive fallback configuration; additive
safe non-secret pinned configuration on `TaskState`/`DelegationRun`; additive non-redundant
primary/fallback/generation metadata on model-call records and audit. Existing `Provider`,
`RequestedModel`/`Model` and `ActualModel` retain candidate/actual semantics. Any narrow model-routing
signal must remain provider-neutral and preserve one-attempt audit.

## Security implications

Fallback must not route to a provider the administrator did not configure; secrets per provider stay in
the existing secret/vault mechanism. Atomic publication closes non-secret provider/profile TOCTOU;
durable pins contain no credential value, version, hash or correlation id. The current credential is
resolved only for the pinned candidate at each attempt, so rotation can revoke old credentials
immediately without changing model/provider selection.

## Acceptance criteria

- [ ] Fresh configuration uses `OpenRouter` / `openrouter/free`, requires an OpenRouter API key and
      never presents the router as deterministic.
- [ ] Settings changes provider/model/profile for the next execution without API restart; an in-flight
      ordinary task or delegated run retains its pinned non-secret configuration.
- [ ] Settings key rotation/removal requires no restart and affects the next model attempt, including
      in an in-flight execution, without retaining the old key.
- [ ] Environment-shadowed persisted values are reported as shadowed, never as effective.
- [ ] Settings shows the router notice in English and Italian.
- [ ] Getting Started explains key setup, router variability, actual-model visibility and the
      specific-model recommendation for serious work.
- [ ] A scripted 429 storm on the primary switches to the configured fallback after the retry
      budget, every attempt audited; 401/400 never trigger fallback.

## Required tests

Configuration tests; live provider/model switch; in-flight key rotation uses the new key while keeping
the pinned provider/model; key removal fails the next attempt explicitly; no authentication/missing-key
fallback; no secret persistence/audit; environment-shadow reporting; atomic non-secret snapshot race;
task/delegation pinning and restart resume with current credentials; Settings UI router notice;
bootstrap/default documentation; fallback-chain tests with fake providers; E2E-4 fallback variant and
live-settings A→B E2E. Full matrix is ADR-0045 §16.

## Required platform evidence

Deterministic tests on CI; optional opt-in live smoke with the new default (non-gating).
