## Objective

A fresh installation defaults to a deterministic, tool-capable model configuration; OpenRouter router
mode stays **supported** but is no longer the **recommended default**; optionally, an explicitly
configured, ordered fallback list recovers from transient/capacity failures without embedding vendor
semantics in `bOps.Runtime`. Settings-driven provider, model, profile and credential changes become
effective for newly admitted executions without restarting the API, while each running or resumable
ordinary task/delegated run remains pinned to one coherent configuration.

## Architecture gate (Block A — 2026-10-06)

[ADR-0045](../../docs/architecture/adr/0045-execution-pinned-provider-configuration-and-fallback-chain.md)
is **Proposed** and D-042 is recorded as **Proposed**. It defines persisted/effective/pinned state,
atomic publication, environment shadowing, top-level task/delegation pinning, deterministic restart
resume through provider-bound encrypted credential leases, the host-level fallback chain, sticky
execution semantics, audit additions and future tests. ADR-0029 has a forward reference; its current
restart-required behavior remains authoritative until ADR-0045 is accepted and implemented.

Operator decisions still required:

1. accept/reject ADR-0045, including ordered fallback support and the credential-lease resume rule;
2. select the fixed shipped default (ADR recommendation: OpenAI / `gpt-4.1-2025-04-14`).

Block A contains architecture/docs only. No H13 production code, configuration default, UI or runtime
behavior has changed.

## Scope

1. Live Settings: provider/model/profile/credential mutations publish atomically for new executions;
   the durable top-level task or delegated run pins one complete configuration across calls, approval
   waits and resume/restart. Persisted, effective and pinned state are distinct and visible without
   exposing plaintext secrets.
2. Default configuration: a fixed, tool-capable model for the default provider (choose with the
   operator; document the choice); `openrouter/free` documented as exploration-only, non-deterministic.
3. Settings UI: show effective source/shadowing accurately; when a router model is configured, show a clear notice ("the actual model may change on
   every call; not recommended for troubleshooting sessions"); the step model-info already shows
   `requested → actual`.
4. Documentation: supported vs recommended provider/model configurations; rate-limit implications of
   free tiers.
5. **Optional** (only if the operator approves the ADR): host-level ordered **fallback chain**
   (`ModelProvider:Fallbacks: [{Provider, Model}]`) implemented as an execution-scoped `IChatModel` in
   `bOps.Hosting`/`bOps.Api`, switching only on HARDEN-2 kinds `Transient`, `RateLimited`, `Timeout`,
   `Unreachable` after same-provider retries are exhausted; never on `Authentication`, `InvalidRequest`,
   `MalformedResponse`, `QuotaExceeded`, `ContextOverflow` or `Unknown`; each attempt audited with the
   pinned primary, actual candidate/model and fallback ordinal.
6. E2E-4 fallback variant plus the no-restart A→B live-settings scenario.

## Out of scope

- Removing router support.
- Any provider-name or router logic in `bOps.Runtime`.
- Cost accounting beyond what providers report.

## Architecture constraints

The Runtime sees one `IChatModel`; composition happens in the host. All calls audited. No fallback on
permanent/unknown errors. The execution scope is one ordinary task or one entire delegated run, not a
call, role or execution attempt. No network call is required merely to save a syntactically valid
configuration.

## Public contract impact

Configuration default change; additive fallback configuration; additive safe pinned configuration on
`TaskState`/`DelegationRun`; additive actual-provider/fallback/generation metadata on model-call records
and audit. Any narrow model-routing signal must remain provider-neutral and preserve one-attempt audit.

## Security implications

Fallback must not route to a provider the administrator did not configure; secrets per provider stay in
the existing secret/vault mechanism. Atomic publication closes provider/profile/key TOCTOU; durable
pins contain only non-secret data plus opaque provider-bound encrypted credential lease ids/versions.

## Dependency gates

HARDEN-2 complete (failure kinds). Canonical order: after HARDEN-12.

## Acceptance criteria

- [ ] Fresh configuration uses a fixed model; router mode still works when configured.
- [ ] Settings changes provider/model/profile/key for the next execution without API restart; an
      in-flight ordinary task or delegated run remains pinned.
- [ ] Environment-shadowed persisted values are reported as shadowed, never as effective.
- [ ] Settings shows the router notice in English and Italian.
- [ ] If built: a scripted 429 storm on the primary switches to the configured fallback after the retry
      budget, every attempt audited; 401/400 never trigger fallback.

## Required tests

Configuration tests; live provider/model/key switch; environment-shadow reporting; atomic snapshot
race; task/delegation pinning and restart resume; Settings UI router notice; fallback-chain tests with
fake providers; E2E-4 fallback variant and live-settings A→B E2E. Full matrix is ADR-0045 §16.

## Required platform evidence

Deterministic tests on CI; optional opt-in live smoke with the new default (non-gating).
