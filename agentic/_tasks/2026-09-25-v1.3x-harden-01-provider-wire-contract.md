## Objective

Every request bOps sends to a model provider is valid under the OpenAI Chat Completions and Anthropic
Messages tool contracts, whatever the tool names, the number of tool calls in a turn, or the quality
of the model's argument JSON. The incident's HTTP 400 must become impossible by construction.

## Confirmed defects addressed

- **C-01** dotted tool names (`fs.size`, `system.crashes`) sent raw; rejected by upstream Poolside via
  `openrouter/free` with *"Function at index 0 has an invalid name … Only a-z, A-Z, 0-9, underscores,
  and dashes are allowed."* (plan §2.2).
- **C-02** the incident 400 happened on the replan call; plan/replan calls offer all 100 tools with
  `tool_choice:auto` and the model called a tool during replanning (plan revision 1, call 1,
  `finish=tool_calls`).
- **C-13** invalid history for multiple tool calls per turn: only `[primaryCall]` is recorded in the
  assistant turn while tool results are added for unexecuted calls.
- **C-14** malformed argument JSON silently becomes `ToolArguments.Empty`.
- Explicit `null` fields on every message (risk H-5).

## Scope

1. **Wire-safe tool-name aliasing** in the provider adapters (`OpenAiCompatibleChatModel`,
   `AnthropicChatModel`):
   - deterministic, injective mapping from canonical name to an alias matching `^[a-zA-Z0-9_-]{1,64}$`
     (e.g. `.` → `_`, with a documented escape for names that already contain the replacement
     sequence); build the map per request and **fail the request build** on any collision or length
     overflow instead of sending an ambiguous alias;
   - map tool-call names in responses back through the same per-request map; an alias not in the map
     is returned as an unknown tool name so the runtime rejects it as `UnknownTool`;
   - history turns (assistant tool calls from earlier steps) are aliased with the same map;
   - policy, audit, `PlanStep`, UI and logs keep the **canonical** dotted name.
2. **Null omission**: `JsonIgnoreCondition.WhenWritingNull` on the OpenAI-compatible request DTOs (and
   the equivalent in the Anthropic adapter if it emits nulls).
3. **Valid multi-call history**: the assistant turn records **every** tool call the model emitted; the
   first is executed; every other call receives a tool-result turn saying it was not executed (current
   text is fine), so each `tool_call_id` is paired with a call in the preceding assistant turn.
   One executed call per step remains the rule. `RebuildHistory` for resume must produce the same
   shape.
4. **Malformed argument JSON**: the adapter preserves the fact that arguments did not parse (for
   example a marker the runtime can see, or raw text), and the runtime turns it into a validation
   failure observation fed back to the model ("arguments were not valid JSON: …"), recorded and
   audited like any other validation failure. Never execute with `{}` substituted.
5. **Plan and replan calls without native tools**: `CreatePlanAsync`/`ReplanAsync` send no native
   `tools`/`tool_choice`; they include a compact text list of tool names and one-line descriptions in
   the planning instructions so plans can still name `expectedTool`.
6. **Strict fake provider** test double (reused by later packets and HARDEN-14): an `HttpMessageHandler`
   that rejects, with a realistic 400 body, any request with an invalid function name, an unpaired
   `tool_call_id`, a `null` field, or a tool call in a plan request.

## Out of scope

- Failure classification, retry/backoff, timeout containment (HARDEN-2).
- `ToolParameter` constraints and JSON Schema bounds (HARDEN-6).
- Context compaction and token budgets (HARDEN-8).
- Changing the canonical tool naming convention (`lowercase dotted names` stays, `00-bootstrap.md`).
- Executing more than one tool call per step.

## Architecture constraints

- `bOps.Runtime`, `bOps.Policy`, `bOps.Memory`, `bOps.Audit` must not name a provider (CI-checked).
  Aliasing lives in the provider packages; if a shared helper is needed, it is provider-neutral and
  lives in `bOps.Abstractions` only if an ADR allows it — otherwise duplicate the small mapping per
  adapter.
- Nothing crosses the tool boundary except `ToolCallResult`; tool output stays delimited data.
- An alias must never resolve to a tool that was not offered in that request.

## Public contract impact

Internal to provider packages and the runtime, unless the malformed-argument signal requires an
additive Abstractions field (then additive, documented in the ADR note).

## Security implications

- Aliasing is a new mapping on the path from model output to tool execution: an unknown or colliding
  alias must fail closed (unknown tool), never fall back to fuzzy matching.
- Audit and policy must continue to see the canonical name; add a test that policy evaluation receives
  the canonical name for an aliased call.
- Malformed arguments are never "repaired".

## Dependency gates

None before it. HARDEN-2 and HARDEN-6 depend on this packet. Do not start HARDEN-2 in the same
session.

## Acceptance criteria

- [ ] No request built by either adapter contains a function name outside `^[a-zA-Z0-9_-]{1,64}$`.
- [ ] Responses with aliased names execute the canonical tool; an unknown alias yields `UnknownTool`.
- [ ] No `null`-valued field is serialized in OpenAI-compatible requests.
- [ ] A turn with 3 tool calls produces a history the strict fake provider accepts on the next call,
      both live and after `RebuildHistory`.
- [ ] Malformed argument JSON produces an audited validation-failure step and a model-visible
      observation; the tool is not executed.
- [ ] Plan/replan requests contain no `tools` and no `tool_choice`.
- [ ] The incident request shape (100 tools including `fs.size`, replan messages) replays against the
      strict fake provider without error (E2E-14).

## Required tests

- Adapter golden-request tests (OpenAI-compatible, Anthropic) validated by the strict fake provider.
- Round trip: canonical → alias → response → canonical for every registered tool name; collision test.
- Runtime tests: multi-call turn history; `RebuildHistory` equivalence; malformed arguments → validation
  failure; plan/replan requests without tools.
- Policy receives the canonical name.
- Architecture test (existing) still passes: no provider names in the core.

## Required platform evidence

- Deterministic tests on Windows and Linux CI.
- Opt-in live smoke (`Category=LiveModel`, non-gating) with one provider per adapter using a tool named
  `a.b` to confirm or refute H-4; record the result in the completion report.
