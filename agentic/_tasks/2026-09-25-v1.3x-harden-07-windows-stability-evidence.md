## Objective

A competent-operator question such as "why has this PC been freezing for months?" is answerable from
typed, bounded, read-only evidence: crashes and hangs are classified with their real meaning,
aggregated instead of flooding the context, dated honestly, and complemented by a typed stability
capability covering unexpected shutdowns, bugchecks, WHEA hardware errors, display driver resets and
storage-controller resets — with explicit coverage metadata telling the agent how much history exists.

## Confirmed defects addressed

- **C-16** WER normalization: on the operator workstation WER 1001 data is named (`Bucket`,
  `BucketType`, `EventName`, `Response`, `CabId`, `P1`…`P10`, `AttachedFiles`), but
  `WindowsCrashEventNormalizer` reads `EventType` (never present) and uses `P1` as "summary". The 100
  rows returned in the incident were 76×`193`, 6×`1e`, 6×`7f`, 3×`101`, 3×`1a1`, 3×`3b`, 3×`50`
  (LiveKernelEvent and BlueScreen codes, plan §2.3), all `process=null`, `kind=wer`, all timestamped
  within 6 s of WER's re-processing burst. For 1000 the normalizer drops `ModuleName` and
  `ExceptionCode`; its unnamed-layout fallback reads PID from index 6 (ExceptionCode) instead of 8.
  Report.wer files above 32 KB are skipped. Two sources share the name `windows.wer.reportarchive`.
  Dump paths present in `AttachedFiles` are ignored.
- **F-10** gap: the workstation holds 16 Kernel-Power 41, ≥ 200 WHEA-Logger and 5 System BugCheck events
  since August (plan §2.4) that no typed tool surfaces; `system.events` can find them only if the model
  knows provider/event-id tuples.
- **F-22 (coverage part)**: System log covers from 2026-07-31, Application from 2026-09-02; no tool
  reports available history, and `system.crashes`/`system.events` cap requests at 7 days.

## Source finding IDs

F-08, F-10, F-22 (coverage). Hypothesis H-7.

## Scope

1. **WER 1001 normalization**: kind from `EventName` (`BlueScreen` → `kernel-bugcheck`,
   `LiveKernelEvent` → `kernel-live-dump`, `APPCRASH`/`BEX`/`CLR20R3` → `application-crash`,
   `AppHangB1`/`APPHANG` → `application-hang`, otherwise `wer` with the event name kept); typed
   `bugcheckCode` / `liveDumpCode` from `P1` when the event name says so; `bucket`; application/module
   from the documented P-fields for application events; dump **reference** from `AttachedFiles`
   (path string only, never opened); unnamed-index fallback for older layouts.
2. **Application Error 1000 normalization**: `AppName`, `ModuleName`, `ExceptionCode`, `ProcessId`
   (hex), `IntegratorReportId`; unnamed fallback indices 0/3/6/8/12.
3. **Honest time**: `timestampKind` = `occurred` (Report.wer `EventTime`, minidump name/time,
   1000 event time) vs `reported` (1001 processing time). Never present `reported` as occurrence.
4. **Correlation and dedup** across 1000, 1001 and Report.wer by report id where available.
5. **Aggregate mode (default model-facing output)**: groups by kind + code + application/module with
   `count`, `firstSeen`, `lastSeen`, `timestampKind`; raw rows available with an explicit parameter and
   the existing limits.
6. **Report.wer**: parse only needed keys within a larger bounded budget (e.g. streaming key scan up to
   a documented cap) instead of skipping files over 32 KB; distinct source names per root
   (`ProgramData` vs `LocalAppData`).
7. **New read-only `system.stability`** (Windows implementation; Linux returns journald-based kernel
   panic/oops/MCE/OOM evidence where available, else `NotApplicable`): categories
   - unexpected shutdown: Kernel-Power 41, EventLog 6008 (+ 6005/6006 for boot/shutdown context);
   - bugcheck: `Microsoft-Windows-WER-SystemErrorReporting` 1001 (System);
   - hardware errors: WHEA-Logger (e.g. 1, 17, 18, 19, 47) with corrected vs fatal;
   - display driver resets: Display 4101, LiveKernelEvent 117/141/193/1A1 from WER;
   - storage/controller resets: disk 7/11/51/153, `stornvme`/`storahci` 129;
   - minidump inventory: file names, times, sizes only (elevation-gated → `partial`).
   Output aggregated by category and time bucket, bounded scans, plus coverage.
8. **Coverage metadata** on `system.crashes`, `system.events` and `system.stability`:
   `requestedFrom`, `oldestAvailable` per log, `logMaximumBytes`, `coverage` (`complete` | `partial`) —
   so "requested period ≠ evidence available" is explicit.
9. **Longer horizons in aggregate mode only**: up to 180 days under the existing scan ceilings; raw mode
   stays at 7 days (`sinceMinutes`/`windowMinutes` ≤ 10080).
10. `ToolCallResult.Completeness` set on all three tools (HARDEN-6).

## Out of scope

- Opening, parsing or uploading dump files.
- A generic Event Log query language, shell, or arbitrary provider/event-id tool.
- The evidence-reasoning prompt (HARDEN-9).

## Architecture constraints

Read-only (`RiskLevel.Read`); bounded reads with timeouts and record/byte ceilings; typed output; unknown
stays null; no raw XML to the model; the core names no Windows provider (all tuples live in the package).

## ADR prerequisite

**ADR-0032 amendment** (aggregate mode, longer horizons, coverage metadata) and a **new ADR for
`system.stability`** (typed categories, bounds, no raw query language). Both accepted before
implementation. The WER/1000 field-mapping fix itself needs no ADR.

**Architecture prerequisites accepted; implementation not started.** Accepted 2026-10-02:
[ADR-0032 HARDEN-7 amendment](../../docs/architecture/adr/0032-bounded-cross-platform-system-events.md#harden-7-amendment--accepted-2026-10-02)
and [ADR-0041](../../docs/architecture/adr/0041-typed-cross-platform-stability-evidence.md) (decision D-037). Where they
are more specific than this packet, they govern the implementation: aggregate-only horizons are the separate
`windowDays`/`sinceDays` arguments (raw stays bounded by the unchanged `windowMinutes`/`sinceMinutes` ≤ 10080);
coverage values are `complete`, `partial` or `unknown`; the dump reference is carried by the existing `dumpPath` field
(no `dumpReference` field); `system.crashes` and `system.events` move to `schemaVersion` 2 and `system.stability`
starts at 1. Independent architecture review of these ADRs precedes implementation.

## Public contract impact

Additive fields on `system.crashes` rows and a `schemaVersion` bump; new tool `system.stability`;
additive coverage objects. See plan §13.

## Security implications

- Paths to dumps are exposed as references only; no dump content.
- Elevation-gated sources degrade to `partial`, never escalate.
- Bounded scans prevent Event Log exhaustion.

## Dependency gates

HARDEN-6 complete (completeness semantics). HARDEN-9 depends on this packet.

## Acceptance criteria

- [ ] Golden XML tests for named and unnamed 1001 and 1000 layouts produce the documented kinds and
      fields; `EventName=BlueScreen, P1=50` → `kernel-bugcheck`, `bugcheckCode=0x50`.
- [ ] Aggregated output for the incident-like dataset reports counts per code instead of 100
      duplicate rows.
- [ ] 1001 processing-time rows are labelled `reported`; occurrence times come from Report.wer or
      minidump names when available.
- [ ] On the operator workstation (or equivalent), `system.stability` reports unexpected shutdowns,
      WHEA events, bugchecks and display resets with coverage dates matching the log's oldest record.
- [ ] Requests beyond available history report `coverage=partial` with `oldestAvailable`.
- [ ] Raw mode still rejects windows above 10080 minutes (via HARDEN-6 constraints).
