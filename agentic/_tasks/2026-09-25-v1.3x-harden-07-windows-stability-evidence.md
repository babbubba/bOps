## Objective

A competent-operator question such as "why has this PC been freezing for months?" is answerable from
typed, bounded, read-only evidence: crashes and hangs are classified with their real meaning,
aggregated instead of flooding the context, dated honestly, and complemented by a typed stability
capability covering unexpected shutdowns, bugchecks, WHEA hardware errors, display driver faults and
storage-controller resets — with explicit coverage metadata telling the agent how much history exists.

## Confirmed defects addressed

- **C-16** WER normalization: on the operator workstation WER 1001 data is named (`Bucket`,
  `BucketType`, `EventName`, `Response`, `CabId`, `P1`…`P10`, `AttachedFiles`), but
  `WindowsCrashEventNormalizer` reads `EventType` (never present) and uses `P1` as "summary". The 100
  rows returned in the incident were 76×`193`, 6×`1e`, 6×`7f`, 3×`101`, 3×`1a1`, 3×`3b`, 3×`50`
  (LiveKernelEvent and BlueScreen codes, plan §2.3), all `process=null`, `kind=wer`, all timestamped
  within 6 s of WER's re-processing burst. For 1000 the normalizer drops `ModuleName` and
  `ExceptionCode`; its unnamed-layout fallback reads PID from index 6 (ExceptionCode) instead of 8.
  Report.wer files above 32 KB are skipped. Two sources share the name `windows.wer.reportarchive`.
  Dump paths present in `AttachedFiles` are ignored.
- **F-10** gap: the workstation holds 16 Kernel-Power 41, ≥ 200 WHEA-Logger and 5 System BugCheck events
  since August (plan §2.4) that no typed tool surfaces; `system.events` can find them only if the model
  knows provider/event-id tuples.
- **F-22 (coverage part)**: System log covers from 2026-07-31, Application from 2026-09-02; no tool
  reports available history, and `system.crashes`/`system.events` cap requests at 7 days.

## Scope

1. **WER 1001 normalization**: kind from `EventName` (`BlueScreen` → `kernel-bugcheck`,
   `LiveKernelEvent` → `kernel-live-dump`, `APPCRASH`/`BEX`/`CLR20R3` → `application-crash`,
   `AppHangB1`/`APPHANG` → `application-hang`, otherwise `wer` with the event name kept); typed
   `bugcheckCode` / `liveDumpCode` from `P1` when the event name says so; `bucket`; application/module
   from the documented P-fields for application events; dump **reference** from `AttachedFiles`
   (path string only, never opened); unnamed-index fallback for older layouts.
2. **Application Error 1000 normalization**: `AppName`, `ModuleName`, `ExceptionCode`, `ProcessId`
   (hex), `IntegratorReportId`; unnamed fallback indices 0/3/6/8/12.
3. **Honest time**: `timestampKind` = `occurred` (Report.wer `EventTime`, minidump name/time,
   1000 event time) vs `reported` (1001 processing time). Never present `reported` as occurrence.
   *Corrected by architecture override 3 below: the minidump file time is `reported` and the file-name
   date is descriptive metadata, not an occurrence time.*
4. **Correlation and dedup** across 1000, 1001 and Report.wer by report id where available.
5. **Aggregate mode (default model-facing output)**: groups by kind + code + application/module with
   `count`, `firstSeen`, `lastSeen`, `timestampKind`; raw rows available with an explicit parameter and
   the existing limits. *Made precise by architecture overrides 4 and 5 below: this default applies to
   `system.crashes`; `system.events` keeps `raw` as its default and offers explicit `mode: aggregate`.*
6. **Report.wer**: parse only needed keys within a larger bounded budget (e.g. streaming key scan up to
   a documented cap) instead of skipping files over 32 KB; distinct source names per root
   (`ProgramData` vs `LocalAppData`).
7. **New read-only `system.stability`** (Windows implementation; Linux returns journald-based kernel
   panic/oops/MCE/OOM evidence where available, else `NotApplicable`): categories
   - unexpected shutdown: Kernel-Power 41, EventLog 6008 (+ 6005/6006 for boot/shutdown context);
   - bugcheck: `Microsoft-Windows-WER-SystemErrorReporting` 1001 (System);
   - hardware errors: WHEA-Logger (e.g. 1, 17, 18, 19, 47) with corrected vs fatal;
   - display driver resets: Display 4101, LiveKernelEvent 117/141/193/1A1 from WER;
     *corrected by architecture overrides 1 and 2 below: category `displayFault` (4101, 117, 141, 193);
     `1A1` is not display evidence;*
   - storage/controller resets: disk 7/11/51/153, `stornvme`/`storahci` 129;
   - minidump inventory: file names, times, sizes only (elevation-gated → `partial`).
   Output aggregated by category and time bucket, bounded scans, plus coverage.
8. **Coverage metadata** on `system.crashes`, `system.events` and `system.stability`:
   `requestedFrom`, `oldestAvailable` per log, `logMaximumBytes`, `coverage` (`complete` | `partial`) —
   so "requested period ≠ evidence available" is explicit.
9. **Longer horizons in aggregate mode only**: up to 180 days under the existing scan ceilings; raw mode
   stays at 7 days (`sinceMinutes`/`windowMinutes` ≤ 10080).
10. `ToolCallResult.Completeness` set on all three tools (HARDEN-6).

### Architecture overrides

Where the ADRs are more specific than, or correct, this packet, they govern the implementation. Corrections to the
packet's original text are marked as such.

1. **Correction — `displayReset` becomes `displayFault`.** The `system.stability` category is `displayFault`: Display
   4101 and LiveKernelEvent `0x117`, `0x141` and `0x193`. It is graphics-stack fault evidence, not proof of a reset
   (`0x193` is a display-kernel live dump) (ADR-0041 §3.1).
2. **Correction — `0x1a1` is not display evidence.** LiveKernelEvent `0x1a1` (WIN32K_CALLOUT_WATCHDOG_LIVEDUMP, a hang
   signature, plan §2.3) is removed from the display category; `system.crashes` lists it as `kernel-live-dump`, and no
   separate category is introduced for it (ADR-0041 §3.1, §10).
3. **Correction — minidump file-name date is not an occurrence time.** A minidump's file last-write time is
   `reported`; the date in its name is the descriptive `fileNameLocalDate` (local, day-only, never converted to UTC,
   never used for windows, buckets or first/last seen). Occurrence times come only from evidence that proves the event
   time, such as Report.wer `EventTime` and the Application Error 1000 record time (ADR-0041 §6).
4. **`system.crashes` defaults to `mode: aggregate`** (scope 5); `mode: raw` returns per-crash rows. This is an
   intentional default behavioural change, versioned by schema 2.
5. **`system.events` keeps `mode: raw` as its default**; aggregation is the explicit `mode: aggregate`, and the long
   horizon `windowDays` (1–180) is valid only with it. The raw window stays `windowMinutes` ≤ 10080 (likewise
   `sinceDays` / `sinceMinutes` ≤ 10080 for `system.crashes`). Cross-field rules are checked in a fixed order:
   minute and day argument together; day argument in raw mode; then the remaining validation (ADR-0032 amendment §1–§2).
6. **Schema versions.** `system.events` and `system.crashes` move to `schemaVersion` 2; `system.stability` starts at 1.
   Coverage values are `complete`, `partial` or `unknown`; the dump reference is carried by the existing `dumpPath`
   field (no `dumpReference` field).
7. **One aggregation contract.** `mode` is the only aggregation switch of `system.events`; HARDEN-9 uses it and must
   not introduce a second `aggregate` parameter.
8. **No unknown zeros, no hints.** A `system.stability` category or minidump counter whose sources could not be read is
   `null` (a `partial` one is a lower bound); the result carries no `drillDown` or other pre-built hint for another tool
   (ADR-0041 §5).
9. **Evidence-driven correction (operator decision, 2026-10-02, during real-Windows validation).** The Report.wer
   `EventTime` of a `BlueScreen` (`kernel-bugcheck`) report is `reported`, not `occurred`: Windows writes it after the reboot
   (operator workstation: `0x50` 08:45:27Z vs Kernel-Power 41 08:44:37Z; `0x1e` 14:26:56 vs 14:26:35; `0x3b` 20:59:23 vs 20:59:04).
   `LiveKernelEvent` and application Report.wer `EventTime` stay `occurred`; precedence is
   unchanged and no other time is promoted in its place (ADR-0041 §6 and its correction section, ADR-0032 amendment §4, D-037).
   This also corrects override 3 and the acceptance criterion on occurrence times for that one kind.

## Independent review implementation notes

Non-blocking findings of the independent architecture review. They are not architecture blockers; the implementation
and its review verify each one.

- **R6** — the journald coverage probe uses the same scope as the source it backs (for example `_TRANSPORT=kernel` for
  `system.stability`), so a store's `oldestAvailableUtc` is not taken from an unrelated journal stream.
- **R7** — per-call and per-source time budgets stay below the 30-second runner tool timeout (`system.crashes` today
  allows three 10-second Event Log reads plus the Report.wer scan), and one flooded source cannot starve the others.
- **R8** — the minidump inventory has no retention guarantee: a count of 0 describes the files present now, not the
  absence of past dumps; the manifest wording says so.
- **R9** — WHEA and MCE classification stays conservative: no `corrected` class without proof (the Linux "Machine check
  events logged" line), and informational WHEA levels are excluded or explicitly documented.
- **R10** — tests prove the report-GUID relations between Application Error 1000, WER 1001 and Report.wer on recorded
  data, and that `uncorrelatedCount` does not suggest certainty for records that carry a GUID but merged with nothing.
- **R11** — dump references (`dumpPath`) are normalized (`\\?\` prefix, control characters), bounded, and documented
  as possibly containing a user-profile path; the `.dmp`-only rule for `AttachedFiles` is stated.
- **R12** — the raw `system.crashes` envelope and its schema-1 differences (renamed WER sources, `observedItems`
  counting merged records, the byte budget in raw mode) are specified and tested.
