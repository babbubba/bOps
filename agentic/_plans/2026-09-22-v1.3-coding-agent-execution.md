# V1.3 — coding-agent execution strategy

Status: **active planning aid**
Scope: V1.3-G through V1.3-M
Repository: `bOps`
Purpose: reduce coding-agent exploration/reasoning cost without weakening architecture, security or test evidence.

This file is operational guidance for executing the authoritative V1.3 tasks. It does **not** override
`00-project-spec.md`, `01-architecture-rules.md`, `03-security-rules.md`, accepted ADRs or the
functional contracts in the task files. If this guide and an invariant disagree, the invariant wins.

## Why tasks are split into execution packets

The V1.3 functional tasks deliberately describe the complete capability. A coding agent should not
have to redesign that capability on every run. From G onward, each task therefore contains numbered
execution packets. One coding-agent session handles **one packet only**, unless the packet explicitly
says it is a final integration gate.

The packet already decides:
- what part of the contract is in scope;
- which existing files are the primary implementation anchors;
- which files/projects are expected to change;
- platform source/API choices already settled by the task;
- failure/completeness semantics;
- minimum tests and evidence;
- when the agent must stop instead of exploring or redesigning.

## Conservative model ladder

Model names are execution guidance, not part of the product architecture. Use the least expensive
model that can complete the packet correctly.

1. **Luna Low** — mechanical edits, documentation, registration, simple contract/test work.
2. **Luna Medium** — default for implementation packets.
3. **Luna High** — only after a concrete packet-local problem survives two reasoned attempts.
4. **Terra Medium, while available** — escalation for cross-platform/native interop or non-trivial
   debugging where Luna has produced a precise blocker.
5. **Sol Low** — narrow architecture/security review or a precisely isolated blocker.
6. **Sol Medium** — exceptional final escalation only; never the default for a whole V1.3 batch.

For M architecture packets, prefer **Terra Medium while available**; if Terra is unavailable, use
**Sol Low**. Do not jump directly from Luna Medium to Sol Medium.

## Mandatory token/usage discipline

Every coding-agent prompt for a packet must enforce these rules:

- Read the selected task and this execution guide first.
- Read only the packet's listed repository anchors initially.
- Do not perform a broad repository scan unless an anchor is missing or contradicts the task.
- Do not read `agentic/obsolete/`.
- Do not refactor unrelated code.
- Do not implement the next packet.
- Use targeted build/tests while developing.
- Run the full non-live solution suite once at the packet's integration gate, not after every edit.
- Maximum two reasoned fix attempts for the same failure. After that, stop and report:
  file, failing test/error, evidence, current hypothesis and smallest next action.
- Never increase reasoning/model tier autonomously.
- Never turn an unavailable native source into a trustworthy empty result.
- Never weaken a hard bound, policy check, approval requirement or verification contract to make a
  test pass.

## Standard repository-navigation rule

Each packet has a **Read first** list. The agent may additionally read:
- the project file containing a referenced class;
- the directly associated test file/project;
- an ADR explicitly referenced by the selected task or changed contract.

Repository search is allowed only to locate one named symbol/file or to resolve an inconsistency.
A broad "understand the whole repository" pass is out of scope.

## Standard implementation order

Unless a packet says otherwise:

1. validate branch, dependency gate and clean working tree;
2. read packet + listed anchors;
3. add/adjust contract and argument validation;
4. implement platform collection/mutation;
5. add targeted tests;
6. run targeted Release build/tests;
7. self-review only the packet diff for security, completeness and contract drift;
8. at an integration packet, update docs/task evidence and run the full non-live suite;
9. stop.

## Completeness semantics

For V1.3 diagnostics, an empty result is trustworthy only when the source was fully observed.

| Condition | Required representation |
|---|---|
| complete source, zero rows | empty rows + `complete:true` |
| permission/visibility restriction | available evidence + `complete:false` |
| source absent/unsupported | explicit unavailable/partial source + `complete:false` |
| hard row/byte/process/FD ceiling reached | truncated evidence + `complete:false` |
| parser sees unknown native expression/state | preserve bounded native evidence + `complete:false` |
| invalid caller argument | Tool Failure |
| timeout/cancellation | normal runtime/tool failure semantics; never partial data presented as complete |

## Settled V1.3-G/H details

These decisions were confirmed before packetization and coding agents must not reopen them:

1. Cron list/inspect identifiers are opaque deterministic ids. Compute a stable hash from the
   normalized cron source identity and normalized entry identity; expose human-readable source/file/
   user metadata separately. The id is not a mutation token.
2. `identity.users.enabled` is nullable. On Linux, where the permitted sources cannot establish
   account-disable state reliably, return `null` rather than guessing from shell/profile. With
   `includeDisabled=false`, exclude only users positively known disabled; unknown users remain.
3. `service.config.enabled` is nullable and `service.config` also returns
   `enablementState`. Preserve native enablement semantics instead of forcing every systemd state
   into a boolean. The implementation task owns the explicit mapping table.

## Standard validation commands

Use the narrowest project during development, then the solution at the integration gate:

```bash
dotnet build <affected-project-or-projects> -c Release
dotnet test <affected-test-project> -c Release --no-build
dotnet test tests/bOps.Architecture.Tests/bOps.Architecture.Tests.csproj -c Release --no-build
```

At the packet that closes a batch:

```bash
dotnet build bOps.slnx -c Release
dotnet test bOps.slnx -c Release --no-build --filter "Category!=LiveModel"
```

Platform evidence must still come from the real Windows/Linux CI targets required by
`04-testing-rules.md`.

## Required handoff at the end of every packet

Return exactly enough information for the next session:

- packet id and branch/commit;
- files changed;
- targeted tests: passed/skipped/failed;
- full-suite/CI evidence if this packet owns it;
- any platform path not exercised locally;
- unresolved blockers or `none`;
- confirmation: **next packet not started**.

Do not include a new architecture proposal in the handoff unless a repository rule forced the packet
to stop.

## Quality measurement from V1.3-H onward

Every milestone from H onward has a quality manifest. The final integration packet executes
`scripts/Test-MilestoneQuality.ps1`; quality score and efficiency metadata remain separate, and a
platform test skipped locally remains `PENDING`. An autonomous milestone may concatenate packets
with local commits, but the final quality gate remains mandatory.

The quality lifecycle is automated after integration: platform evidence is collected by the CI
matrix, aggregate CI evidence is published separately from local reports, and only a `VERIFIED`
aggregate may produce a deterministic verified-report branch and manual-review PR. The finalizer
never auto-merges and runs only for successful push CI on `main`.
