This plan is the authoritative record of the review. A packet file references it by finding ID
(`C-nn`, `F-nn`, `H-n`) instead of repeating the evidence. When a packet and this plan disagree,
the normative rules in `agentic/` and accepted ADRs win (see `agentic/README.md`, Precedence), then
this plan, then the packet.

The objective is **not** to fix a demo. It is to make bOps reliable for real interactive system
troubleshooting — dashboard, resume, delegations and UI operability — while preserving the product
axiom: *the LLM proposes; the runtime decides and executes; policies authorize; verification
confirms; audit records.* Nothing in this train gives a model shell access, relaxes fail-closed
safety, lets a model bypass typed tool contracts, silently clamps arguments, adds arbitrary
SQL/process execution, makes a mutation automatic or hides incomplete evidence.

## 3. Executive diagnosis

bOps did not fail because of one bug. Several individually correct components fail at their joins.

1. **The HTTP 400 that killed task 88f97dda has an exact, recoverable cause.** bOps sends dotted tool
   names (`fs.size`, `system.crashes`) that violate the OpenAI function-name contract
   (`a-z A-Z 0-9 _ -`). The `openrouter/free` router hit seven `429 free-models-per-min` errors and
   fell back to the upstream provider "Poolside", which enforces the contract and rejected the
   request. The same request succeeds or fails depending on which upstream the router picks. It is a
   **bOps wire-contract defect**, not a provider outage. The 400 occurred during **replanning**.
2. **Resume cannot reliably make progress, and the UI cannot observe it.** The API returns 202 before
   anything is saved as `Running`; the UI watcher reads the old terminal snapshot and stops;
   `MaxStepsReached` resumes with zero steps; zero-plan tasks throw after the 202; token usage resets
   on resume; delegated role tasks can be resumed outside their authority envelope.
3. **A model-call timeout leaves a task `Running` forever with no audit record.** The default
   `HttpClient` 100 s timeout raises an `OperationCanceledException` that every catch on the path
   excludes. Task 88f97dda is in exactly this state: persisted `Running`, no executor, and the UI
   offers neither Cancel nor Resume.
4. **The decisive evidence was collected and then made unreadable.** `system.crashes` returned WER
   rows whose "summary" was the bugcheck or LiveKernelEvent code, with the event name dropped and the
   timestamps being WER re-processing time. The workstation also holds Kernel-Power 41, WHEA-Logger
   and BugCheck evidence that no typed capability surfaces. `storage.health` fails on every Windows
   host because its query selects a property that does not exist.
5. **Delegation cannot be used on a fresh install, and the obvious workaround is unsafe.** Even
   diagnosis-only needs all four role profiles, including a Remediation profile with required
   Skills/Capabilities, so an operator must author mutation grants just to diagnose.
6. **UI:** Italian labels overflow (measured); a refresh loses authentication; error mapping sends
   the operator the wrong way ("API unreachable" for "already running" or "at capacity").

None of this needs shell access, relaxed policy or looser verification. Every proposal is typed,
bounded and audited.

## 5. Confirmed defects

Proven by code reading and/or the forensic evidence of §2. Severity and category live in §7.

### Provider and runtime

- **C-01 — Dotted tool names cause HTTP 400.** Proven by the stored response body (§2.2): *"Function
  at index 0 has an invalid name: "fs.size". Only a-z, A-Z, 0-9, underscores, and dashes are
  allowed."* (upstream Poolside, after 7 × 429). Both the OpenAI-compatible and the Anthropic
  adapters send `manifest.Name` unchanged.
- **C-02 — The incident 400 happened on the replan call, not a step call.** Plan revision 0 had 6
  steps and was exhausted at step 6; `ReplanAsync` received the 400 in 383 ms; `BuildFailed`
  appended synthetic step 7 and the replan's `plans.Add` never ran. Audit records the failure as
  `StepIndex=6`, the task as step 7 (LOW numbering mismatch).
- **C-03 — A provider timeout escapes every handler.** Providers use the default factory
  `HttpClient` (100 s). A timeout raises `TaskCanceledException` (an `OperationCanceledException`).
  `SendAsync` catches only `HttpRequestException`; `CallModelAsync`, `ContinueAsync` and
  `AgentTaskLauncher` all filter out `OperationCanceledException`. Result: no model-call audit event,
  no `ModelCallRecord`, no terminal status, task left `Running`. Tool timeouts, by contrast, are
  handled correctly (`ExecuteWithTimeoutAsync` uses `when (!ct.IsCancellationRequested)`).
- **C-04 — Resume does not persist `Running` before returning 202.** `TryStartAsync` does
  (`AgentTaskLauncher.cs:37-40`); `TryResumeAsync` does not. `Running` is first saved at
  `AgentRunner.cs:407`, after the first complete resumed step; if that step fails, `Running` is never
  saved at all.
- **C-05 — The UI watcher consumes the stale pre-resume snapshot and stops.** `resume()` sets
  `selectedTask=null` and calls `watch()`; the first `GET` returns the old terminal status; `poll()`
  sets `stopped=true`. Deterministic whenever the first resumed step takes longer than one HTTP round
  trip — always true with a model call (32 s in the incident). The SSE endpoint applies the same stop
  rule (`AgentsEndpoints.cs:147`).
- **C-06 — `MaxStepsReached` makes zero progress on resume.** `startStepIndex = steps.Count = 15`,
  loop condition `stepIndex < MaxSteps` is `15 < 15` = false, the task is immediately re-saved as
  `MaxStepsReached`. Task `8747e59a` (15/15) is in the store with Resume offered.
- **C-07 — Zero-plan `Failed` tasks get 202 from resume, then fail in detached execution.**
  `ResumeAsync` throws `InvalidOperationException("…has no recorded plan and cannot be resumed.")`
  inside `Task.Run`; the launcher logs it; no state change, no audit. Five such tasks are in the store.
- **C-08 — The API accepts resume for any status**, including `Completed`; a duplicate resume returns
  503 instead of 409; the 503 has no body.
- **C-09 — `ResumeAsync` resets `totalTokens` to 0.** A resumed task gets a fresh `MaxTotalTokens`
  budget every time, bypassing the lifetime token/cost budget; no audit event records the operator's
  resume decision (no task-lifecycle audit type exists; only delegations have one).
- **C-10 — Synthetic failure steps consume step budget.** Each "Model protocol failure" step takes an
  index; repeated failed resumes shrink the remaining budget. A task that failed after 7 tool steps
  resumes with at most `15 − 8 = 7` steps. `MaxSteps` is effectively a lifetime cap, undocumented.
- **C-11 — Delegated role tasks can be resumed outside their delegation envelope.** Role tasks are
  persisted by the same `AgentRunner` singleton into the same `ITaskStore`
  ([`Program.cs:132-160`](../../src/core/bOps.Api/Program.cs)), listed on the Dashboard, and accepted
  by `POST /api/agents/tasks/{id}/resume`, which calls `ResumeAsync(..., delegation: null)`: full tool
  view, no envelope enforcement, no delegation correlation.
- **C-12 — Orphaned `Running` tasks are indistinguishable from active ones.** Persisted `Running`
  means both "executing now" and "interrupted, resumable". The UI shows neither Cancel (none exists
  in the UI or its API client) nor Resume for `Running`. Task 88f97dda is stuck in this state.
- **C-13 — Multiple tool calls per turn produce an invalid chat history (latent).** The assistant turn
  records only the first call, but tool-result turns are added for the unexecuted calls; their
  `tool_call_id`s do not appear in the preceding assistant turn. Not involved in this incident (every
  step had one call).
- **C-14 — Malformed tool-argument JSON silently becomes empty arguments** (`ParseArguments` returns
  `ToolArguments.Empty` on `JsonException`); a tool with all-optional parameters then runs with
  defaults the model never asked for.
- **C-15 — Provider failure handling is unclassified and too short-lived.** Retry delays 100/200 ms,
  `Retry-After` ignored, 500/401/"context length" unclassified; the actionable provider reason is
  invisible to the operator because `ErrorMessage` is generic and `ResponseJson` is stripped from the
  API view.

### Windows evidence

- **C-16 — WER normalization discards the diagnostic meaning.** Local event XML proves the 1001 layout
  (`EventName`, `P1`…`P10`, `AttachedFiles`); the normalizer's `EventType` lookup never matches, so
  hangs are never classified and BlueScreen/LiveKernelEvent are lost; `P1` becomes an opaque summary;
  the dump path in `AttachedFiles` is ignored; processing time is presented as crash time; for 1000,
  `ModuleName` and `ExceptionCode` are dropped. The incident rows (§2.3) and the local evidence (§2.4)
  show what was lost.
- **C-17 — `storage.health` fails on every Windows host** (§2.5): wrong `Temperature` property on
  `MSFT_PhysicalDisk`.

### UI and configuration

- **C-18 — Italian (and, at narrower widths, English) layout overflow is real and measured** (§2.6).
- **C-19 — Duplicate resume or launcher capacity (a body-less 503) is shown as "Impossibile
  raggiungere l'API di bOps"** — the operator is told the backend is down when it is busy or already
  running the task.
- **C-20 — `openrouter/free` is the shipped default and routed one task across 7 different actual
  models in 12 calls**, with free-tier 429s.
- **C-21 — Browser authentication disappears on full refresh by design**: token and identity live

## 8. Resume state-machine analysis

**Is the stale-status watcher race real? Yes — proven (C-04, C-05).**

1. `POST /resume` loads the `Failed` task; `TryRunDetached` starts; the endpoint returns 202. Nothing
   has been saved.
2. The UI sets `selectedTask=null`, calls `watch()`; the first `GET` returns `status=Failed`;
   `poll()` stops.
3. In the background, the step-8 model call (32 s) and tool run; `SaveAsync(Running)` happens only at
   `AgentRunner.cs:407`, after the first complete resumed step. The Running-list poll (every 3 s) later
   brings the task back into the list — the reported "one extra step, shows Running, does not update".
   If the first resumed step fails, `Running` is never saved.

**Can `MaxStepsReached` make progress after resume? No** — zero steps, deterministically (C-06).
`MaxSteps` is effectively a **lifetime** cap measured in step indices including failure steps.
A task that failed at step 8 with one failure step receives `15 − 9 = 6` steps.

**Which statuses should be resumable.** A task gains an additive **`Attempt`** number, persisted and
incremented atomically on resume. No new `AgentTaskStatus` value.

| Status | Resumable | Behaviour |
|---|---|---|
| Failed — transient (timeout, 429, 5xx, network) | Yes | Normal resume. |
| Failed — configuration (401/403, permanent invalid request) | Yes, with warning | UI shows "fix provider configuration, then resume"; failure kind shown. |
| Failed with 0 plans | Yes | Resume **re-enters planning** as a new attempt instead of throwing. |
| MaxStepsReached | Yes, if lifetime steps < `MaxLifetimeSteps` | Fresh per-attempt step budget, capped by the lifetime total; otherwise not resumable ("start a new task"). |
| BudgetExceeded | Only if tokens used < current `MaxTotalTokens` | Tokens are cumulative and never reset; raising the cap is an explicit administrator configuration act. |
| ReplanLimitReached | Yes | Per-attempt replan budget plus a lifetime replan cap. |
| PolicyBlocked | **No** | Rule C4 dead end: start a new task or change policy. |
| Cancelled | Yes | The operator's own interruption (ADR-0017 intent). |
| Completed | **No** (409) | |
| Running and executing in this host | **No** (409) | Offer **Cancel** instead. |
| Running but not executing (orphaned) | Yes | Shown as "Interrupted" — a **computed view**, not a persisted status. |
| Delegated role task | **Never via the task endpoint** (409) | "Resume the delegation run." |

**Immediate transition.** A compare-and-set in the store saves `Running`, `Attempt+1` and a
`resumedBy` stamp **before** the 202; the 202 body carries the new snapshot so the client observes a
coherent transition. A `TaskLifecycleAuditEvent` (Started / Resumed / Terminal) records actor,
attempt, prior status, terminal reason and a budget snapshot — which also records the budget
decision. A duplicate resume receives 409; a full launcher receives 503 with a body and
`Retry-After`.

**Budgets.**
- **Reset per attempt:** steps (`MaxSteps`), replans (`MaxReplans`), optional duration.
- **Cumulative, never reset:** tokens (and cost when reported), lifetime steps, lifetime replans.
- **Not counted:** synthetic failure steps.

**History.** All steps retained. Step `Index` stays globally monotonic; each step also records its
attempt. On resume the runtime adds one runtime-authored note ("previous attempt ended: kind /
reason") and uses the compaction of HARDEN-8.

**Is a new attempt/generation concept warranted? Yes**, as an additive field, not a new status.

**Caveat (F-25, deferred).** A crash during a non-Read step leaves no intent record in an undelegated
task; a resumed model may propose the same mutation again. Policy, approval and verification are
required again, which mitigates but does not reconcile.

## 9. UI analysis

**Exact cause of the Italian overflow.**
1. The Dashboard left-column header (`flex justify-between`) holds an uppercase `h2`, the "Aggiorna"
   button, and a `<select>` whose intrinsic width equals its longest option ("Limite di
   repianificazioni raggiunto", 222 px). It needs 365 px and has 286 px inside
   `lg:grid-cols-[minmax(0,320px)_1fr]`; the select spills 78–110 px outside the card.
2. `StatusBadge` is an `inline-flex rounded-full` pill without `whitespace-nowrap`, `shrink-0` or
   `max-w`; next to a `truncate` goal, flexbox squeezes it until the label wraps to 3 lines inside
   the pill.
3. The mobile nav row neither wraps nor scrolls (472 px in 375 px).

**Affected components.** Dashboard list header and select; `StatusBadge` in the list
(`dashboard.html:88`) and the detail header (`dashboard.html:115`, whose title/id block lacks
`min-w-0`, so long goals or UUIDs overflow on mobile); Delegations status pill (same pattern); app
nav. Plugins (5 pills, 2 selects), Approvals and Settings share the unguarded pattern and belong to
the same audit.

**Responsive strategy — never shorten strings to hide layout defects.**
- Filter on its own full-width row, or `min-w-0 w-full max-w-[14rem]` with a visible `<label>`;
  header `flex-wrap`.
- Badge `shrink-0 whitespace-nowrap max-w-[12rem] truncate`, with `title` and `aria-label` carrying
  the full label; list row keeps `min-w-0` on the goal.
- Nav `overflow-x-auto` (or `flex-wrap`) below `md`.
- Detail header `min-w-0 break-words`; `break-all` for ids.
- English labels become human text ("Max steps reached", …).
- Playwright checks at 375, 768, 1024 and 1440 px for `en`, `it` and a +40 % pseudo-locale asserting
  `scrollWidth <= clientWidth` for every card.

**Authentication-on-refresh strategy — server-issued browser session.**
- `POST /api/session` with `{apiKey}` in the JSON body (rate-limited, never in a query string);
  returns identity only; sets `__Host-bops_session` — opaque, 256-bit, `HttpOnly`, `Secure`,
  `SameSite=Strict`, `Path=/`. Chrome and Firefox treat `http://localhost` as a secure context,
  which covers the dev proxy.
- Server stores only an HMAC/hash of the session token (a small SQLite table survives API restarts),
  bound to the credential id plus a key-version fingerprint; rotating or removing the key invalidates
  its sessions.
- Idle ≈ 60 min, absolute ≈ 12 h. Default is a browser-session cookie (no `Max-Age`); an explicit
  "keep me signed in on this device" sets `Max-Age` up to the absolute limit.
- `DELETE /api/session` revokes server-side and expires the cookie.
- CSRF: unsafe methods authenticated by cookie also require a custom header (`X-bOps-Request: 1`) and
  a same-origin `Origin`; custom headers force a CORS preflight and no CORS policy exists.
- Bearer stays unchanged for CLI and API clients. The key is never echoed back and never enters
  browser storage or a URL.
- Same-origin cookie auth later allows native `EventSource`, with polling as fallback.

**Live task reconnect / resume strategy.** The watcher becomes a small state machine:
`expectedAttempt` comes from the resume 202 body; a snapshot with a lower attempt is stale and never
ends the watch; the watch ends only on a terminal status with attempt ≥ expected; transient errors
(0/502/503/504/429) show "Reconnecting…" and keep backing off without a permanent stop; polling
resumes on `online` and `visibilitychange`; 401 switches to "Session expired — sign in" and restores
the watch after re-login; 404 is terminal. The UI renders Resume/Cancel from server-computed
`executing`, `resumable` and `resumeBlockedReason`; no policy is duplicated in Angular.

**Error and recovery states (Area 23).** Each state tells the operator what to do: wait (running,
reconnecting), resume (interrupted/recoverable), authenticate (session expired), fix configuration
(provider authentication, delegation profiles), inspect provider (classified provider failure with
sanitized reason), or start a new task (non-resumable terminal). The generic "Qualcosa è andato
storto" is reserved for genuinely unknown errors.

## 10. Delegation analysis

**Why a fresh install cannot use it.** `SafeDefault` ships no role profiles and there is no local
`policy.yaml`. `DeriveRootAttributed` requires a profile for every role of the fixed pipeline,
including Remediation (Skills and Capabilities `Required`) and Verification, even without a
remediation request. ADR-0030 §1 mandates this. The UI accepts the request and reports `Denied` only
afterwards.

**Diagnosis-only requirements.** Only **Discovery and Diagnostic** should be required when
`Remediation == null`. The run ends in `DiagnosisCompleted` before Remediation or Verification could
be derived, so requiring them adds no safety — it subtracts safety by pushing operators to author
mutation grants they do not need. Remediation requests keep requiring all four roles, fail-closed.
**An amendment to ADR-0030 §1/§3 and ADR-0031 is required before implementation.**

**Readiness UX.** `GET /api/delegations/readiness?remediation=false|true`, computed by the runtime's
own reducer against a synthetic request (no policy logic in Angular), returns per role
`ready | missing | malformed | notRequired` with the reducer's reason and dimension. The UI calls it
on load and when "prepare a change" toggles, shows the four-role panel, and blocks Submit with the
reason. CLI: `bops delegate readiness [--remediation]`.

**Safe configuration path.** `bops delegate profiles init --read-only` writes an explicit YAML with
Discovery and Diagnostic profiles listing today's registered **Read** tools by name (expansion at
generation time; no runtime wildcards), finite budgets, targets and environments (`local`), a
deadline, no Skills or Capabilities, and never a Remediation profile. `bops delegate profiles check`
reports drift (new Read tools missing from profiles, unknown names, malformed dimensions); readiness
shows the drift count. Capability input: `GET /api/skills` exposing `CapabilityManifest.InputSchema`
and a schema-driven form (same `ToolParameter` shape plus the HARDEN-6 constraints), raw JSON only as
an advanced fallback.

## 11. Proposed architecture changes (minimal)

1. **Wire-safe tool-name aliasing in provider adapters** — deterministic, injective alias map per
   request, collision-checked, mapped back on response; unknown alias → unknown tool. Null-omitting
   serialization. Valid multi-call history. Plan/replan calls without native tools.
2. **Model-call containment** — timeout not requested by the task is an audited `Timeout` failure;
   launcher backstop persists `Failed` for any exception, never leaving `Running`; additive failure
   classification; bounded same-provider retry honouring `Retry-After` inside a per-call time budget;
   sanitized provider reason.
3. **Task attempt model** — `Attempt`, cumulative token/step counters, terminal reason,
   origin/delegation marker, compare-and-set transition, `TaskLifecycleAuditEvent`;
   `executing`/`resumable` computed at the API edge.
4. **Additive tool contract** — `ToolParameter` constraint init-properties (enforced by the runtime,
   emitted to schema); `ToolCallResult` `FailureKind` and `Completeness` init-properties.
5. **Typed Windows stability evidence** — fixed normalizers, aggregate mode with history-coverage
   metadata, new read-only `system.stability`.
6. **Context economy** — older-step compaction with evidence ids pointing to full persisted
   observations; replan digest; default token budget.
7. **Browser session** — cookie scheme alongside Bearer.
8. **Delegation** — request-dependent role requirements, readiness endpoint, profile tooling.
9. **Optional host-level fallback `IChatModel` composite** in `bOps.Hosting`/`bOps.Api`, switching only
   on classified transient/capacity failures and auditing every attempt. `bOps.Runtime` stays
   vendor-agnostic.

## 18. Definition of Done

**A. "bOps reliably diagnoses a real workstation problem."**
On a Windows host the scenario of task 88f97dda completes without a provider 400 under both a fixed
model and router mode. Crash and stability evidence arrives classified (bugcheck vs live dump vs app
crash/hang), aggregated, with real occurrence times where available, and includes unexpected-shutdown,
WHEA and storage-controller categories. `storage.health` returns a real status. The final answer
separates current from historical evidence and states coverage (for example "System log covers 56
days; Application 23 days") and any partial sources. Every model and tool call is audited, including
timeouts.

**B. "Resume reliably continues a recoverable task."**
For each status in §8, resume either progresses (≥ 1 new step after `Running` / `Attempt+1` is
persisted before the 202) or is refused with 409 and a reason, and the UI offers only what the server
says is possible. Tokens are never reset. Every resume produces a lifecycle audit event. Role tasks
cannot be resumed through the task endpoint. No task stays `Running` without an executor unless it is
shown as Interrupted and can be resumed.

**C. "bOps Delegations is operational on a fresh configured installation."**
After `bops delegate profiles init --read-only`, readiness shows Discovery and Diagnostic ready and
Remediation/Verification "not required"; a diagnosis-only delegation completes with
`DiagnosisCompleted`. A remediation request is blocked in the UI with per-role reasons until an
administrator configures all four roles; mutation still requires plan approval, step policy and
verification.

**D. "bOps UI is production-quality in English and Italian."**
No element overflows its container at 375, 768, 1024 and 1440 px in `en`, `it` and a +40 %
pseudo-locale (automated `scrollWidth` assertions); clipped text keeps an accessible full label.
Refresh keeps the session within its bounds; logout revokes it. Every error names the next action:
wait, reconnect, resume, sign in, fix configuration, inspect provider, or start a new task.
