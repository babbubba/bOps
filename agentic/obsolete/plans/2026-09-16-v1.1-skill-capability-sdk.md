# V1.1 Skill/Capability SDK and immutable execution plans

## Context

V1.0 implementation is complete and the current `main` build and cross-platform CI are green.
The formal release gate is still open because no V1.0 tag exists and `.github/workflows/release.yml`
has not produced the release-candidate artifacts, SBOMs, checksums and attestations yet.

V1.1 is already in progress. ADR-0023 introduced the Skill/Capability vocabulary, Evidence,
Finding, SkillReport, CapabilityManifest and immutable hashed ExecutionPlan contracts. ADR-0024
added execution of an approved ExecutionPlan through the existing policy, approval,
verification and audit pipeline. The milestone is not complete because no executable
`ICapability`/`ISkillProvider` boundary or end-to-end sample Skill exists yet.

## Objective

Complete the generic, dependency-free V1.1 Skill/Capability SDK and prove it with an OSS sample
Skill that gathers evidence, selects a capability, produces an immutable plan, passes policy and
approval, executes typed tools, verifies the result and emits a structured audited report.

## Constraints

- Preserve architecture rules A1-A12 and security rules S1-S11.
- Do not introduce V1.2 multi-agent behavior.
- Keep `bOps.Abstractions` dependency-free and SemVer-compatible with 1.0.
- Skill logic is deterministic package code, not a second model invocation.
- Capability execution may invoke only typed tools; no shell, arbitrary SQL or free command path.
- `IToolInvoker` exposes read-only tools from the same package only, as required by rule A10.
- Policy, approval, verification and audit remain enforced at each execution step.
- `specifiche-pendenti.md` is a non-normative working document and any local edits to it remain
  outside this plan.
- Do not create or push a release tag as a side effect of V1.1 implementation.

## Affected areas

- `bOps.Abstractions`: Skill/Capability execution contracts and serialization surface.
- `bOps.Runtime`: restricted invocation, registration and orchestration.
- `bOps.Policy`: contextual rules for Skill, capability, target, environment and blast radius.
- `bOps.Audit` and `bOps.Memory`: complete audit and a deliberate persistence/resume model.
- `samples/`: one end-to-end Apache-2.0 sample Skill.
- Core tests, architecture tests, README, CHANGELOG, HANDOFF and SDK documentation.

## Dependencies

- V1.0 implementation and the stable `bOps.Abstractions` 1.0 surface (ADR-0022).
- Dynamic package loading and package trust (ADR-0020).
- ADR-0023 and ADR-0024.
- Formal V1.0 release execution remains an independent release-management gate.

## Risks

- Accidentally creating a second policy or execution path for Skills.
- Letting capability-level approval bypass per-tool authorization.
- Exposing tools across package boundaries through `IToolInvoker`.
- Freezing incomplete or ambiguous public contracts into the 1.1 SDK.
- Resuming a partially executed plan without accounting for prior side effects.
- Producing findings that are not structurally linked to recorded evidence.

## Implementation strategy

1. Keep ADR-0023/0024 immutable and write a follow-up ADR for `ICapability`, `ISkillProvider`,
   registration and the restricted `IToolInvoker` boundary.
2. Implement contracts test-first, including round-trip coverage and package-boundary checks.
3. Register Skill providers through the existing package activation/trust boundary.
4. Extend policy configuration and evaluation for the contextual V1.1 fields without weakening
   the Critical invariant or per-step enforcement.
5. Decide and document persistence/resumability semantics before storing partial Skill runs.
6. Add an OSS sample Skill and exercise the complete flow end to end.
7. Align public SDK versioning, README, CHANGELOG, HANDOFF and task tracking with validated state.

## Validation strategy

- Test-first targeted suites for every core boundary change.
- Contract round-trip and canonical hash tests.
- Policy tests for Skill/capability/target/environment/blast-radius matching and fail-closed cases.
- Architecture tests for package isolation and absence of product/package names in the core.
- End-to-end sample Skill test covering evidence, findings, plan approval, execution,
  verification and audit.
- `dotnet build bOps.slnx --configuration Release`.
- `dotnet test bOps.slnx --configuration Release --no-build --filter "Category!=LiveModel"`.
- Angular production build and headless tests when API/UI behavior changes.
- Windows and Linux CI remain authoritative for real-platform validation.

## Completion criteria

- Follow-up ADR accepted before the new public execution interfaces are implemented.
- `ICapability`, `ISkillProvider` and restricted `IToolInvoker` are documented and round-trip
  compatible where applicable.
- Contextual Skill policy is enforced and audited.
- Persistence/resume behavior is either implemented and tested or explicitly excluded by an ADR
  with no misleading resumability claim.
- A sample Skill satisfies the V1.1 Definition of Done end to end.
- `bOps.Abstractions` carries the correct 1.1 SemVer and package documentation.
- Build, non-live tests, relevant UI validation and cross-platform CI are green.
- README, CHANGELOG, HANDOFF and task tracking describe the same state.
- V1.2 has not been started.
