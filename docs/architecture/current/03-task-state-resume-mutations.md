## 1. Scope and boundaries

This contract binds the authority of `TaskState` and the loop around it: loop containment and budgets, persistence, plans and the cursor, transactional replanning, the one-tool step view and first-call-wins, the single bounded argument correction, early-final recovery, execution attempts and terminal reasons, task origin, the resume policy and its fencing, lifecycle audit, the mutation intent journal with uncertain outcomes and reconciliation, the delegation journal, Skill terminal handling and planner-facing `PlanningGuidance`.

**Boundaries with the other contracts**

- **Contract 01** owns the model-call broker and context; model failures arrive here as classified kinds.
- **Contract 02** owns policy, approval, verification and entitlement; this contract records and fences their effects.
- **Contract 04** owns evidence, grounding and final-answer validity; this contract owns the state they are computed from.
- **Contract 05** owns the API/CLI resume and recover surfaces.

## 2. Binding rules

### C03-R01 — Loop containment, statuses and budgets are configuration

The agent loop is explicit: every state transition is a method that can be logged, tested and inspected. Nothing thrown escapes an iteration: an unknown tool name, a tool that throws or a provider that returns malformed output becomes an observation fed back to the model, never an exception that kills the task; a model-call failure (ModelProtocolException or any other exception from the model call) ends the task Failed rather than escaping. The final TaskState reflects reality, including all steps, with an enum status (Completed, MaxStepsReached, BudgetExceeded, PolicyBlocked, Failed, Cancelled, ReplanLimitReached; never a bare string). A Forbidden decision produces an audited event and an observation; N consecutive denials of the same tool (default Agent:MaxConsecutivePolicyDenials = 2) end the task PolicyBlocked. Budgets are configuration, not constants (MaxSteps, per-tool timeouts, context limit, a maximum token budget per task); exceeding any budget is a distinct, audited terminal state. Model output is intent, never instruction: text from a tool result is data and can never alter the system prompt, the tool list, the policy or a budget (see C02 external-data rule).

### C03-R02 — Task persistence

ITaskStore (save, load, list by status) is declared in dependency-free bOps.Abstractions and implemented by bOps.Memory's SqliteTaskStore over Microsoft.Data.Sqlite, one table with the whole TaskState serialized as a JSON column through System.Text.Json source generation; there is no EF Core. AgentRunner takes ITaskStore as a required dependency (no optional no-op shim): it saves the task Running after the initial plan and after every step so a crash leaves the last completed step durable and never a half-written one, and saves the final TaskState at a terminal status. bOps.Memory is a core assembly scanned by the A1 rule and contains no package, tool or provider literal.

### C03-R03 — Plan and replan model

A PlannedStep (index, description, optional expected tool) and an AgentPlan (revision, rationale, ordered steps) live in bOps.Abstractions; a planned step is a stated intention, never a tool call with arguments, and the runtime never auto-executes ExpectedTool: the model proposes the concrete call with real arguments every time. Every task opens with a dedicated planning call (revision 0) before the first step. After a step the runtime replans (one more model call producing revision N+1) when the step's authorization was PolicyDenied, UnknownTool, UserRejected or EntitlementDenied, when a step's outcome was Timeout, when the second argument-validation failure of a planned step occurs or a deviation is recognized (see C03-R06), or when the model proposes a tool call after every step of the current non-empty plan was attempted; a plain tool Failure never triggers a replan. TaskState.Plans holds every accepted plan revision, distinct from Steps (tool-call iterations); PlanStep.PlanRevision is nullable. A replan receives the goal, the current plan revision only (a deterministic projection of at most 2,048 characters), the bounded history and the directly triggering step; no earlier revisions. Plan and replan calls carry no native tools and no tool_choice: their instructions carry a compact text catalog of the tools the task may use (the same tool view as the step, so a delegated task sees only its envelope), one line per tool in ordinal order (canonical name, risk, first sentence of the description, bounded, no parameter schemas); the catalog is prompt text and not an executable surface. Planning and replanning model calls are audited like step calls (StepIndex -1 for the initial plan, the triggering step index for a replan).

### C03-R04 — Planning failure and transactional replanning

A plan or replan reply that does not parse (duplicate JSON keys at any depth count as a parse failure and never throw out of the runner) is recorded and audited as a failed attempt of kind MalformedResponse, NotRetryable, with no transport retry on top; correction re-asks are separate logical calls. A rejected initial plan is re-asked with the runtime's own bounded (512-character) validation problem ahead of the standing format instruction; at most two corrections follow the first reply (AgentRunner.MaxPlanCorrections) and a correction leaving the identical problem ends the corrections; each call is recorded, audited and charged and the token budget is checked after every call; when no valid plan results the attempt fails as ModelFailure/MalformedResponse with a synthetic 'Planning failed' step carrying the planning calls and no plan is persisted, so a resume plans again (an accepted empty plan is unchanged). Replanning is transactional: with Pcurrent the last accepted plan, a valid candidate commits; a malformed or semantically unusable candidate gets the single corrective re-ask; if the second candidate is also invalid, no empty replacement plan is appended, Pcurrent stays the last persisted accepted plan, model-call records, audit and token accounting are retained, and the attempt ends Failed through the model-failure terminal path with MalformedResponse (ordinary tasks stay resumable); a failed candidate never increments accepted plan history or resets the cursor. A resumed task with no plan re-enters planning as the new execution attempt. The initial-planning state machine was not otherwise redesigned; there is no duplicate suppression; no Evidence Store, evidence-search API or new compaction mechanism is introduced by this rule.

### C03-R05 — Step-scoped tool routing

ExpectedTool is a plan intention, never a concrete call and never a source of arguments; the executor model still emits the actual call and policy, entitlement, approval, validation, execution and verification stay runtime-owned. For a normal executable step the offered tool view is the authorized tool view (ordinary, or the delegated envelope view) intersected with the exact (ordinal) current planned step's ExpectedTool: exactly one native tool schema; ExpectedTool may only narrow authority, never widen it; a missing, unavailable, unknown or unauthorized expected tool never falls back to the complete catalog (zero native tools instead). Every newly produced non-empty planned step names a non-empty canonical expectedTool (an empty steps array means no further tool execution is planned); a persisted legacy plan or a step without a usable authorized expectedTool must not expose the full catalog and the runtime requires replanning before another operational tool can execute; if the current plan has no remaining executable steps the runtime replans before executing another operational tool (a valid replan may be empty and the following call has no native tools and can produce the final answer). The step prompt states that the single offered tool is the current plan step's tool, to be invoked at most once. No manual or automatic model selection is made by planner, replanner, executor or final response.

### C03-R06 — Bounded in-step corrections and the persisted plan position

When the current planned step has a usable ExpectedTool, the model called exactly that offered tool and the call reached runtime argument validation (including arguments the adapter reported malformed) with ToolOutcome Failure and ToolFailureKind.Validation, the failed step is persisted, audited and accounted like any step, the planned-step cursor does not advance, no replan happens, and the next execution request offers exactly the same single tool with one fixed correction sentence. Valid arguments take the normal path and any outcome other than another validation failure on that tool consumes the planned step (deviations — denial, rejection, timeout, refutation — replan). A second argument-validation failure on the same planned tool gives no third attempt and triggers the existing transactional replan with zero native tools; the correction never increments a replan counter; any other tool name keeps exact ADR-0046 enforcement (not offered, rejected as UnknownTool, a deviation that replans; no alias, fuzzy match or rewrite). A call refused by name while the current step's single tool is offered, as that step's first deviation, is classified UnofferedTool (append-only persisted value) and keeps the step with a fixed correction sentence (audited UnknownTool as before, policy never consulted); a second refusal or one after a spent correction replans. The cursor, the spent corrections and 'replan required' are one runtime value (PlannedStepPosition): a pure fold over the persisted steps of the current plan revision, oldest first, advanced by the same function in the live loop and on resume, using only typed data (exact tool name, no ToolNameError, outcome, failure kind, verification status, runtime-assigned Authorization refusals; never error text or step descriptions; synthetic steps carry no plan revision and do not count); a resumed task whose plan already exhausted its correction replans first before any operational tool is offered; a legacy record contradicting the one-correction rule fails closed and replans first. Boundary losslessness: adapter rejections (ToolNameError, ArgumentsError) cross the MAF boundary as reserved AdditionalProperties and return unchanged, so a rejected raw name never contributes to a request's alias map. With every planned step resolved the prompt says so and the following replan receives a runtime-authored turn stating the plan was complete; every replan prompt lists the task's completed read checks (successful, not partial/unavailable, not refuted, read-only, sensitive values redacted, bounded to 2,048 characters) and a replan step whose tool and complete expected arguments equal one of them is a validation problem of the existing corrective re-ask (not duplicate suppression: nothing is dropped or rewritten; a model that repeats after the correction fails the attempt as ModelFailure/MalformedResponse with the plan preserved).

### C03-R07 — Premature final answers replan; early-final plan continuation

A final candidate (a reply with no tool call) is accepted directly only when the current plan revision has no unresolved executable step (the persisted PlannedStepPosition fold has its cursor at or past the end; an empty or fully consumed plan completes as before). Otherwise the reply is not completion: the paid call is recorded once on a runtime-authored non-tool bookkeeping step ('Premature final response; plan re-evaluation required') carrying the call's ModelCalls and a runtime-authored observation naming only the unresolved planned positions and catalog-validated tool names (no tool call, result or planned-step index; never evidence, never addressable, never a limitation, never a final-response step; it consumes no planned step but counts as one step of the attempt), and the answer's text is not repeated to the replan; the replan is the normal governed replan (zero native tools, through the broker, audited, token-counted, against attempt and lifetime replan budgets, transactional) with a fixed trigger directive; an empty replan is an accepted revision after which the next call offers no operational tool and the final it produces (a new call, never the earlier premature reply) completes the task; on resume the fold treats the bookkeeping step as ReplanRequired; the unresolved suffix of a replaced revision is Superseded and no status is added; no planned tool is ever executed without a model call and MAF decides nothing about completion. Early-final recovery (AF-05H2): only a replan triggered by a rejected early final whose reply was received and was not a plan is eligible (a received output-limit reply is not retried at the same limit); the persisted plan may continue at its unchanged cursor only on a bounded runtime proof (the early final is the latest step of the revision; the fold over earlier steps is coherent with an unresolved step and no spent correction pending; the pending step's tool is a registered read-only tool offered in the current view; every earlier tool call used a registered read-only tool and was not denied, timed out or refuted; every earlier failure is a validation-class rejection of the planned tool resolved by a later successful call of the same tool at the same planned index), with the anti-loop rule that a continuation must be strictly further along than any earlier continuation of the same revision (RepeatedWithoutProgress), paid early-final replans reserved against the replan budgets before the call and continuations never charged; every evaluation is persisted on the early-final step as EarlyFinalRecoveryDecision, an acceptance writes a continuation record and the EarlyFinalPlanContinued lifecycle audit event, a refusal the EarlyFinalPlanContinuationRefused event with a stable snake_case code and then fails the attempt as a malformed-response model failure; a continuation grants nothing (the model must still call the pending tool through validation, step authority, policy, entitlement, approval and the mutation journal; resume re-proves it against the current tool view and the journal admission still refuses an unknown mutation outcome); replan calls of an early final are kept as EarlyFinalReplanCalls disjoint from its ModelCalls.

### C03-R08 — Prompt wording is honest

Prompt wording and the lifetime of one temporary instruction (no routing, budget, policy, approval, audit, accounting or tool-surface change): a completed plan offers no operational tool and the instruction does not promise that a prose proposal makes the runtime ask for a revised plan (text is the final answer; an evidence limit is reported in the answer; the one recognized channel for more work is a native call of a tool the plan or task already names, refused, audited UnknownTool and answered by the governed replan; nothing parses prose); the step prompt does not say a final answer is a way to proceed while steps remain (a reply without a tool call only makes the runtime re-evaluate the plan); recovery prompts ask for the step's operational call while its tool is offered and for the final answer otherwise, and a recovery turn is removed from the logical call as soon as the retry is answered with something usable, with the retry budget unchanged; the step prompt says only the current step's tool is offered and no other tool, URL or resource is to be invented; the one terminal correction after protocol-artifact markup follows the request's tool surface. The runtime guarantees exactly what it did before; a model's reaction to clearer text is probabilistic and is checked only by live reruns.

### C03-R09 — Budgets: steps, replans, tokens, attempt duration, accounting

Steps: per execution attempt Agent:MaxSteps (15) and lifetime Agent:MaxLifetimeSteps (60); replans: per attempt Agent:MaxReplans (3) and lifetime Agent:MaxLifetimeReplans (12); an attempt runs at most min(MaxSteps, MaxLifetimeSteps - LifetimeSteps) executable steps, the lifetime cap always wins (terminal MaxStepsReached with TerminalReason LifetimeStepLimit or StepLimit; likewise ReplanLimit/LifetimeReplanLimit) and the loop bound is an explicit per-attempt counter, never Steps.Count; Validate rejects MaxSteps < 1, MaxLifetimeSteps < MaxSteps, MaxReplans < 0 and MaxLifetimeReplans < MaxReplans naming the keys; exhausting MaxReplans ends the task ReplanLimitReached, distinct from PolicyBlocked and MaxStepsReached. Tokens: Agent:MaxTotalTokens (350,000; nullable explicit opt-out, validated positive, no clamping) is a finite cumulative emergency ceiling over the known prompt+completion usage of every model attempt (failed, retried, planning, steps, replans, EvidenceRead continuations, overflow retries) across resumes, never reset by a resume; exhaustion is strictly TokensUsed > MaxTotalTokens; absent usage stays null so TokensUsed is a lower bound, never an estimate; a planning, replanning or non-final response that crosses the cap persists exactly one synthetic non-tool PlanStep carrying the crossing call's ModelCalls (excluded from evidence resolution, the limitations digest and final-marker matching), executes no proposed tool and ends BudgetExceeded/TokenBudget, while an original final answer completes normally even if it crosses the cap (once a step enters the final-answer path MaxTotalTokens is not re-evaluated after the original final answer). Attempt duration: Agent:MaxAttemptDuration (1 h; nullable, positive, at most 24 h) is TimeProvider-based active time starting at attempt admission, paused immediately before awaiting human approval and resumed after the decision; model calls, planning, EvidenceRead processing, retry waits and tool execution consume it; a dedicated attempt-budget cancellation signal distinct from caller cancellation and provider/tool timeouts stops in-flight work, persists the interruption record and ends BudgetExceeded/AttemptDurationBudget without retry or replan. Counting: lifetime steps count executable steps (tool-call, proposed, or final-response); synthetic failure steps (Model protocol failure, Unexpected runtime failure, Execution not started) are recorded but never counted; lifetime replans count accepted revisions after revision 0 (a zero-plan resume creates revision 0); Accounting is updated in memory and written with every save; for a row without Accounting the runtime derives it deterministically from persisted history only (TokensUsed lower bound = sum of reported usage over every ModelCallRecord; LifetimeSteps = non-synthetic steps; LifetimeReplans = max(0, Plans.Count-1)), materialized by the first authoritative write and never recomputed; delegated roles keep envelope budgets and a role task has a single attempt.

### C03-R11 — Task origin and the delegated-role resume guard

### C03-R12 — Resume policy is one pure function

One pure runtime function TaskResumePolicy.Evaluate (used by the API, the CLI and the task view; no host re-implements a status check) decides resumability with ordered first-match refusal: (1) Origin Delegated -> task_delegated; (2) Origin Unknown -> resume_origin_unknown; (3) Running, whether or not an executor here holds it -> task_running (a persisted Running task is never ordinarily resumable because the absence of a local executor does not prove that no other process is running a tool call and fencing cannot undo an external side effect); (4) Completed -> task_completed; (5) PolicyBlocked -> task_policy_blocked; (6) any other status -> task_status_not_resumable (fail closed for a future status); then the journal rows 6a-6e of C03-R20; (7) token budget exhausted against the cap configured now; (8) lifetime steps exhausted; (9) ReplanLimitReached with lifetime replans exhausted. Resumable: Failed (any kind), Cancelled, MaxStepsReached, ReplanLimitReached, BudgetExceeded; rows 7-9 apply to every resumable status so an accepted resume always has headroom (no zero-work resume); BudgetExceeded is resumable only when an administrator configured a MaxTotalTokens above the tokens used. Resume rebuilds the conversation history from persisted steps (each re-wrapped exactly as the live loop does) and the current plan from the last plan, then continues the same loop; the history rebuilt on resume is identical to live history, so no runtime-authored resume note is added. Every resumed step goes through policy, entitlement, approval and verification exactly as a first-attempt step; no approval is carried across attempts or processes and a step needing approval asks a currently authenticated approver again.

### C03-R13 — Atomic transition, fencing and post-execution writes

Resume acquisition is a real atomic conditional write through the additive capability ITaskTransitionStore: TryCreate inserts only if no row exists; TryTransition replaces the row atomically at the persistence level, across threads and processes sharing the store, iff persisted status and ExecutionAttempt equal the expected ones, otherwise changes nothing and returns false; it is never emulated by load/check-in-process/save; a store without it makes resume fail closed (501 transition_unsupported) and only attempt 1 can exist; SqliteTaskStore saves with a lower ExecutionAttempt write nothing and throw TaskExecutionSupersededException. API resume sequence: load (404 if none); evaluate policy (refusal = 409 {code,message}, audited ResumeRejected); build the next snapshot (Running, ExecutionAttempt+1, ResumedAtUtc/By, TerminalReason null, Accounting materialized once) and TryTransition (false = 409 resume_conflict, nothing written); audit ResumeAccepted; submit to the launcher; 202 only after the transition AND launcher admission (a free slot and a registration keyed by task id and attempt); a non-admitted attempt is transitioned (Running,N+1) -> Failed with TerminalReason NotAdmitted and a synthetic 'Execution not started' step, audited ExecutionTerminal, and answered 503 executor_unavailable with Retry-After: 5, never 202 and never left Running; after a 202 a reader observes Running for the accepted attempt or a terminal state written by that same attempt. The CLI runs the same sequence in-process with the same refusal codes (printed, non-zero exit). Exactly one resume can win a given (status, execution attempt) without relying on the in-memory launcher registry. The execution attempt is a fencing token: with a transition-capable store every write by an executing attempt is TryTransition(state, Running, itsAttempt); a failed write means superseded (the executor stops, writes nothing more, audits ExecutionSuperseded); this covers per-step and terminal saves, the zero-plan replan, the launcher cancellation write, the backstop and admission containment, so no terminal path is unfenced. Fencing protects persisted state only; no lease, heartbeat or forced orphan resume exists. Launcher cancellation re-reads and transitions (Running, thatAttempt) -> Cancelled and audits ExecutionTerminal, never overwriting a newer attempt or a terminal state, after the runner persisted its in-memory accounting. The launcher is the final containment boundary: cancellation of its own token = Cancelled; any other exception is logged at Error and the runner's escaped-failure containment re-reads the latest persisted state and only if still Running persists Failed (RuntimeFailure) with a synthetic 'Unexpected runtime failure' step (type and redacted bounded message), never replacing a terminal state or writing an unreadable one and never throwing out of the detached task; that transition is audited by TaskExecutionFaultAuditEvent (timestamp, node, task, step index, actor, ExceptionType, bounded sanitized Reason; never stack traces, bodies, credentials, headers, prompt content or tool secrets) written only when the transition happened.

### C03-R14 — Task lifecycle audit

TaskLifecycleAuditEvent (discriminator taskLifecycle; the hash-chain format is unchanged) has stages ExecutionStarted (runner; also role tasks with the delegation correlation), ResumeAccepted, ResumeRejected (refused, lost transition or missing capability; not for 404), ExecutionTerminal (runner, launcher cancellation, backstop and admission containment: every terminal write), ExecutionSuperseded and, from the mutation journal, RecoveryAccepted/RecoveryRejected; every resume request for a stored task produces exactly one ResumeAccepted or ResumeRejected. ### C03-R15 — Mutation intent journal: guarantee, scope and boundary

Exactly-once execution is not a property the runtime can have; the guarantee is that a mutation is never executed twice unknowingly: an intent committed with an unknown effect is fail-closed and never read as 'did not happen'. Every invocation of a non-Read tool in an ordinary task (Origin Ordinary, model-driven loop) is preceded by a durable, fenced intent and followed by a durable, fenced outcome in the table task_mutation_journal in tasks.db. Not journaled: Read calls (an interrupted read is repeated), runtime post-action verification and reconciliation verification (Read by registration), delegated tasks (their own IStepJournal; never both journals), task-less plan or Skill runs (declared residual R-1) and EvidenceRead/control-plane operations. The intent is written at exactly one point: after every gate has allowed the call (resolution, delegated envelope, argument validation, the journal-mode gate where a MutationsDisabled task is a runtime Forbidden before policy, policy, human approval and IApprovalBoundTool binding, entitlement) and immediately before the timed execution; nothing refused, rejected, mismatched, unoffered, superseded or skipped has an intent. A fenced intent write that returns false means the executor was superseded (stop, write nothing more, audit, tool not invoked); an intent write that throws means the tool is not invoked and the attempt ends Failed/RuntimeFailure (a commit whose acknowledgement was lost stays Pending, unknown); cancellation or attempt-duration expiry observed after the intent and before invocation records NotInvoked, the only post-intent outcome that proves 'known not executed'.

### C03-R16 — Journal outcomes, states, identity and contents

Outcome kinds (MutationOutcomeKind): NotInvoked = 0 (known not executed), Returned = 1 (the invocation ended and the runtime observed it: Success, Failure or a contained throw; known executed, although a Failure may have partially applied and is never relabelled safe to retry), TimedOut = 2, Cancelled = 3, Interrupted = 4, and no outcome at all (all unknown). Settled iff the runtime observed the invocation end and the tool did not report a timeout, or proved the tool was never invoked, or verification confirmed the effect; a tool-reported Timeout counts as unknown. Every executed non-Read call is still verified whatever its kind; for unknown kinds only Confirmed settles; Refuted and Inconclusive do not settle (the external operation may still complete). States (TaskMutationState): Pending = 0, Settled = 1, Ambiguous = 2, Escalated = 3, ReconciledDone = 4, Abandoned = 5; unsettled = Pending, Ambiguous or Escalated; Abandoned blocks resume permanently; ReconciledDone by OperatorAcceptedDone stays unknown but is treated as executed by an administrator's decision; the classification is one pure runtime function (MutationJournalPolicy) and stores only persist the state they are given. Identity is (TaskId, ExecutionAttempt, StepIndex) plus a per-task monotonic Sequence assigned inside the intent statement (StepIndex alone is not unique across attempts); plan revision and planned-step index are context, never identity. The intent holds task id, attempt, step, sequence, canonical ToolName, ArgumentsHash (SHA-256 over canonical arguments with every Sensitive value replaced by the redaction marker), Risk, the declared VerificationToolName, plan context and IntentAtUtc; it never holds raw or redacted arguments, the ArgumentsFrom projection, credentials, tool output or error text, provider material, approvals or entitlement decisions. The outcome holds kind, tool outcome and failure kind (for Returned), verification status and time, with no message, observation or output; reconciliation reuses ADR-0030's StepReconciliation/ReconciliationAction plus HistoryRecordedInAttempt; an administrator's note goes only to the bounded audit event. Reconciliation arguments come only from the task's own recorded step; their absence means verification is unavailable (the accepted price: crash windows C2-C6 always need an administrator).

### C03-R17 — Journal storage, atomicity and fencing

The journal is a separate SQLite table in tasks.db with a conditional INSERT...SELECT fenced on the task row, per-entry compare-and-set, no TaskState writer able to drop it, queryable columns, enum values stored by name, PRIMARY KEY (task_id, execution_attempt, step_index) and UNIQUE (task_id, sequence); every journal write runs with PRAGMA synchronous=FULL so a returned commit survives power loss; the table inherits the file's owner-only permissions. Writes, each a single statement or one BEGIN IMMEDIATE transaction and never load/check/save in process: Intent requires the task row (Running,N) and a free key; Outcome requires an existing entry with no outcome and no reconciliation AND (Running,N), and in the same transaction replaces the task row with the attempt's state including the step that records it (both commit or neither); Reconcile requires (S,N) with S not Running and each named entry in its expected unsettled state (all-or-nothing); Acquire requires that no entry is Pending, Ambiguous, Escalated or Abandoned and that every named entry is ReconciledDone with history unrecorded, and replaces the task row with (Running,N+1) carrying the history steps; Recovery is the existing TryTransition to (Failed,N) and does not touch the journal. SqliteTaskStore.TryTransitionAsync also enforces the same predicate for any acquisition. Every executor journal write requires its own (Running,N); a late outcome or intent from a recovered or superseded attempt changes nothing, is deliberately not accepted even if truthful (its step can no longer be written to the fenced task row), is audited OutcomeNotCommitted/IntentNotCommitted carrying what the writer saw, and the executor stops as superseded; a stale attempt can never authorize, settle or replay a mutation, and nothing it fails to write erases the intent.

### C03-R18 — Journal pipeline, in-process outcomes and process startup

Pipeline after the gates: intent commit (fenced) -> pre-invocation check -> timed execution -> post-action verification (always) -> atomic outcome+step commit -> an unsettled outcome ends the attempt. No crash window is read as 'did not happen'; windows C2-C6 leave a Pending entry that needs an administrator; no window leaves a settled outcome without the step that records it. In-process: Returned + step atomically, then the loop continues as before; a PRE-1 runtime timeout or a tool-returned Timeout writes TimedOut + step, verifies, and Confirmed settles while otherwise the entry is Ambiguous and the attempt ends Failed with TaskTerminalKind.MutationOutcomeUnknown with no replan and no further step (a timeout is never a retry); an attempt-duration interruption writes Interrupted + step and ends BudgetExceeded/AttemptDurationBudget; cancellation while invoked writes Cancelled + a step 'cancelled while running; outcome unknown' with CancellationToken.None, runs no verification and leaves the entry Ambiguous while the cancellation propagates; cancellation before invocation writes NotInvoked + step; an exception escaping after invocation leaves the entry Pending and the launcher backstop ends the attempt; a refused outcome commit audits OutcomeNotCommitted. No new AgentTaskStatus exists; the journal is authoritative for resumability (a Cancelled task can be non-resumable with mutation_outcome_unknown); TaskState.MutationJournalMode (Absent = 0, Journaled = 1, MutationsDisabled = 2) is set when the runtime creates an ordinary task and never changed. Process startup does nothing new: no recovery, verification, reconciliation, resume or write; detection happens on read in the task view; the only path from a restarted process to a tool running again is recover, reconcile if needed, resume, and then every gate of every new call.

### C03-R19 — Orphaned Running recovery

An orphaned Running task stays non-resumable; the only path is an administrator-only fenced recovery: POST /api/agents/tasks/{id}/recover (CLI bops recover <task-id> --attempt N) with the attempt the administrator was shown. Ordered refusals: no such task (404); task_delegated; task_origin_unknown; task_not_running; task_executing_here (an execution attempt of the task is registered in this host's launcher; use DELETE to cancel it); mutation_journal_absent; transition_unsupported (501); mutation_journal_unsupported (501); recovery_conflict (persisted attempt differs from the requested one, or the fenced transition returns false). Success writes the task row only, via the fenced transition (Running,N) -> (Failed,N) with the synthetic 'Execution interrupted' step and TerminalReason ExecutionInterrupted; it executes no tool, runs no verification, asks no approval and changes no journal entry; audited RecoveryAccepted (or RecoveryRejected with the code) plus one AmbiguityDiscovered per unsettled entry. It is safe without proving the old executor dead because any mutation the old executor can still perform has a committed intent, it cannot begin another (its next intent requires (Running,N)), it cannot settle or overwrite anything, and recovery itself acts on nothing; the worst case is that the old executor completes the one invocation it had already intended, recorded as possibly applied and never repeated by the runtime. Alternatives rejected: ownership lease/heartbeat, startup containment, resume of a Running task without a local executor.

### C03-R20 — Reconciliation, journal-aware resume and the duplicate guard

Reconciliation is an administrator decision (API administrator policy; CLI as the local OS user) by a human identity (an agent or RuntimeSystem identity is refused, reconcile_not_human), allowed only for Ordinary, Journaled tasks that are not Running and have at least one unsettled entry (nothing_to_reconcile otherwise; also mutation_journal_absent, mutation_journal_unsupported, mutation_journal_unavailable, task_running, task_delegated, task_origin_unknown, reconcile_conflict). Actions: verify (re-run the entry's declared verification: Confirmed -> ReconciledDone/VerifiedDone, otherwise Escalated/EscalatedToOperator; repeatable on Escalated entries; executes only the declared Read verification tool), acceptDone (ReconciledDone/OperatorAcceptedDone; executes nothing; knowledge stays unknown in the view) and abandon (Abandoned/OperatorAbandoned; permanently task_abandoned; what it meant to do is a new task with new approvals); note at most 500 characters, audit only. There is no retry action and no 'accept as not executed': the runtime cannot verify a negative and such a mark would license repeating the mutation. Reconciliation verification finds the persisted step (attempt, index, tool name, redacted-arguments hash equal) or is Inconclusive (arguments_unavailable); requires the tool registered, IVerifiableTool and declaring the same VerifyToolName (else verification_unavailable); runs the same path as post-action verification (argument projection, fresh entitlement, bounded timeout, exceptions contained); a failed, timed-out or denied verifier is Inconclusive and never Confirmed by default; commits per entry with compare-and-set (concurrent verify answers reconcile_conflict). TaskResumePolicy rows 6a-6e follow row 6: mutation_journal_absent (409), mutation_journal_unsupported (501), mutation_journal_unavailable (503), task_abandoned (any entry Abandoned), mutation_outcome_unknown (any entry Pending, Ambiguous or Escalated); MutationsDisabled tasks pass 6a-6e on any store; the atomic Acquire re-checks 6d/6e. The acquisition that starts the next attempt appends one runtime-authored synthetic 'Mutation reconciled' step per not-yet-recorded ReconciledDone entry (tool, attempt, step, 12-hex fingerprint, verified-versus-accepted wording, not repeated automatically; not counted in any budget) in the same transaction that marks history_recorded_in_attempt, so every later rebuild of history is identical; the acquisition is the only writer of a non-Running task row. Approvals are never persisted: recovery, reconciliation and resume grant no execution authority and every call of the resumed attempt runs every gate again (Forbidden stays forbidden; Approval asks a currently authenticated approver). Duplicate guard: a non-Read call whose (ToolName, ArgumentsHash) equals a ReconciledDone entry of the same task is escalated from Automatic to Approval in the policy step with a reason naming the identity, never relaxing a decision.

### C03-R21 — Journal store capability, legacy rows, audit, guarantees and residuals

ITaskMutationJournalStore : ITaskTransitionStore (record intent, record outcome, load with journal, reconcile, acquire) is additive; every method is atomic across threads and processes and never load-check-save; LoadWithJournal reads the task and its entries in one read transaction. Fail closed, decided once per task: when the runtime creates an ordinary task it records MutationJournalMode = Journaled if the store implements the capability, else MutationsDisabled for the task's whole life (refusing every non-Read call at the journal-mode gate even if the store later gains the capability, so its read-only work stays resumable); a Journaled task on a store lacking the capability refuses resume (mutation_journal_unsupported) and non-Read execution; there is no path 'journal unavailable -> execute anyway'. SqliteTaskStore implements it and test doubles that execute non-Read tools must too. Legacy ordinary rows (MutationJournalMode = Absent: every row written before the journal) are not resumable (mutation_journal_absent) and not recoverable and no intent is invented; Completed, PolicyBlocked, delegated and unknown-origin tasks keep the unchanged refusals. A task interrupted during a Read, a model call or between steps has no unsettled entry and is resumable after recovery under the ordinary rules (read-interrupted and mutation-outcome-unknown are different states with different codes). Audit: TaskMutationAuditEvent (discriminator taskMutation, hash-chained) with stages IntentCommitted, IntentNotCommitted (superseded, store_failure, mutations_disabled), OutcomeCommitted, OutcomeNotCommitted, AmbiguityDiscovered, VerificationAttempted, Reconciled, ReconcileRejected; no arguments, output, error text, observation, credentials or provider material; the duplicate-guard escalation appears in the PolicyDecisionAuditEvent reason. API/CLI/UI: the task view carries mutationJournal (mode, available, unsettled count, entries with knowledge KnownNotExecuted/KnownExecuted/Unknown), recoverable, recoveryBlockedReason and the resumable fields; recover and reconcile endpoints are administrator-only; the UI never shows an outcome-unknown task as a plain Failed and offers no retry button. Guarantees P1-P15: no non-Read operation begins without a durable intent; an intent without outcome is never proof of non-execution; an ambiguous mutation is never automatically re-executed; a mutation proven or accepted as applied is never re-executed by resume, recovery or reconciliation; no old approval is reused; read-only work stays recoverable; late writes cannot authorize, settle or replay; no raw arguments or tool output in the journal; Running/executor safety is not weakened; nothing happens at startup; every write is atomic and fenced; a settled outcome is never durable without its step; recovery and reconciliation never invoke a non-Read tool; without a usable journal no mutation runs; pre-journal rows are never assumed safe. Declared residuals: task-less plan/Skill runs are not journaled; crash windows C2-C6 always need an administrator; a live old executor may complete its one intended invocation; OperatorAcceptedDone is an assertion; downgrading to a pre-journal binary is unsupported; the duplicate guard matches the exact (tool, redacted-arguments hash) only.

### C03-R22 — Delegation durable state and journal

IDelegationStore (in Abstractions) persists a DelegationRun aggregate (objective, actor, status, per-role identity, envelope hash and status, budget consumed, approved plan hash, step journal), implemented by bOps.Memory over SQLite (whole aggregate JSON, one row per run, transactional replace); TaskState/ITaskStore are unchanged; delegation start is idempotent on a caller-supplied key and the store is node-local. Only steps with side effects are journaled, in two durable writes: an intent (step index, tool, argument hash) committed before execution and an outcome after; read-only roles store their result at completion and restart from the beginning against the remaining budget. A child's deadline and budgets are reserved from the parent's remaining amount before the role starts and reconciled at the end, with consumption persisted; restarting a role never resets its budget and a maximum number of resumes bounds crash loops; one cancellation token tree covers run, role and step; cancelling a side-effecting step whose outcome is unknown is journaled as unknown, not failed; budget exhaustion, deadline expiry and cancellation are distinct audited terminal states. Resume is fail-closed: a completed role leads to the next role; an interrupted read-only role restarts; a plan prepared without approval needs a fresh human approval of the same hash (approvals are never persisted); an outcome Succeeded is never re-executed; an intent without outcome, or an outcome Cancelled/Timeout, is AMBIGUOUS: the declared VerificationSpec runs (Confirmed records done-by-reconciliation; Refuted/Inconclusive stops the run RequiresReconciliation); RequiresReconciliation waits for an administrator (accept the step as done, audited and administrator-only, or abandon) with no automatic retry (a retry is a new objective, plan and approval). A required budget granted as zero, a non-intersecting window or an already-past deadline at root derivation is DelegationDenied; once running, exhausting a granted budget or reaching the deadline ends the run as BudgetExceeded or DeadlineExceeded (not an authority denial).

### C03-R24 — Planner-facing parameter guidance (PlanningGuidance)

ToolParameter.PlanningGuidance is an optional (null by default), init-only, non-constructor string: a short planner-facing note on how the parameter's value changes what the result means. It is display-only: read by exactly one consumer, the planning-catalog renderer, and never by argument schema validation, expected-argument checks, policy, risk, approval binding, verification, audit or the execution path; it is prose for the planner and no code parses it; it is author-owned (the core supplies no text for any tool). For each non-sensitive parameter the catalog appends it in parentheses after type, required flag, allowed values and bounds, collapsing whitespace to a single line; a blank value renders nothing; absence renders exactly as before; rendering is cut at 320 characters (never splitting a UTF-16 surrogate pair) and happens inside the same loop that omits every Sensitive parameter, so a sensitive parameter's guidance is never emitted; authors must not put secrets in guidance. Provider adapters and the API skills DTO do not carry it, so it reaches the model only through the planning catalog. Guidance has no authority: it never makes a value mandatory or forbidden, never widens a manifest, supplies no argument, and a planner that ignores it is not rejected; the wording rule is to describe the trade-off, not the command. It is not a place to encode relations the runtime must enforce (those belong to a validator or a declarative contract, see the amendment below).

**Amendment (BOPS-0125, 2026-10-26 — narrow contract update, no new ADR; an ADR can still be required by the operator).** A tool may declare relations between two of its own parameters in `ToolManifest.ArgumentRules` (null when none; omitted from the serialized manifest), of two kinds only: `MutuallyExclusive` (both may not be supplied) and `ForbiddenWithValue` (the first may not be supplied while the second has one of the listed String/Enum values), each with a short message. The runtime reads only parameter names, values and the message, names no tool, and evaluates them in one place (`ToolArgumentRules`): (1) a plan step whose `expectedArguments` already break a rule is refused at plan time with the rule's message (only a violation no completion of the expected subset can repair; a tool default or a value the call may still add is never assumed); (2) the applicable rules are listed after the tool's parameters in the planning catalog; (3) registration refuses malformed or unbounded rules (null, blank names or message over 240 characters, self-relation, empty values, non-text second parameter), and a rule that names a parameter the manifest no longer declares (a derived manifest with fewer parameters) is inert and never shown. The tool remains the authority at execution: the rules neither widen nor replace its own validation, and a drift between them and the tool's reader is caught by a parity test for `system.events` and `system.crashes`.
