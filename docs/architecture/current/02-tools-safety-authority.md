## 1. Scope and boundaries

This contract binds the safety model: what the core may and may not name, the package and tool boundary, the absence of any generic execution tool, risk and policy, human approval, post-action verification, timeouts, tool output as data, secrets and the vault, audit, least privilege, path policy and SSRF, governed deletion, Skills, entitlements, delegation and its separation of duties, plugin trust and lifecycle, and the prerequisite and registry model.

**It contains all security invariants S1–S11** (see the invariant map in the last section). A requirement stated more strongly in an ADR or in a security invariant than in a summary is binding at the stronger strength.

**Boundaries with the other contracts**

- **Contract 01** owns model calls; this contract only fixes that the model proposes and the runtime decides (C02-R05–R09).
- **Contract 03** owns the task lifecycle that executes these controls (journal, resume, fencing). Approval binding and verification requirements are here; the mutation-journal mechanics are there.
- **Contract 04** owns evidence semantics; tool output being data (C02-R11) is the safety half, typed evidence and completeness the other.
- **Contract 05** owns the API/CLI/UI authentication, CSRF and browser-session rules; the plugin and approval endpoints enforce rules defined here.

## 2. Binding rules

### C02-R01 — The core names no package, tool or provider

bOps.Runtime, bOps.Policy, bOps.Memory and bOps.Audit contain zero literal references to a concrete tool, provider or OS identifier (examples that must never appear in the core: a docker.* or service.* tool name, a provider name such as OpenRouter, /proc, systemctl, ServiceController, or any other package-specific identifier, and never a commercial package's identity). This is mechanically checked in CI. If a core class needs knowledge about a tool, it belongs in the ToolManifest or in data (policy configuration, capability and prerequisite ids), not in the core. The single exception: bOps.Abstractions may define enums and shapes that name concepts (RiskLevel.Critical, ChatRole.Tool), never instances. Core assemblies add no package-specific vocabulary through contracts either: contract types are product-neutral and round-trip tested.

### C02-R02 — Serializable tool boundary, node scoping and local-first execution

The runtime receives from a tool exactly one thing: a ToolCallResult. Never a Stream, FileInfo, live Process, DbConnection or package-defined type: a tool reads a stream, it does not hand one back. Everything crossing the boundary round-trips through System.Text.Json with source generation and has a round-trip test (this single rule makes a LocalToolExecutor -> RemoteToolExecutor swap a DI change rather than a rewrite). Everything carries a NodeId (TaskState, PlanStep, every AuditEvent, every registry lookup; today the constant NodeId.Local, never assumed: no Environment.MachineName shortcuts). IToolRegistry and ICapabilityProbe are resolved per node, never process-wide singletons. Policy is enforced where execution happens: on the node that will execute, through the node-scoped path, so a future remote worker never trusts a controller that says 'this was approved'. Audit is written locally first (an IAuditSink writes to node-local storage; aggregation is layered on top; no path writes an audit event directly to a remote destination). A future Control Plane may send a node only typed objectives, plans and capabilities, never raw commands, and the node re-checks policy, approval and entitlement locally regardless of what it says. Remote execution by SSH-wrapped textual commands is rejected permanently (it would be the generic execution tool S1 forbids under another name).

### C02-R03 — Packages: dependency direction, extension points, operating systems as packages

A package depends only on bOps.Abstractions (it may reference third-party NuGet packages and a shared library of its own family) and never on bOps.Runtime, bOps.Policy, bOps.Memory or bOps.Audit (A7). There are exactly two package extension points, IToolProvider and IModelProviderPackage (extended by ISkillProvider : IToolProvider), identical for first-party and third-party packages: the only difference is where a package is loaded from, never how it is built. Operating systems are packages: bOps.Packages.System.Windows and .Linux each contribute their own complete tools declaring their own Platforms, selected by the registry's platform filter; there is no ISystemProvider or IServiceProvider2 and no cross-package service resolution; duplication of the tool shell is avoided with a plain library (bOps.Packages.System.Core: manifests, argument parsing, result DTOs, formatting, no OS calls) and each OS package implements only data collection; the same pattern applies to Service, Network, Process, Filesystem, Storage and the other families. Output format is part of the contract: two OS packages producing the same tool must produce the same shape, enforced by the shared conformance suite. The C# namespace is bOps.Packages.Sys.* (a namespace segment named System breaks unqualified System.* references) while project and assembly names keep bOps.Packages.System.*; the Windows package targets plain net10.0 with [assembly: SupportedOSPlatform("windows")] so bOps.Cli can reference both OS packages. Packages never resolve services from other packages (A9): shared code lives in a shared library and host services come only from the closed published set (C02-R04). Adding another operating system is a package anyone can write with zero core change. One tool answers one question on both platforms (for example one system.events tool with two collectors, never service.logs/journalctl.*/eventlog.* tools); a family may have a sibling native package (bOps.Packages.Network.Native.Core/.Windows/.Linux, exactly one chosen by OS) when new tools need native APIs, without reworking shipped tools; tools that need no OS split are concrete classes in the family's Core library taking a platform string.

### C02-R04 — The host publishes a closed set of services; PackageId is host-assigned

A package's IToolProvider / ISkillProvider / IModelProviderPackage is constructed with ActivatorUtilities (never Activator.CreateInstance) from a container that exposes only ILoggerFactory, IHttpClientFactory, TimeProvider, IConfigurationSection (the package's own section only) and ICapabilityProbe. IToolInvoker is deliberately not a constructor-injected service: the host creates it for one ICapability.PrepareAsync invocation and binds the task, actor, Skill, Capability and host-assigned package identity, and it can invoke only visible Read tools owned by that package through validation, policy, timeout and audit. Anything else is out of reach by design and the list changes only by an approved contract change. The effective PackageId stamped onto a ToolManifest or CapabilityManifest is assigned by the registry at registration time from the loading context (a package states its id in bops-plugin.json, but cannot claim to be another package or inherit its trust level); PackageTrustLevel (Unverified, Community, Verified, Official) is assigned by the host (first-party static packages default to Official; dynamically loaded packages inherit the trust established from their verified publisher key); a package-declared maxDeclaredRisk is informational and the host's configured ceiling is authoritative. A package never stamps its own prerequisite id or timestamp.

### C02-R05 — Risk model and policy: deterministic, fail closed, Critical never executable

Risk is declared once per tool in its ToolManifest as one of five ordered levels Read, Low, Medium, High, Critical, never inferred from name or arguments; the policy engine maps risk (or a tool override or a package ceiling) onto three modes Automatic, Approval, Forbidden; this is a declarative model, not a command blacklist. Policy fails closed: an unknown risk level, a missing policy entry, a malformed policy.yaml or a tool whose package cannot be identified resolves to Forbidden, never Automatic. Critical is Forbidden unconditionally and cannot be configured otherwise: PolicyConfigLoader rejects (PolicyConfigurationException) any document assigning another mode to Critical, and PolicyEngine.Evaluate checks Critical first, before any configuration lookup, so no override, default or ceiling yields anything but Forbidden; approval does not unlock it; the documented answer to 'but I need it' is that the operation happens outside bOps, by hand. Two built-in fallbacks: SafeDefault (Read/Low automatic, Medium/High approval, Critical forbidden) only when no policy.yaml exists, and AllForbidden (everything forbidden) when a file exists but failed to load, so a broken policy never falls back to something more permissive. Per-package ceilings are applied after the per-tool decision and can only lower it; a package cannot raise its own ceiling. The maximum risk a plugin manifest declares is informational and never configures policy: the host's configured ceiling is authoritative. PolicyEngine never names a tool or package in code (identifiers come from PolicyConfig data), depends only on bOps.Abstractions (YamlDotNet is a bOps.Policy dependency, never Abstractions) and bOps.Runtime depends only on IPolicyEngine/IApprovalProvider and never references bOps.Policy, so the concrete engine stays swappable at the composition root. A Forbidden decision is always audited as a PolicyDecisionAuditEvent before the loop continues. Skill-originated calls: policy.yaml has an optional skills sequence whose rules name an exact Skill, Capability, target, environment, blast radius and mode; a Skill-originated call with missing context, no exact matching rule or multiple exact matches is Forbidden; Critical stays Forbidden and package ceilings apply before contextual rules; exact matching is deliberate (no wildcards at an authorization boundary); SafeDefault ships no contextual Skill grants. PolicyContext carries NodeId, PackageId, PackageTrustLevel, the manifest, the arguments, the actor and the optional Skill context fields (SkillId, CapabilityName, Target, Environment, BlastRadius {Single, Multiple, Fleet} — a magnitude, never a count or named resource).

### C02-R06 — Tool contract: manifests, validation before execution, no clamping

A ToolManifest declares name, description, risk, platforms, required (and optional) prerequisites, typed parameters (String, Integer, Number, Boolean, Path, Duration, Enum, PathList) with required/sensitive/allowed values, additive init-only constraints (numeric Minimum/Maximum, string/path MinLength/MaxLength, PathList MinItems/MaxItems) and an optional VerificationSpec; registry validation rejects inconsistent or inapplicable constraints and blank or duplicate parameter names. The runtime validates a ToolCallRequest against the manifest BEFORE policy, approval or execution — required parameters present, types coercible, allowed values respected, every declared constraint honoured, unknown parameters rejected — and a validation failure is ToolOutcome.Failure with ToolFailureKind.Validation and an actionable message, never an exception and never a partially applied call; out-of-range values are rejected, never clamped or silently corrected (a clamped request is a wrong answer that looks right and hides the requested operation from policy and the model); every provider schema projects the same constraints, enum values and additionalProperties:false from the manifest, the manifest being the sole constraint source (package-local validation is defence in depth); bounds and completeness are never inferred by the runtime from descriptions or package JSON. Inside a tool, arguments use ToolArguments.TryGet/GetRequired, never unchecked casts. A PathList is a JSON array of path strings (no delimiter grammar or embedded JSON in a string). Read tools declare no VerificationSpec (an observation has no effect to confirm; a read verifying itself would turn a live-machine race into a Refuted step); every non-Read tool must declare one (C02-R08). Name and character-set discipline: caller-supplied names accept a small fixed character set so a value can never carry query syntax. ToolArguments is JSON-native and round-trippable (not a dictionary of objects); Sensitive parameters are redacted before any audit event is built (C02-R13). A tool's runtime-mandated Duration is measured by the runtime, never reported by the tool.

- **Supersedes / consolidates:** S2, B1 (ToolArguments), B2 (tools), ADR-0022 HARDEN-6 (decisions 1-3), ADR-0027 (PathList), ADR-0032 (arguments), ADR-0034/0035 (reject never clamp), D-028, 07-plan-corrections (validation), ADR-0033, ADR-0035

### C02-R07 — Contextual tools, mandatory approval and approval binding

Host-owned node, actor and task identity reaches a tool only through the optional IContextualTool overload with ToolExecutionContext(Node, TaskId, Actor): the runtime invokes it when a tool implements it, the legacy ExecuteAsync stays mandatory and a contextual tool fails closed there when its operation requires host-owned context; the context is built from the same host-owned values written to audit events, neither a model nor a package may supply or replace it, and verification and restricted Skill evidence calls preserve the original task and actor context. ToolManifest.RequiresExplicitApproval (default false) turns an Automatic decision into an approval decision after ordinary policy evaluation; it may tighten but never loosen: Forbidden stays forbidden, mandatory approval is an invariant not configuration, and the effective decision and its reason are audited. The optional IApprovalBoundTool: after a human answers and before target execution the runtime gives the tool the host-owned context and the exact ApprovalDecision; the callback may update only approval/preflight bookkeeping and validate that the approved arguments still identify a consumable object; a failed approved binding prevents execution and a rejected decision is audited and never calls ExecuteAsync. IToolAuditSummaryProvider is opt-in aggregate metadata only: the runtime caps it at 8 KiB, drops oversize summaries, ignores provider failures and never substitutes a complete tool result; summaries never carry messages, paths or arbitrary output (the runtime never audits an arbitrary full tool output). Runtime argument types are validated before these hooks.

### C02-R08 — Human approval and separation of duties for approval

A non-Read operation that policy marks Approval requires a decision from a human identity: IApprovalProvider returns an ApprovalDecision carrying the approver's ActorIdentity (an audit log that cannot say who approved is not an audit log), and ApprovalAuditEvent (distinct from PolicyDecisionAuditEvent) records who decided. A rejected approval ends the step like a denial with AuthorizationKind.UserRejected and is a deviation that triggers a replan. Approvals are never persisted: in-flight approvals are not restored after a crash, a resumed task requests a NEW approval from a currently authenticated approver, because persisting a decision would turn a point-in-time human decision into a reusable bearer capability; no approval is carried across attempts or processes. Console and API hosts implement IApprovalProvider (the console prints tool, risk, reason, arguments and what will be verified, then blocks on y/N plus an optional note) without AgentRunner or PolicyEngine changing. API identities come from the authenticated channel and request DTOs cannot nominate an approver (C05-R03). Approval of an ExecutionPlan means 'the operator agreed to run this plan', never 'every call is pre-authorized' (C02-R20).

- **Supersedes / consolidates:** B7 (approval), B8 (ApprovalAuditEvent), ADR-0015 (approval flow), ADR-0022 decision 6, ADR-0040 §12 (policy on resume), ADR-0018 (host-local provider), 07-plan-corrections (approver identity), ADR-0024

### C02-R09 — Post-action verification fails closed

Every EXECUTED non-Read tool call (outcome Success, Failure or Timeout) is verified after execution: the runtime resolves VerifyToolName in the same registry, carries over only the ArgumentsFrom names (the argument naming the thing to verify must carry the verifier's name), validates against the verification tool's manifest, executes it through the same per-tool-timeout path (a throw becomes Failure) and hands whatever ToolCallResult results — including one the runtime manufactured because the verifier did not resolve or failed validation — to IVerifiableTool.EvaluateVerificationAsync, whose package-owned evaluator compares observed state with the original arguments (never the original result). A tool whose Risk != Read must declare a VerificationSpec AND implement IVerifiableTool or IToolRegistry.Register rejects it with a clear error: a missing verification is impossible by construction and no fallback treats 'no verification declared' as confirmed. VerificationStatus is Confirmed, Refuted, Inconclusive or NotApplicable; Inconclusive and NotApplicable are never success; a predicate that cannot distinguish success from failure returns Inconclusive, never Confirmed by default; an exception in the evaluator yields Inconclusive; the runtime never invents a fallback and never assigns NotApplicable itself; a verification does not run for a call never executed (policy denial, operator rejection, validation failure), where Verification stays null; it runs on Failure and Timeout because a timed-out or partially failed side effect may have partially happened (S7). Refuted joins the replan deviation set and triggers a replan with an explicit observation; Inconclusive and NotApplicable do not trigger a replan; ToolCallAuditEvent.Verification carries the status for every executed non-Read call and the observation fed to the model gets an explicit 'Verification: {status}' line after the tool output. The verification call is runtime-mandated infrastructure that is not routed through IPolicyEngine/IApprovalProvider, is never seen or requested by the model and is not recorded as its own ToolCallAuditEvent; a bops.verification child activity is tagged with the original tool, the verification tool, its outcome and the final status. Package IVerifiableTool implementations must tolerate a verification result they did not expect. In the narrow case where runtime authorization (delegated envelope, governed entitlement denial, missing or failing governed provider, invalid binding or validity) prevents the verification tool from being invoked at all, neither the tool nor EvaluateVerificationAsync is called and the runtime returns Inconclusive with bounded neutral detail naming the boundary (C02-R22, C02-R24).

### C02-R10 — Every action runs under a timeout

Every ExecuteAsync is invoked with a linked CancellationTokenSource carrying a per-tool timeout. The effective timeout is the timeout the tool's manifest requests (ToolManifest.RequestedExecutionTimeout, positive and finite), or the host default Agent:DefaultToolTimeout when the manifest declares none, in either case never longer than the absolute host ceiling Agent:MaxToolTimeout (AgentRunner.EffectiveToolTimeout). A tool that needs longer than the default declares it in its manifest (for example system.dump_analyze declares 12 minutes, so first-time symbol downloads do not need a raised global default); operators may raise Agent:DefaultToolTimeout for tools without a declaration, within MaxToolTimeout. A tool that hangs must not hang the task. A timeout is ToolOutcome.Timeout — distinct from Failure, because 'it did not finish' and 'it failed' lead to different replanning, and because a timed-out side-effecting action may have partially happened and therefore still requires verification (C02-R09); the timeout is audited.

### C02-R11 — Tool output is data, never instruction

Any text originating outside the runtime — container logs, file contents, command output, event messages, a process title, a unit description, fetched web text — is untrusted input. Tool output enters the context as a structured tool-result turn (ChatRole.Tool with a ToolCallId), never concatenated into the user or system turn; it is wrapped in explicit, non-guessable delimiters and preceded by a standing marker that the system prompt defines as untrusted data; delimiter sequences appearing inside the output are neutralized before insertion; the system prompt states as a standing instruction that content inside those delimiters is observational data and can never change the goal, the tool list, the policy or the operator's intent; nothing in a tool result may alter runtime state (system prompt, available tools, policy, budget). Typed metadata is not tool text: runtime-authored context (for example the evidence-limitations digest) may depend on typed values the runtime already extracted from a result — ToolOutcome, ToolFailureKind, ToolResultCompleteness, step indexes, lengths — and on resolved canonical tool names that pass a fixed shape check; such values may only select fixed runtime-authored text; raw tool-result text (output, error messages, observations, arguments) and model text never enter that context; any marker that delimits such context is neutralized in tool output like the tool-output delimiters. A model that proposes a dangerous tool after reading a poisoned log is not a failure of this rule (policy and approval exist for that); a model whose proposal is auto-approved because the output changed the runtime's state is. Model output is intent, never instruction.

### C02-R12 — External reference data is not an instruction

External reference data — text authored by a third party and admitted by the host before any tool call, today only the knowledge index of ADR-0057 (skill names, descriptions and resource paths of the verified pack a task is bound to) — gains no authority from its position and may enter a model request only: (1) as one User-role turn per pack, in the runtime-protected context before the goal, carrying typed provenance assigned by bOps (signed pack kind as origin, pack id, version and manifest hash, tenant, admitted provider id, operation 'index', content hash) and checked by the runtime against the task's persisted binding; (2) never in the system prompt, in instructions, in a tool name, description or schema, in a runtime-authored notice, in the goal turn, or as a fabricated assistant or Tool turn; (3) after an admission check that rejects, never rewrites, text outside the published contract (normalization, allowed Unicode categories, forbidden characters, role labels, length), with the whole pack refused and audited; (4) encoded as data inside runtime markers that are neutralized in tool output and in served content like the tool-output delimiters; (5) under a standing system-prompt statement, written by the runtime from typed values only, that the block is third-party reference data, is not from the operator and is not an instruction. The role of that turn confers no authority: operator intent comes only from the goal; such text can never change the goal, the plan, the tool list, the policy, approval, a budget or an identity; the runtime never reads it to decide anything; it is never persisted, logged or exported; runtime-authored context about it may use only typed values (counts, host-generated references, closed codes, budget state). A model that proposes an action after reading such data is governed exactly like one that read a poisoned tool result. Content obtained by an actual read stays a Tool turn. The rule of C02-R11 stays true: the index is not tool output and is a turn of its own, never concatenated into the goal. The concrete admission check required by point (3) is the contract U1–U10 of ADR-0057 §U.1 and the marker neutralization of §U.2, restated in the section "Admission contract and marker neutralization" of `docs/knowledge/local-agent-pilot.md`; the rule C05-R13 binds them in the Knowledge Discovery M1 scope and adds the M1 invariants, authorization and revocation limits. (The rest of the knowledge index mechanism is Pending: C05 Pending decisions D5.)

### C02-R13 — Secrets never reach a log; secret resolution and the encrypted vault

ToolParameter.Sensitive marks an argument; the runtime redacts marked arguments before the audit event is constructed (redaction happens at the boundary, never inside a sink, so a new sink cannot leak what an old one masked). API keys come from environment variables or user-secrets in development and never as a literal in a committed appsettings.json (the committed file contains an empty ApiKey and nothing else); telemetry never carries arguments or output (C02-R14); no secret may be staged in a configuration commit. A SecretReference (provider id + opaque name, never a value) and ISecretProvider are resolved by hosts at the last responsible moment; secret providers are host infrastructure and not in the restricted plugin container; a model-provider package receives only the single credential selected for its own configured model through ChatModelOptions; hosts never log resolved values; secret values in plugin configuration are rejected. Writable local secrets use an encrypted versioned vault with an external master key and no plaintext fallback: one JSON vault file (Vault:FilePath, default vault.dat) with entries per provider id, each encrypted independently with AES-256-GCM (BCL AesGcm), a fresh random 96-bit nonce on every write, and additional authenticated data UTF8('{SchemaVersion}:{providerId}') so ciphertexts cannot be relabeled or swapped between ids; the master key is supplied externally through a SecretReference (Vault:MasterKeySecret, default environment variable BOPS_VAULT_MASTER_KEY) and fed to HKDF-SHA256 (fixed non-secret salt/info) to derive the 32-byte key; startup is fail-closed (a resolved value shorter than 20 characters is rejected and a configured-but-unresolvable key makes the host refuse to start; with no Vault:MasterKeySecret the vault is inactive and CLI-only deployments are unaffected); writes go to .tmp-{guid} then an atomic same-volume move, Linux files are restricted to UserRead|UserWrite (Windows ACL hardening is a documented known gap), a SemaphoreSlim serializes in-process writers and the root Version integer is an optimistic-concurrency token (a write requires expectedVersion to match the disk or throws VaultConcurrencyException, mapped to HTTP 409); corruption or tamper (invalid JSON, failing GCM tag, truncated nonce/tag, unknown SchemaVersion) is fail-closed with VaultCorruptedException/VaultDecryptionException and never drops the entry or treats it as absent; backup is file-level and a copied vault alone is inert; rotation is a CLI-only command (bops vault rotate-key, never on the API): decrypt all entries, read a new key from a second SecretReference, re-encrypt with fresh nonces and atomically replace the file. A secret is never returned in full: the display mask is the first six characters...last four for length >= 10 and for length 1-9 revealed = min(length-1, floor(length*0.4)) with prefix = ceil(revealed/2) and suffix = revealed - prefix (always fewer than the length), computed once at write time and stored as non-secret metadata (rendering a mask never reads plaintext back out of the vault). Every Settings mutation emits a SettingsChangedAuditEvent (SettingName, Operation Set/Replace/Clear/SelectProvider, ProviderId, Outcome Success/Denied/Failure) that never carries a value or a reversible fingerprint (sentinels TaskId = Guid.Empty and StepIndex = -1). ### C02-R14 — Audit is complete, local, append-only and tamper-evident

### C02-R15 — In-process packages are trusted code; least privilege

### C02-R16 — Path policy is checked immediately before the operation

Filesystem tools validate the requested path against the configured glob patterns immediately before touching the filesystem, on the fully resolved path — after symlink resolution and '..' normalization. A check performed on the raw input, or performed early and acted upon later, is a time-of-check/time-of-use bug. Deny by default: a path matching no read or write pattern is denied. Inventories and traversals never follow symlinks or reparse points and resolve and check the read policy immediately before reading metadata or children; limit exhaustion, policy denial, inaccessible entries, overflow, cancellation or detected mutation make an inventory partial, never complete or approval-ready. fs.size stays Read: it streams bounded summaries (one path, max depth, max entries, top-N, max duration, an exact-inventory flag with host defaults and hard ceilings; out-of-range requests fail, never coerced; a top-N accumulator retains only N largest files) and may write exact entries incrementally to a package-owned SQLite store (WAL, busy timeout, restrictive Unix permissions, parameterized SQL); a manifest is building, becomes ready only after complete enumeration and final validation, otherwise incomplete; expired and abandoned building rows are cleaned up; manifest ids carry 128 bits from a cryptographically secure GUID and are opaque; every row is scoped to host-supplied node, actor kind/id and task id and paging or deletion APIs must match the complete scope (an id alone is not authorization); entries use normalized root-relative paths with type, length, timestamps, attributes and link target. The content hash is computed over entries read in ordinal relative-path order through a length-prefixed canonical binary encoding covering the canonical root, traversal semantics and every entry but excluding random id, creation, expiry and scope; the tool result carries only bounded counts, totals, top entries, warnings, completion state, elapsed time and (ready exact inventory only) id, content hash and expiry — exact entries never enter normal tool output, model context, telemetry or a single audit event. An inventory is evidence, not a filesystem lock.

### C02-R17 — Governed recursive deletion

Permanent recursive or batch deletion uses a distinct High-risk tool with a complete, canonical, immutable manifest and RequiresExplicitApproval = true (mandatory approval is an invariant, not a configuration default): read-only fs.delete_tree.prepare builds the manifest through the inventory service from a bounded path list; fs.delete_tree accepts ONLY manifestId and approvalHash (never a root path, glob or recursive flag); roots with glob metacharacters are rejected, fully resolved under S11, required to satisfy both read and write policy, deduplicated by platform comparison, sorted and reduced so descendants of a selected root are not enumerated or deleted twice, with the reduced canonical root list shown as a warning-bearing preview; the manifest has a cryptographically random opaque id scoped to node, task and preparing actor; the SHA-256 approval hash (length-prefixed binary) covers the schema and permanent-delete semantics (no-follow-links, children-first), id, node, task, owner, creation and expiry, every canonical root, counts and bytes, and every canonical absolute entry path with type, size, timestamps, attributes and link target; it is instance-specific (random id and scope), unlike the repeatable content hash; the full list stays in SQLite; model, browser, approval and audit payloads carry only bounded summaries, id, approval hash, counts and bytes (never the entry list). ### C02-R18 — Network-reaching tools: SSRF defense at connect time

web.search and web.fetch are the first tools that reach destinations the operator did not enumerate; a URL is adversarial input like a log line, and the Read classification exempts a tool only from approval and IVerifiableTool, not from S5/S6/S10. web.search calls exactly one address, Web:Search:BaseUrl (operator configuration read at startup, never model-influenced; same trust as ModelProvider:BaseUrl), requests format=json and never scrapes HTML (a non-JSON reply is an actionable structured failure) and declares Requires ['web.searxng'] satisfied by a local synchronous check that the BaseUrl is a well-formed absolute http/https URI (not a live probe), so an unconfigured instance hides the tool; no public instance is chosen automatically; web.fetch has Requires [] and accepts a model-chosen URL governed by the SSRF, redirect and decoding rules. web.fetch uses one SocketsHttpHandler per package instance with AllowAutoRedirect=false, UseCookies=false, Credentials=null, AutomaticDecompression=None and a custom ConnectCallback that on every new connection resolves the host through IDnsResolver, validates EVERY returned address against IpAddressPolicy (by default denying loopback, link-local including the 169.254.169.254 metadata address, RFC 1918, IPv6 unique-local fc00::/7, multicast, unspecified and IPv4-mapped IPv6 wrapping any denied address), connects a raw Socket to the first surviving address or fails with an actionable 'destination denied by network policy', and returns a NetworkStream (TLS is layered by the handler with the original hostname for SNI/validation); the only override is an explicit narrow operator allowlist (Web:Fetch:AllowedHosts/AllowedNetworks) checked before the deny rules; the validated address is the connected address atomically (no check-then-connect window; a hostname blocklist, a pre-send check and inspecting the final URI after redirects are rejected). ### C02-R22 — Entitlement: one fresh boundary, product-neutral, fail closed for governed operations

Entitlement is independent of model proposal, policy, human approval, execution, verification and audit. Standalone Apache-licensed bOps operates when no entitlement provider is installed, reachable or healthy; but once an operation is explicitly governed, a missing, failed, stale or unsuitable decision prevents it. Applicability is a dependency-free public EntitlementApplicability/requirement in the resolved execution context, stamped by the HOST at registration from trusted host configuration or a trusted host-registered capability boundary (never a package declaration, a model, a provider response, a product name or installation state), with exactly two meanings — Not governed (recorded, normal path, no provider consulted) and Governed (a current matching Allowed decision is required immediately before the operation executes); a missing assignment for an operation meant to be governed is a registration/invocation error that fails closed and is never converted to not-applicable. Requests carry a FRESH opaque RequestBinding generated by trusted code for every evaluation attempt (opaque to the LLM, echoed unchanged by the provider, containing no license, token, credential or vendor payload, never entitlement proof and never reused across retry, resume, replan, delegation or verification) plus subject, installation, feature, Skill identity/version, capability, requested resource and amount, node, target and validity context; the decision is a closed Allowed|Denied with the same binding, reason code, source category, effective limits and validity metadata (ValidFrom, ValidUntil, authority/freshness id); NotApplicable is host-owned and a provider cannot return it for a governed request; the provider returns the FINAL interpreted decision and the runtime validates structure, binding match and usability only (it does not reinterpret raw grants nor hash every dimension; missing, malformed or wrong bindings fail closed). The service is one node-scoped dependency-free interface; the host owns registration and lifetime; a provider cannot widen policy, approval, the delegation envelope, package trust or the applicability boundary. The single semantic boundary is immediately before every entitlement-governed tool invocation (one shared internal routine): in ExecuteStepAsync after envelope enforcement, argument validation, policy, required approval and approval binding but BEFORE durable side-effect intent and ExecuteWithTimeoutAsync; and for an explicitly governed runtime-mandated verification invocation after the envelope permits that read; any other runtime path that can invoke a governed ITool gets the same boundary; prepared-plan, delegated, evidence, resume, retry and replan paths route through ExecuteStepAsync; only a newly obtained, binding-matched, currently usable Allowed decision permits execution, so approval followed by revocation yields no execution; entitlement never replaces policy or approval (a policy denial is final) and an Allowed cannot override an envelope denial. An entitlement denial of an ordinary invocation is AuthorizationKind.EntitlementDenied (= 5, distinct from PolicyDenied), the tool does not execute, a model-driven denied call is a denied-action deviation for replanning and a prepared or delegated plan stops (StoppedBy = EntitlementDenied, no later step); no global task status is added. The runtime's injected TimeProvider is the authoritative clock; providers state validity in UTC; there is no skew tolerance or grace: an allow is usable only when ValidFrom <= now <= ValidUntil, and a future, expired, missing-window, malformed, revoked or binding-mismatched decision is denied; a detected wall-clock rollback invalidates cached authority; a previously returned Allowed cannot be replayed; resource exhaustion or an unrecognized resource/constraint is denied and consumption/reservation is atomic at the provider boundary. A decision is per evaluation attempt and never persisted as reusable authority: resume, retry, replan, delegated execution and verification reconstruct the request, generate a new binding and obtain a new decision; revocation cannot undo a completed effect nor cancel an irreversible native operation already running (recorded and reconciled through the timeout/verification and journal semantics) but prevents later not-yet-executed governed effects; verification of an executed effect stays meaningful and must be attempted. Verification and entitlement: ADR-0016 still requires verification after every executed non-Read call; a governed mutation denied before executing has no effect to verify; when runtime authorization prevents the required verification tool from being invoked at all, neither the tool nor the evaluator is called and the runtime returns VerificationStatus.Inconclusive with bounded neutral detail naming the boundary (never Confirmed, never Refuted, no automatic rollback); everywhere else the verification result goes to the package evaluator, which stays the sole interpreter even for Failure; a verification Read is governed only if its own applicability says so (mutation entitlement neither propagates nor exempts all reads) and delegated post-action verification checks the envelope (including Tools) then evaluates entitlement freshly. Audit: a bounded neutral entitlement record correlated with the tool call (applicability, request binding as neutral correlation, decision, source category, reason code, non-sensitive constraints and limits, validity state) and never raw license or token material, provider payloads, credentials, signatures or unnecessary fingerprints; a denial after a mutation distinguishes effect executed, verification not executed, the boundary that prevented it and final status Inconclusive; runtime-mandated verification gets no peer ToolCallAuditEvent. The public surface owns only neutral contracts and generic enforcement: product business rules, provider implementations, credential formats, activation rules and product Skills stay outside this repository and Runtime names none of them.

### C02-R23 — Delegation: fixed pipeline, logical agents, separation of duties, audit

Delegation must not weaken the safety model: one place authorizes and audits a tool call (A5, S9); Critical is unbypassable and approval never waives per-step policy; tool output is data including between agents (S5); verification fails closed; approvals are not persisted across restarts. An agent is a runtime-created single-run execution context with identity, role, authority envelope, budgets and parent — not a process, service, thread or plugin; the runtime assigns the AgentId (no package or model can supply one); AgentIdentity is additional to ActorIdentity and every audit event of a delegated run carries both; roles are the generic AgentRoleKind {Discovery, Diagnostic, Remediation, Verification}; role profiles are host configuration (the optional delegation section of policy.yaml), never code and never plugin-contributed; a missing or malformed section or a REQUIRED role without a profile denies delegation (S3); SafeDefault ships no profiles, so delegation is off until an operator grants it. The orchestrator is deterministic runtime code, a fixed pipeline: Discovery (read-only, Read tools) -> Diagnostic (read-only; Findings; may prepare an immutable ExecutionPlan through an ICapability but not execute) -> operator approval of the plan hash (no plan = completed diagnosis, no approval = rejected, neither an error) -> Remediation (executes exactly the approved plan through the step pipeline; NO model call, so a model cannot alter an approved plan) -> Verification (distinct identity, gathers its own Read evidence, evaluates the declared VerificationSpec deterministically, NO model call; Inconclusive and Refuted are not success); the model reasons only inside Discovery and Diagnostic over an envelope-restricted tool view; the set and order of roles cannot be changed by a model, tool output or configuration; roles cannot request further delegation (depth structurally 1, no cycles); parallel execution is excluded. Approvals are human only: IApprovalProvider is never invoked on behalf of an agent, an ApprovalDecision whose actor is an agent identity is rejected, the API approval route authenticates a human principal, and an AgentIdentity can never be an approver; Diagnostic, Remediation and Verification receive three different AgentIds (a run whose Verification identity equals another role's is invalid); Verification does not trust Remediation's ToolCallResult — it receives the approved plan hash and expected end state and reads the system itself. Only Evidence, Finding, ExecutionPlan and VerificationReport values cross between roles: no free-text channel and no role can address another; their text reaches a later role only as delimited tool-result data (S5); every Finding keeps citing recorded Evidence; Evidence gains optional provenance (AgentId, role, delegation id). Audit: new events (delegation requested, envelope reduced, delegation denied, role started/completed, budget consumed, journal intent/outcome, reconciliation, run terminal outcome); existing ToolCall/PolicyDecision/Approval/SkillRun events gain an optional Delegation correlation block (delegation id, agent id, role, parent, envelope hash), null for non-delegated runs; envelope contents are audited as a hash plus reduced dimensions; arguments and output keep their redaction (S6) and never reach telemetry. Out of scope: parallel agents, agent-to-agent conversation, approval by any agent (including low-risk auto-approval), wildcards in envelopes, model-driven role selection or ordering, a model in Remediation or Verification, per-role model choice, plugin-contributed roles, multi-node delegation, commercial Skills, guarantees against a malicious in-process package (S8). The delegation store is protected by file permissions only (not tamper-evident like the audit chain).

### C02-R24 — Delegation authority envelope and per-role table

AuthorityEnvelope is immutable with exact non-wildcard members: allowed Skill/Capability names and Read-evidence tool names, maximum RiskLevel and blast radius, allowed targets and environments, an optional UTC maintenance window, budgets (steps, tokens, absolute deadline), depth and the originating ActorIdentity. Child = parent ∩ role profile ∩ request per dimension (set intersection, minimum risk and blast radius, interval intersection, minimum budgets against the parent's REMAINING amount, earlier deadline); an empty intersection of a REQUIRED dimension is a denial (DelegationDenied, audited with role and dimension), never a fallback to a default or the parent value. The envelope is checked in ExecuteStepAsync BEFORE IPolicyEngine.Evaluate and can only deny, the effective decision being the more restrictive of envelope and policy; per step it checks the tool against Tools, the risk against the ceiling and the time against the window at execution, and for a step with a skill scope also Skill, Capability, target, environment and blast radius; a model-proposed Read call is bound by Tools, the Read ceiling, window and budgets (Targets/Environments are audited and placed in PolicyContext but not matched per Read call, since what a Read tool touches stays bound by its own argument validation and path policy, S2/S11 — a known limit); a step above Read carrying no skill scope is denied in a delegated run (only Remediation acts, only by executing the approved plan whose steps carry scope); a delegated step without an envelope is rejected, never run unrestricted. Per-role table (ADR-0031): each dimension is Required (non-empty after reduction else DelegationDenied audited with role and dimension), Optional (empty = nothing permitted, not a denial) or Not applicable (forced empty/zero): Skills and Capabilities are not applicable for Discovery and Verification, optional for Diagnostic and required for Remediation; Tools, Targets, Environments and Steps are required for all; the risk ceiling is fixed to Read for Discovery, Diagnostic and Verification and required above Read for Remediation (a Read ceiling would execute nothing so it is denied; Critical stays Forbidden); blast radius is the minimum of the three ceilings; the maintenance window: profile, request and parent windows present and not overlapping is denied, absent means unrestricted; Tokens required (>= 1) for Discovery and Diagnostic and not applicable (0) for Remediation and Verification; the deadline is the earliest of the three and already past at root derivation is denied; a Diagnostic with no Skill/Capability yields Findings only (a completed diagnosis, not an error); Tools covers any tool a step calls, so a plan step whose tool is not in Remediation's set is denied even if its Capability is allowed. Not applicable is structural: forcing a dimension to empty only removes authority, so child ⊆ parent ∩ profile ∩ request and reduction stays monotone; a profile granting a non-empty value in a not-applicable dimension (Skills to Verification, a positive token budget to Remediation) is MALFORMED and denies delegation as a whole when loaded, never silently ignored; the operator request is one narrowing for the objective, not per role; a model call or Capability invocation in a role where the dimension is not applicable is denied at enforcement. Grant versus exhaustion: a required budget granted as zero, a non-intersecting window or an already-past deadline at root derivation is DelegationDenied; once running, exhausting a granted budget or reaching the deadline ends the run as BudgetExceeded or DeadlineExceeded (not an authority denial) and exhausting tokens cannot block an approved plan or its verification. The table is both documentation and code; changing it is an approved contract change, tested table-driven and with a monotonicity property test.

### C02-R25 — Request-dependent delegation: required roles, root, read-only diagnosis, readiness, fail-closed policy

The request shape is ONE boolean — whether DelegationRequest.Remediation is set (DelegationRun.Remediation for a stored run) — and nothing else contributes. Diagnosis-only = Discovery + Diagnostic required; a remediation request (dry run included) requires all four roles, unchanged and fail-closed. ### C02-R28 — Prerequisite readiness: registered is not available

Every Tool and Skill Capability has two independent facts: registered (loaded and validated) and available (its REQUIRED prerequisites are satisfied right now); a registered-but-unavailable component is never offered to a model and never resolves for execution; an unsatisfied OPTIONAL prerequisite leaves it available and degraded. ToolManifest.Requires keeps its meaning and is by definition the REQUIRED prerequisites; ToolManifest.OptionalRequires and CapabilityManifest.Requires/OptionalRequires are additive init properties with empty defaults (an id in both lists of a manifest, or a blank optional id, is refused at registration). Packages contribute read-only, cancellable IPrerequisiteChecks through an optional IPrerequisiteProvider on their existing entry point (first-party and plugin alike), described by a PrerequisiteDescriptor (stable id, display name, description, kind, operator remediation text, check timeout) and returning a PrerequisiteCheckOutcome (state, stable code, message, metadata — no id, no timestamp); the host stamps the id and CheckedAtUtc onto every result (a package never stamps its own, like A11), owns timeouts, state and visibility, registers the provider under the host-assigned PackageId and unregisters it with the package; PrerequisiteState is {Unknown, Available, Degraded, Unavailable, Error} (Unknown is host-internal: a check returning it is recorded as Error); components reference prerequisites by string id only (no package-to-package resolution); a prerequisite id may be registered by exactly ONE package (a second registration is refused so a plugin cannot shadow a first-party check); ids match ^[a-z0-9][a-z0-9._-]{0,127}$ and codes ^[a-z0-9]+([.-][a-z0-9]+)*$ (at most 64). PrerequisiteRegistry (host-owned, mutable, not an ICapabilityProbe) owns registration, execution, timeouts (descriptor timeout, default 10 s, clamped 1-60 s), caching and state; a timeout, thrown exception or invalid outcome becomes Error with a fixed code (check-timeout, check-failed, check-invalid-result) and fixed message — exception text is NEVER copied (it can carry secrets) while caller cancellation propagates; ICapabilityProbe remains as the boolean compatibility view (PrerequisiteRegistry.AsCapabilityProbe(): Available/Degraded -> true; Unavailable/Error/Unknown and unregistered ids -> false) that cannot be cast to the registry or to the host-only registrar and is never resolvable through RestrictedPackageServiceProvider; ToolRegistry and SkillRegistry snapshot the full PrerequisiteState from the host-owned state source (last recorded result, no I/O): required Available = available; Degraded = available AND degraded; Unavailable/Error/Unknown = not available; optional Available = no degradation, any other state = available AND degraded; a tool with unmet required prerequisites stays hidden (GetReadiness reports every registered tool; SkillRegistry withholds such a Capability from GetAvailableSkills and Resolve); a Capability with Requires but no probe/source fails closed. Unrecorded is unavailable: the cycle order (check, record durably, then snapshot) is an invariant — when recording throws, the host replaces that prerequisite's result with Error and the host-authored code state-record-failed BEFORE any Tool/Skill snapshot (required dependents not available, optional ones degraded, the successful check result not reused, fixed text, no exception text in state, messages or API, other prerequisites still record, overrides replaced as a set at the end of each cycle so a later successful record restores normal behavior; if the message store itself is down nothing is written and nothing gains authority); declared-but-unregistered prerequisites are observable (declared ids minus registered ids are recorded as host-observed Error/not-registered through the same recorder, deduplicated by fingerprint, one prerequisite.not-registered message per prerequisite, Error if some component requires it else Warning, no invented remediation); a successful non-replayed plugin enable or disable runs one RefreshAsync at the API boundary before the response (a failing refresh is logged and changes nothing about the committed result; rejected, stale, unconfirmed, failed and replayed operations and recovery refresh nothing). Messages, host wiring and surfaces: C05-R10.

### C02-R29 — Registry, capability probing and listing

IToolRegistry registers a tool under a PackageId (validating the verification rule of C02-R09 and stamping the package, A11), resolves tools by name, filters available manifests by platform and prerequisites, and supports enabling/disabling a package without a restart. GetAvailableManifests() is synchronous (the planner calls it on every step) so the registry never probes inline: RefreshCapabilitiesAsync/the prerequisite refresh is the explicit, host-driven point where availability is re-evaluated (at startup and on a timer from the version that needs live discovery), and results are cached with a time-to-live rather than resolved once, so a daemon that starts later becomes visible without a restart. Registries and probes are node-scoped (C02-R02).
