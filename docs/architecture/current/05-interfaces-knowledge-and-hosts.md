## 1. Scope and boundaries

This contract binds the hosts and their external surfaces: the console and HTTP API hosts, the task/resume/recover endpoints, API authentication and provider endpoints, the browser session (cookie, token, store, binding), the CSRF and session endpoints, session-secret hygiene in the UI, delegation endpoints and UI, plugin lifecycle endpoints, the governed-deletion authorization surface, system messages, SDK compatibility and the open-core boundary.

The Knowledge system (packs, discovery index, `runtime.knowledge_read`) is binding here **only** through `C05-R13`, in the limited scope of the development and testing of Knowledge Discovery M1 authorised by ADR-0057 and D-049. Everything else about it (the knowledge-engine mechanism of ADR-0054/0055/0056/0058/0059, production adoption and distribution) is Proposed and non-binding (see Pending decisions, D1 and D5).

**Boundaries with the other contracts**

- **Contract 02** owns the rules these surfaces enforce (approval, entitlement, secrets, plugin trust).
- **Contract 03** owns resume/recover semantics; the endpoints are bound here (C05-R02).
- **Contract 04** owns the diagnostic reply carried by the delegation surfaces (C04-R13).

## 2. Binding rules

### C05-R01 — Hosts are thin; the CLI is primary; local-first topology

bOps runs on the machine it administers: the contract is shaped for a future controller/remote-agent topology (serializable tool boundary, NodeId everywhere, per-node registries, policy enforced where execution happens, audit written locally then shipped — see C02) but no transport exists; SSH-based remote execution is rejected because it would demolish typed tools. The CLI is the primary interface and the web UI is a second client of the same runtime, never a privileged one. Hosts (bOps.Cli, bOps.Api, the Worker/AppHost composition roots) wire the same core components (AgentRunner, IToolRegistry, IPolicyEngine, IAuditSink, ITaskStore, providers) and contain no logic of their own; bOps.Api is a thin ASP.NET Core Minimal API host that adds only what an HTTP channel needs and names its packages directly in its composition root. .NET Aspire is a development-time orchestrator of dependencies and test targets only (never hosting the production runtime, which is never containerized for its real work because a container cannot restart the host's services). Native AOT is dropped: bOps ships self-contained with partial trimming and loads packages dynamically through AssemblyLoadContext.

### C05-R02 — API task execution, approvals and resume contract

A task runs as a detached background operation, not inside the starting request; AgentRunner has no mutable instance state so a singleton serves concurrent requests; progress is observed through ITaskStore (updated after every step) and the events endpoint polls the store rather than needing an event bus. Approvals cross the request boundary through a host-local ApiApprovalProvider : IApprovalProvider that stores (manifest, reason, TaskCompletionSource<ApprovalDecision>) in memory and a different request completes it; pending approvals are not persisted (a restart loses them while the Running task stays resumable and the model is re-asked for that step after resume). POST /api/agents/tasks/{id}/resume returns 202 {taskId, status, executionAttempt, executing, resumable, resumeBlockedReason} for the accepted transition, 404 for an unknown id, 409 {code,message} for every resume-policy refusal and resume_conflict, 501 transition_unsupported, and 503 executor_unavailable with Retry-After: 5 only when the launcher did not admit the acquired attempt; start's capacity 503 has the same body; DELETE is audited ExecutionTerminal/Cancelled. The task view keeps every existing property (model bodies stripped) plus executionAttempt, accounting (shown effective), origin, terminalReason, executing, resumable and resumeBlockedReason from TaskResumePolicy ('Interrupted' = Running && !executing and is not resumable; no status is added); /events emits on step count, status or execution-attempt change and ends at a terminal status. Mutation-journal surfaces: the task view adds mutationJournal (mode, available, unsettledCount, entries with knowledge KnownNotExecuted|KnownExecuted|Unknown), recoverable and recoveryBlockedReason, executionPlan shows OutcomeUnknown for an unsettled planned step; POST /api/agents/tasks/{id}/recover and /reconcile are administrator-only with the refusal codes of C03-R19 and C03-R20/R20; the CLI offers bops recover <task-id> --attempt N, bops reconcile <task-id> verify|accept|abandon [--note] and bops resume printing the same codes with a non-zero exit; the UI shows Recover with a confirmation that it runs nothing, an unsettled-entry banner with Verify again / Accept as already applied / Abandon task and no retry button, and never a plain 'Failed' for an outcome-unknown task.

### C05-R03 — API identity, roles and the single credential authority

API identities come from the authenticated channel; request DTOs cannot nominate an approver; roles distinguish observation, task operation, approval and administration (viewer, operator, approver, administrator), and writing credentials needs the administrator. All credential matching lives in one internal singleton ApiCredentialAuthority owning FindByPresentedKey (configuration order, skip empty Id, resolve the secret, skip an empty secret, SHA-256 of both sides, FixedTimeEquals, first match wins), FindBySessionBinding (including the Bearer-equivalence check evaluated with the same ordered resolution, so one configuration and secret yield the same effective credential under Bearer and a session) and CreatePrincipal (only the authentication type differs); a match exposes Id, DisplayName, roles and SecretDigest, never the secret; the Bearer handler's observable behavior is unchanged. Hosts provide an ISecretProvider and never log resolved values; the UI carries credentials without placing them in URLs (browser polling, since EventSource cannot attach a bearer header). Settings/provider APIs: GET /api/providers returns the registered provider ids (IChatModelRegistry.RegisteredProviderIds: deduplicated ids supported by at least one registered package, no metadata beyond the id) and a summary of the configured provider (provider, model, base URL, whether an API key is present) and never the key value; every settings mutation is audited and no endpoint or log can expose plaintext; a provider's non-secret configuration (BaseUrl, Model, SupportsNativeToolCalling, open ExtraParameters string map — stored and returned but not wired into ChatModelOptions) is a ProviderProfile in the plain settings.json SettingsStore keyed by provider id while the API key stays in the encrypted vault under the same id (the two halves are joined only by provider id); if ModelProvider__Provider is a real environment variable the whole appsettings ModelProvider block is used and Settings is not consulted, otherwise BaseUrl/Model/SupportsNativeToolCalling come from the stored profile with field-by-field fallback to appsettings; a host without Vault:MasterKeySecret behaves as before. Windows ACL hardening of the vault files is a known gap relative to Linux.

### C05-R04 — Browser session: trust boundary, token, store and binding

- A browser exchanges an API key once (POST /api/session) for an opaque server-side session represented by the cookie __Host-bops_session: bounded (idle and absolute expiry), revocable (logout, credential change), bound to the credential AND its current secret, stored only as digests; Bearer for the CLI and API clients is unchanged; no CORS, OAuth/OIDC/SSO, user accounts, refresh tokens or production SPA hosting is introduced.
- Token:
  - 32 bytes from RandomNumberGenerator (256-bit CSPRNG, per login, never derived);
  - cookie value = unpadded base64url (exactly 43 characters, accepted only if it decodes to 32 bytes and re-encodes identically);
  - raw bytes zeroed after use;
  - stored digest = plain SHA-256(token) as a 32-byte BLOB (no HMAC pepper);
  - lookup by digest equality on the primary key;
  - a unique-constraint violation on insert regenerates the token once, a second is a server error (500, no session);
  - no rotation during a session.
- The session store is an HTTP-host concern (IBrowserSessionStore / SqliteBrowserSessionStore in bOps.Api, no generic SQL exposed) in its own file BrowserSession:FilePath (default sessions.db; WAL, busy_timeout 5000, synchronous=FULL, owner-only mode on Unix; deleting sessions.db while stopped revokes every session);
- table browser_sessions (token_digest BLOB primary key, credential_id, credential_binding, created_at/last_seen_at/absolute_expires_at as UTC Unix ms) and NOT stored: the raw token, API key, any secret digest, Authorization header, cookie string, the keep-signed-in choice, a revocation flag (revocation is deletion), user agent or IP;
- PRAGMA user_version 0 -> create schema and set 1, 1 -> open, greater than 1 -> refuse to start naming the file;
- concurrency fails closed;
- NO caching (every cookie request reads the store);
- bounded cleanup at startup and opportunistically after login at most every 5 minutes and per invalid session;
- no hosted background service.
- Binding:
  - each row stores the credential id and binding = HMAC-SHA256(key = the 32 token bytes, message = ASCII('bops-session-binding-v1') ‖ UInt32BE(len(UTF-8 credentialId)) ‖ credentialId ‖ SHA-256(UTF-8 resolved secret));
  - validation order per cookie request: parse/canonicalise token, find row by digest, idle and absolute expiry, locate the candidate credential by stored id, verify the binding with FixedTimeEquals, resolve the secret through the current Bearer ordering and require the Bearer-selected entry to be the same entry (if an earlier entry under any Id resolves to the same secret the session is invalid: 401, row deleted, deletion cookie, category credential_changed), derive current claims and roles from that entry, authenticate;
  - any failure in these steps is 401 with the row deleted and the deletion cookie, so session authority never exceeds current Bearer authority for that key;
  - roles are re-resolved on every request and never snapshotted;
  - a rotated secret fails the binding, a removed credential has no candidate, an empty secret fails closed.
- Lifetime:
  - defaults idle 60 minutes, absolute 12 hours, touch granularity 60 s;
  - a session is expired when now >= absolute_expires_at, or now >= created_at + AbsoluteTimeout (current configuration), or now >= last_seen_at + IdleTimeout (current configuration) — equality is expired;
  - absolute expiry never slides;
  - last_seen advances only for a request that authenticated with the session, passed the CSRF gate, was not rate-limited and passed authorization, by a conditional UPDATE that re-checks expiry;
  - 401/403/429 requests never extend idle.
- Cookie: __Host-bops_session, HttpOnly, Secure always (no switch), SameSite=Strict, Path=/, no Domain; a browser-session cookie by default, keepSignedIn:true sets Max-Age = remaining absolute lifetime and no Expires; deletion with identical attributes by DELETE /api/session and on every 401 challenge of the session scheme for a request that presented the cookie.
- Authentication composition:
  - three schemes (bops policy scheme, bops-api-key Bearer, bops-browser-session);
  - any Authorization header (even empty) selects Bearer, else a Cookie containing the session cookie selects the session, else Bearer;
  - an explicitly supplied Authorization header always decides (never a silent downgrade to the cookie, and with Bearer the cookie is neither looked up, touched, deleted nor CSRF-checked);
  - authorization policies apply identically whichever scheme produced the principal;
  - the global limiter keys on NameIdentifier;
  - pipeline order UseExceptionHandler, UseAuthentication, UseBrowserSessionCsrf, UseRateLimiter, UseAuthorization, UseBrowserSessionTouch, endpoints.

### C05-R05 — CSRF gate, session endpoints and login rate limiting

The CSRF gate applies only when the effective authentication is the browser session AND the method is unsafe (anything except GET, HEAD, OPTIONS, TRACE); Bearer requests are never checked; the gate runs before rate limiting, authorization, model binding and any body read; both conditions are required, otherwise 403 {"code":"csrf_rejected",...} with Cache-Control: no-store, no cookie change and no idle extension: (a) exactly one X-bOps-Request field whose value is exactly '1'; (b) same origin against the CONFIGURED BrowserSession:Origins (canonical (scheme,host,port) tuples): if at least one Origin field exists there must be exactly one comma-free value, not 'null', parsing as http(s)://host[:port] with no user-info/path/query/fragment, whose tuple equals a trusted tuple and Referer is not consulted even if Origin fails; only if no Origin field exists, exactly one Referer parsed as an absolute http/https URL without user-info whose tuple equals a trusted tuple; neither = reject; canonical comparison: lower-case scheme, lower-case ordinal IDN host (no suffix, wildcard or DNS resolution), default-port equivalence; localhost, 127.0.0.1 and [::1] are different origins; Host, X-Forwarded-Host, X-Forwarded-Proto and Forwarded are never read (the cookie jar is not port-isolated, so SameSite=Strict does not stop a page on another localhost port; the custom header plus Origin validation is load-bearing); the UI sets no Referrer-Policy that makes the browser send Origin: null. POST /api/session (anonymous, rate-limited): origin gate always (failure = 403 csrf_rejected without reading the body or validating the key); Content-Type application/json (charset utf-8) else 415; at most 4,096 bytes else 413; body {apiKey, keepSignedIn?} with unknown/duplicate members and trailing content disallowed, apiKey trimmed as Bearer trims, bad shape 400 (parse failures never log the payload); no match = 401 invalid_credential (an already presented session stays valid); the matched credential must hold viewer else 403 viewer_role_required; creation of token, digest, binding and row (a presented cookie's digest is superseded in one transaction; a failed login never revokes anything); 200 {id, displayName, roles} and the cookie, never the key, token, digest or binding; there is no CORS policy and none may be added. GET /api/session/me (viewer, Bearer or cookie) and DELETE /api/session (browser session with CSRF passed = delete idempotently + deletion cookie + 204, replay 401; Bearer = 204 with no server change and no Set-Cookie — a Bearer request never revokes a browser session). Login rate limit: policy bops.session-login on POST /api/session only, partitioned by RemoteIpAddress, fixed window 10 requests per minute, QueueLimit 0, counting every request reaching the middleware for the endpoint except those already rejected by the CSRF gate; rejection 429 with Retry-After, Cache-Control no-store and {"code":"rate_limited",...}; fixed constants; identical for valid and invalid keys with a uniform 401.

### C05-R06 — Session secrets never leak; the Angular client holds no key

The raw API key, the raw cookie value and the token bytes must not appear in any API response body or header (other than the login Set-Cookie), application or structured log, the audit log, exception messages, sessions.db, browser localStorage/sessionStorage/IndexedDB, URLs or history, or Angular state after login completes (the digest and binding are not logged either): no request logging of bodies, Authorization or Cookie; fixed messages for every AuthenticateResult.Fail and error body (no exception text on the login path); an explicit exception handler in every environment as the outermost middleware (a problem body with no request data) so the Development developer exception page can never render Cookie/Authorization; log events carry no secrets (session created with credential id and persistent flag, login rejected category only, session revoked category logout/superseded/expired/credential_changed/credential_removed); authentication events are host-channel logs, not audit events. Angular: AuthService is a state machine (initializing, authenticated, unauthenticated, session-expired, unavailable) with the key never held (a function argument dropped when the login request completes; the login field cleared whatever the outcome; no storage API called); boot GET /api/session/me (10 s timeout) through an app initializer; 401 at boot = unauthenticated, 0/429/502/503/504/5xx/timeout = unavailable with retry; the interceptor treats a request as a bOps API request iff its URL is relative and starts with /api/, never sets Authorization, adds X-bOps-Request: 1 to unsafe bOps API requests, relies on same-origin fetch for the cookie and is the one place turning a 401 received while authenticated into session-expired; logout sends DELETE with the header and 204 or 401 means signed out, any other outcome stays authenticated with an error; the selected task is durable UI state in the dashboard URL (/dashboard?task=<uuid>; a task id is not a secret and every read is authorized server-side) read once after boot (a malformed value is removed and ignored; a 404 shows the gone error and removes the parameter) and the watch uses expectedAttempt = snapshot.executionAttempt.

### C05-R07 — Delegation surfaces: start, readiness, skills catalog, profiles CLI

- Delegation is exposed through the runtime DelegationRunner (start, resume, cancel, reconcile), the CLI (bops delegate [resume|cancel|reconcile|status|readiness|profiles init|profiles check]) and authenticated API endpoints (start/list/read/cancel/resume with the operator role; reconcile with the administrator role; approval reuses the existing human path) and a Delegations UI that applies the existing untrusted-output rendering rules.
- GET /api/delegations/readiness?remediation=false|true (default false; anything else 400 with a fixed message; Viewer; safe, no audit event, Cache-Control no-store) returns {remediation, ready, policy noFile|loaded|loadFailed, roles (exactly four entries in pipeline order with role, state, dimension, reasonCode, reason), profileDriftCount, evaluatedAtUtc};
- exactly four public states ready|missing|malformed|notRequired (malformed = present but not usable, UI label 'Not usable');
- reasonCode is the stable snake_case machine field (ready, not_required, profile_missing, policy_load_failed, profile_for_other_role, reduction_denied);
- the set may grow and clients treat an unknown reasonCode as NOT ready (never fail open);
- reason is bounded English text (the loader message and path are never sent over HTTP; for policy_load_failed the fixed 'policy.yaml could not be loaded; delegation is off until it is fixed (see the host log)');
- ready == every role not notRequired is ready and clients use the field and never recompute it;
- errors never mention profiles.
- GET /api/skills (Viewer, safe, no-store) reads ISkillRegistry.GetAvailableSkills() only (activated Skills; nothing from disabled/failed/uninstalled plugins and no plugin internals) with Skill fields skillId, package (host-stamped), trust and Capability fields name, version, description, risk, supportsDryRun, inputSchema (OutputSchema, RequiredPermissions, Timeout, Verification and RollbackDescription omitted);

- empty = 200 with skills [].
- POST /api/delegations stays Operator, is bound with strict JSON (AllowDuplicateProperties = false so a duplicate key anywhere including input is 400 malformed_json) and returns typed 400 codes (unknown_capability, capability_input_invalid ...); the CLI --input uses the same strict options; both endpoints accept Bearer or a valid browser session and need no X-bOps-Request as safe GETs.
- The UI selects Skill then Capability from /api/skills (no free-text field in the ordinary form; raw JSON only behind 'Advanced: edit as JSON' with the same client checks and the same server validator), queries readiness on load and when the 'Prepare a change' toggle changes (latest request wins), lists all four roles with the server reason verbatim and an informational drift note that never disables Submit, presents 'ready' as 'the required role profiles are usable for this type of delegation', enables Submit only when the latest readiness has ready:true, and fails closed on any readiness failure;

- by default it prints the generated YAML to stdout with the resolved absolute policy path on stderr and never writes;
- --write writes atomically (temp file + create-new move) to the CLI-resolved policy path and never overwrites silently (refuses with exit 1 and prints the fragment);

- drift is information only.

### C05-R08 — Plugin lifecycle API and UI responsibilities

One keyed asynchronous lifecycle lock per manifest id serializes install/replace, enable, disable and recovery (no global lock; multi-process access unsupported). Every mutable plugin resource exposes an opaque monotonic ETag; If-Match is required for replace/enable/disable/recovery and identity-bound If-None-Match: * for creation, checked while holding the key before promotion or activation; a stale or missing precondition gives a deterministic conflict/precondition response, deletes or quarantines the validated staging candidate and mutates nothing. A durable lifecycle operation record is atomically reserved at request admission (before archive parsing or identity discovery) under the scope (NodeId, ActorIdentity, IdempotencyKey) (128-character key bound, bounded retention) in Pending/InProgress state; only its owner executes and concurrent same-scope requests join, wait or replay and never begin a second transaction; the record stores a deterministic canonical intent fingerprint (operation kind, known plugin identity, expected ETag/precondition, activation confirmation, normalized body, and for upload the SHA-256 of the received archive bytes plus the validated manifest identity/version — a request fingerprint, not a signature; raw bytes not retained); same key + same intent replays the one logical result, same key + different intent is a deterministic idempotency conflict with no second mutation; ETag concurrency and idempotency are separate controls and idempotency never bypasses a stale-state failure. The API extends /api/plugins (no parallel surface) with administrator-only archive install/replace, explicit-confirmation enable, disable, recovery and a bounded operation/status projection; it owns authorization, the existing CSRF handling for browser mutations (ADR-0043 §9), request-body bounds, Idempotency-Key, ETag transport, rate limit and sanitized HTTP mapping (stable sanitized categories for validation/trust/compatibility/risk errors; conflict/precondition for stale state); the lifecycle backend owns archive validation, signature/trust, compatibility, the in-lock concurrency check, atomic commit, activation cleanup and recovery; the API never duplicates trust logic and the public projection excludes paths, journal data, raw exceptions, signature material and trust-store data. The UI extends the existing catalog (persisted vs actually loaded state, bounded validation outcome, publisher/signature/trust, compatibility, dependencies, capabilities, declared/effective risk, recovery availability, sanitized failure stage), may upload and initiate enable/disable/recovery, sends ETag/idempotency key, prevents obvious double-submit and refreshes stale state; it cannot decide authorization, signature validity, trust, compatibility, risk ceiling or transition legality; it must show an explicit confirmation naming plugin and version before enable (including after an update); stale state refreshes the authoritative catalog, never a blind retry; installation never implies activation. (Activation-side generations and trust: see C02.)

### C05-R10 — System messages and prerequisite state surfaces

A system message is an operator-facing operational notice — not application logging, not audit (it proves nothing and is not hash-chained) and not model evidence (it never enters a model context): SystemMessage {Id, TimestampUtc, Node, Source '<kind>/<name>', Severity Information|Warning|Error|Critical (no Debug or Trace), Code (stable machine value), Message at most 1,024 characters, Metadata, optional TaskId/ComponentType/ComponentId}; OperationalMetadata holds at most 32 entries, keys ^[A-Za-z][A-Za-z0-9._-]{0,63}$, values strings (<=512), numbers, booleans, null or arrays of at most 32 strings, at most 4,096 UTF-8 bytes serialized, and refuses keys whose normalized name contains password, passwd, secret, token, apikey, credential, privatekey, connectionstring, authorization or cookie and string values carrying URL user-info or a 'Bearer ' prefix. Checks do not write messages, transitions do: PrerequisiteTransitionRecorder compares each result with the persisted state of the same (node, prerequisite) by fingerprint state|code (none->Available quiet; ->Unavailable prerequisite.missing, Warning if any component requires it else Information; ->Degraded prerequisite.degraded likewise; Unavailable/Degraded/Error->Available prerequisite.recovered Information; ->Error prerequisite.check-failed Error; same fingerprint none; message text or metadata alone never emit); one message per prerequisite transition, never per affected tool (affectedComponents at most 16 and affectedComponentCount); the state row and message are written in one SQLite transaction guarded by compare-and-set on the previous fingerprint. Messages and prerequisite state live in one node-local SQLite database owned by bOps.Memory (SqliteSystemMessageStore, user_version 1; a newer schema refused), never in audit.jsonl, task JSON or log files; queries take optional inclusive FromUtc/ToUtc, exact Severity and case-insensitive Text (AND), ordered TimestampUtc DESC then Id DESC, keyset pagination with an opaque versioned cursor (never OFFSET), page size default 50 (1-200), retention PurgeOlderThanAsync default 90 days. Host wiring: the recorder uses the registered descriptor ('<DisplayName> is unavailable. <Remediation>', remediation <= 600 and message <= 1,024; the check's own free text is not copied); RefreshAsync runs at most Prerequisites:MaxConcurrency (default 4, 1-32) checks at once; PrerequisiteReadinessService serialises one cycle (registry refresh -> atomic transition and message records -> Tool and Skill snapshots) used by the API boot refresh, the periodic coordinator and the CLI one-shot refresh; API boot order: compose first-party providers and checks -> activate enabled plugins -> one full refresh -> only then accept work, and a missing ordinary prerequisite never stops the host; periodic refresh is API-only (Prerequisites:RefreshIntervalSeconds default 30, 5-3600); a plugin entry point implementing IPrerequisiteProvider is registered under the plugin's host-assigned id before its tools and Skills (rolled back on later failure) and removed before its load context is released; GET /api/system-messages and GET /api/prerequisites (both Viewer) project current state; retention SystemMessages:RetentionDays (90) is purged at API start then every RetentionIntervalMinutes (360), never on insertion, in batches of 1,000. AgentRunner (additive optional ISystemMessageStore argument) writes one Warning (source runtime/agent, code agent.replan.threshold) when an accepted replan brings the task's lifetime count to Agent:ReplanWarningThreshold (equality, so at most once per task; default 3 capped by MaxLifetimeReplans only when unset; an explicit value must be 1..MaxLifetimeReplans), carrying task id, provider and model ids, counts and attempt and no goal, prompt, model reply, tool argument or output; best effort, bounded to 5 s, never failing the task.

### C05-R13 — Knowledge Discovery M1: guarantees approved for M1 development and testing

**Scope.** This rule is binding **only** for the development and testing of Knowledge Discovery M1 (tasks T1–T8 of ADR-0057 §E), as authorised by ADR-0057 rev. 2 (operator, D-049). It is not a commercial-release authorisation, it removes no pending gate, it does not adopt the knowledge engine in general and it does not make ADR-0054, ADR-0055, ADR-0056, ADR-0058 or ADR-0059 Accepted: they stay Proposed (Pending decisions, D1 and D5). Words such as pack, pin, grant, trust store, provider registration and snapshot name the objects the guarantees below protect; they do not accept the architecture that defines them. The technical detail this rule needs (admission constraints U1–U10 and marker neutralization, ADR-0057 §U.1–§U.2) is the section "Admission contract and marker neutralization" of `docs/knowledge/local-agent-pilot.md`; it is detail of this rule, not a new architectural authority.

1. **Invariants that make the index data turn acceptable (ADR-0057 §D.4).** (a) The runner never reads the content of the index turn to decide anything: it verifies hash and provenance and inserts the turn; an architecture test forbids any access to the content of an index rendering in the runner other than computing its hash. (b) No byte of the index enters the system prompt, a tool manifest, a Runtime turn, audit, telemetry or persisted state. (c) The available tools depend neither on the state nor on the content of the index. (d) No field of the plan, the cursor or the budget depends on the index. (e) The only statement of operator intent remains the goal (Task) turn. Complements C02-R12, which owns the generic rule for external reference data.

2. **Closed arguments of `runtime.knowledge_read` in M1 (ADR-0057 §C.3).** Besides the existing `operation` (`discover` | `load` | `read_resource`), `skill` and `resource`, M1 adds exactly `ref`, `query` and `page`: `ref` matches `^K[1-9][0-9]{0,2}(\.R[1-9][0-9]{0,2})?$` (`load`: `Kn` only; `read_resource`: `Kn.Rm` only; `discover`: `Kn` only, listing that skill's resources) and is mutually exclusive with `skill`/`resource`; `query` (1–128 characters, `discover` only, mutually exclusive with `ref`) must pass U1–U3 and contain only letters, digits, U+0020 and `-`; `page` (JSON integer 1–64, `discover` only, default 1). Any other key, and any argument outside these limits, is `Malformed`; a page beyond the last is `OutOfRange`. `knowledgeRefs` is **not** an argument of the function: it is a plan field reserved for a possible, conditional phase M4 (ADR-0057 §A.7), absent from M1.

3. **Reference authorization and resolution (ADR-0057 §R.1, §R.3, §R.5).** A ref is a handle, never a capability: an ordinal position in the pin of this task (skills in ordinal order of name, resources in ordinal order of path), carrying no id, path, tenant or hash, not secret, never persisted outside the logical-call context, audit events and continuation turns; there is no global ref registry and no tenant, pack or version argument, so a ref from another task, or one suggested by tool output, resolves only against this task's pin. A read by ref skips no check of a read by skill and resource, in this order: offer, closed-set parsing, **current authority (including snapshot integrity)**, budget, resolution of the ref **only against the pin**, framework read, hash comparison with the pin, size limit, frame and neutralization, audit. The current authority is verified **before** the ref is resolved and is requested anew at every index refresh and every read, its outcome never memoised (only the selection-and-render computation may be, for an immutable pin and goal), so a ref cannot become a capability and a non-existent ref and an unauthorised one return the same code (no enumeration oracle). Resume re-runs the full admission with the pin as expected and the current actor's tenant; a refusal ends the task `KnowledgeUnavailable` before any step request, so no index is ever built.

4. **Revocation: what is observable in one attempt, and what is not (ADR-0057 §R.2, B1, §R.4).** Within the same attempt the runtime observes only provider deregistration, change of the actor's tenant, and a tampered or removed snapshot (index suppressed, reads refused). The grant set and the trust store are immutable during the attempt, captured by the admission service: the withdrawal of a grant, or the revocation of a key or publisher, is seen only at resume (block B1). This rule promises **no** dynamic revocation, and no M1 task, test, message or document may assume that the index or the reads observe such revocations before resume. An authorization epoch/revision (host-supplied, captured at attempt opening, compared at every refresh and read, never persisted or shown to the model) is only an extensibility requirement for a future decision on hot reload of grants or trust store; M1 neither implements, reserves fields for, nor simulates it.

5. **Restrictions of D-049 that remain in force.** (a) The index is not composed in any production host and no production configuration key is introduced; the opt-in Local Agent pilot that exists in code is the subject of the Proposed ADR-0058 (D5) and is not accepted by this rule. (b) No live benchmark is run before block B2 (acceptance of two consecutive `User` messages by the real server and chat template) is verified and the other conditions of ADR-0057 §H.4 hold: M1 merged with CI green and the offline gate passed, explicit operator authorisation, the live harness unchanged, at least three runs per arm, and the stated prerequisite on the exported requests. (c) The index is never merged into the goal turn; if B2 shows a rejection, the operator decides. (d) No implicit authorisation of a commercial release, and no pending gate is superseded.

6. **Provenance and trust boundaries of external content (ADR-0057 §D.1, §D.5).** Authority by source: the runtime is normative (system prompt, Runtime turns: fixed text or typed values); the operator's intent is the goal (Task) turn alone; tool output is observation with no authority (Tool turn with a real call id, delimited and neutralised); Knowledge content obtained by a read has no authority and is a reference (Tool turn with a real call id, pin, hash, frame, audit); the Knowledge index has no authority and is a reference, carried by a non-operator `User` turn admitted by the §U contract, encoded as JSON data inside runtime markers, placed before the goal, declared as data by a host-generated control text, with no path to state. The difference of treatment between the `User` role and the `Tool` role depends on the model's training and is residual risk, not a boundary the runtime enforces; JSON encoding does not prevent persuasive natural language; with some providers the index and the goal are distinct blocks of the same `user` message. What protects state is point 1, not the validation of text: a model that proposes an action after reading such data is governed by policy and approval exactly like one that read a poisoned tool result (C02-R11, C02-R12).

7. **Context budget of reads (dynamic, token-based).** Besides the fixed limits (reads, rejections, characters per read), reference knowledge is limited by a configurable share (`Knowledge:Budget:ContextShare`, default 0.35, 0.05–0.90) of the input space that is left after everything mandatory (protected instructions, goal, offered tool schemas, evidence, history). The runtime computes it for the provider/model actually selected, from that exact model's configured context profile minus the output reserve and the safety reserve, and from the prompt the request really held (the provider-reported prompt tokens when it reported any, else the bytes/4 estimate, kept apart in the audit). A read that does not fit is refused whole as `ContextBudget` (recoverable, no truncation, no read spent), audited with the estimated and the allowed tokens; evidence is never sacrificed to documentation and the output reserve is never lowered to make room. With an unknown capacity no allowance is invented and only the fixed limits apply. The model call audit carries the window, reserves, estimated and provider-reported prompt tokens, compactions and the knowledge share of every attempt (counts only).
