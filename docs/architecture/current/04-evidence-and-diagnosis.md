## 1. Scope and boundaries

This contract binds how observations become evidence and how answers are allowed to rest on it: the evidence model, observation versus hypothesis versus cause, negative evidence, time semantics, identity and de-duplication, typed results and completeness, coverage and aggregate modes, disclosed filters, crash and dump correlation contracts, the stability evidence contract, the evidence-limitations digest, disclosure, the structured Diagnostic reply, grounding, the final-answer pipeline, `EvidenceRead`, tool output as data in the evidence sense, and Skill evidence.

**Boundaries with the other contracts**

- **Contract 02** owns the safety half of tool output being data (S5) and the verification of side effects.
- **Contract 03** owns the persisted state evidence is read from and the terminal reasons a final validity failure produces.
- **Contract 01** owns the context and compaction that must never drop grounding or limitations.

## 2. Binding rules

### C04-R01 — Evidence model: deterministic code establishes, the model interprets

Evidence reasoning is not an inference engine. Deterministic code normalizes, classifies, bounds, identifies, aggregates, buckets, labels time kinds, reports coverage/status/completeness, removes caller-named noise sources with an echo, and lists the steps whose requested result was not obtained; the model chooses evidence, mode and horizon, relates evidence across tools, forms, ranks and tests hypotheses and writes the answer. The runtime makes limits impossible to miss, and nothing the model writes is rewritten. There is no reasoning or correlation tool, no relation, cause or confidence field in any package output or in code, no confidence score or percentage, no hypothesis ranking, no post-processing of the model's text, no cross-tool correlation code and no runtime-initiated tool execution. Evidence classes: Observed (what a tool result states, including deterministic aggregates and exact-identity merges), Derived (follows deterministically from observed evidence under stated preconditions: an at-least bound from a lower bound, the digest steps, an occurrence bound from the event's own reported time, the order of different events only under the clock preconditions of C04-R04), Hypothesis (temporal proximity, co-occurrence, frequency, similarity, patterns or non-derivable order, stated with support, contradiction and what would confirm it, never presented as observed, derived or a cause), Attributed cause (a causal relation a source record itself states, reported as that record's attribution; nothing else — correlation, order, proximity, frequency, co-occurrence, absence of other evidence, partial coverage or ruled-out hypotheses — authorizes a cause) and Unknown (not collected, unavailable, outside retained history, not applicable, null count, truncated or shortened, not visible, excluded: never zero, absence or health). bOps has no product contract that verifies a causal fact, so the model never states 'X caused Y' as its own conclusion. Forbidden inference (forbidden to the model by the evidence rule; no code produces it): a reported or record time as an occurrence time; an order between different events without the C04-R04 preconditions; proximity, order, frequency or co-occurrence as a cause; a record's attribution restated as the model's own conclusion; an empty, partial, unavailable, truncated, shortened, excluded, notCollected, notApplicable or null result as zero, absence or health; any result as proof something did not occur; a lower bound as an exact count; adding counts across overlapping tools; two records as one incident without a tool-established identity; a single current sample as a historical trend; anything before a store's oldestAvailableUtc as known; a descriptive local date as an occurrence time. High-density diagnostic tools expose bounded, decision-relevant structured EvidenceFacts (packages own the fact vocabulary; the runtime stays opaque to domain keys; complete tool JSON is not mirrored into facts).

### C04-R02 — The standing evidence rule (E1-E8)

A fixed, product- and platform-neutral paragraph of at most 2,000 characters is appended to the base system prompt, so every plan, replan and step call carries it: E1 observation versus inference; E2 current versus historical (a single sample is not a trend); E3 bounded evidence (partial, unavailable, truncated, shorter-than-requested or not fully visible evidence is a bounded observation and counts are minimums); E4 absence (no result proves something did not happen; the strongest statement is that no matching records were observed in the readable sources covering the requested period and filters, and only when the result says it is complete; not collected, not available, outside retained history, excluded and not applicable are unknowns, never zero); E5 time (record time versus occurrence time; a recording time shows only that the thing happened no later than that time; order different events as a fact only on one comparable clock with no clock change or restart between them and a gap larger than the precision of the times — two seconds when unstated — otherwise only as a hypothesis); E6 correlation (closeness never proves a cause; do not add counts of tools that say they overlap); E7 cause (never the model's own conclusion; a record's own stated reason is that record's statement, otherwise hypotheses with evidence for and against and what would confirm); E8 disclosure (when the runtime lists evidence limitations the final answer contains a section whose heading is exactly the English 'Evidence limitations' on its own line whatever the answer's language, naming per listed step the tool and what it reported as partial, missing or cut, and with none listed no such section — no empty or boilerplate one). Constraints: no identifier-shaped tokens (no token with '.', '_' or '/' between letters/digits, no camelCase/PascalCase, no letter-digit mix), no name from a fixed deny-list of operating systems, products, providers, log stores, event sources and symptom words, and no example from any incident. The digest template and the disclosure instruction are runtime-authored texts outside this rule.

### C04-R03 — Negative evidence and what may be said per evidence state

No bOps result establishes that something did not happen and no component computes absence. What may be said: Complete = observed values for the requested period and, for an empty result, at most 'no matching records were observed in the applicable, readable sources covering the requested window and filters', never that the event did not occur; Partial because truncated = lower bounds and nothing about unreturned records; Partial because a source was unreadable = that source unknown; Partial coverage = only [max(examinedFromUtc, oldestAvailableUtc), requestedToUtc] observed and everything before it unknown; coverage unknown or directory stores = reach unknown (a directory inventory describes files present now); Unavailable = nothing known and no negative statement; Unspecified = no negative statement supported; notApplicable, notCollected or null = unknown, never zero; a runtime-shortened observation = what the model did not see is not visible to it; an excludeSources source = not looked at, never 'no events from that source'; a result that says it is partial is partial as a whole. Correlation versus causation: identity exists only where a tool established it (system.crashes report-GUID merges; exact native record identity within one call); no identity key spans tools; a temporal relation between records of different results is the model's derived fact (only under C04-R04) or hypothesis, stated with both time kinds, never a merge, count adjustment or identity; overlap declared by tools may be described as 'probably the same incident' only as a hypothesis and counts are never added.

### C04-R04 — Evidence time semantics

timestampKind is 'occurred' (by documented source semantics the native time is when it happened) or 'reported' (when the system recorded, processed or wrote the evidence, possibly later). When bOps cannot establish an occurrence time it is 'reported', a reported time is never relabelled, displayed or aggregated as occurred and nothing is promoted in its place. Occurred: Application Error 1000 and Report.wer EventTime (all kinds except BlueScreen), EventLog 6005/6006, corrected WHEA, Display 4101, disk/stornvme/storahci, Linux coredumpctl and kernel journal. Reported: WER 1001 (processing), Report.wer BlueScreen EventTime (written after the reboot: evidence-driven correction of 2026-10-02), Report.wer without EventTime (file time), WER-SystemErrorReporting 1001, Kernel-Power 41, EventLog 6008, uncorrected or unknown WHEA, minidump file times. A minidump file name's date is returned only as the descriptive fileNameLocalDate (local calendar day, never converted to UTC, never an occurrence time, never used for window, bucketing, ordering or first/last seen). Merged crash primary-time precedence: Report.wer EventTime, Application Error 1000 time, earliest WER 1001 time, with reportedUtc = earliest WER 1001 time when the primary is occurred. Aggregation never mixes kinds (timestampKind is in every system.crashes and system.stability aggregation key; timeline rows are per category AND kind); system.events groups carry record times and no timestampKind and record times are described as 'the event record is timestamped at T' and never promoted. Relations between different events require all clock preconditions to be shown by evidence: one comparable clock domain (the same host); normalized UTC instants (a local date is never an instant); no known clock adjustment and no restart between them (no boot, shutdown or unexpected-shutdown evidence in the interval and the interval not left uncertain); a difference exceeding the coarser precision (two seconds when not stated). Derivation: occurred vs occurred = order and interval (never causation); reported A < occurred B = A before B; reported A >= occurred B = nothing about occurrence order; reported vs reported = order of reporting only; record time A vs any B = order of the record only; local date vs instant = nothing; when any precondition is not shown the order is not a derived fact and is only a hypothesis input. For one event occurred(A) <= reported(A).

### C04-R05 — Identity, correlation and de-duplication

Exact native identity (same channel and record id) means one record, within a call. A crash's identity is the set of WER report GUIDs its records carry (Application Error 1000 IntegratorReportId; WER 1001 ReportId; Report.wer ReportIdentifier/IntegratorReportIdentifier), used only if they parse as a non-zero GUID and normalized lower-case D; records whose identity sets intersect transitively are one crash, with fields by the stated precedence, and repeated WER 1001 records of one report count once. A record without a usable GUID is never merged, and bOps never correlates by time proximity, process name, code, bucket, message text or similarity: a possible duplicate is reported (uncorrelatedCount) and not removed. system.stability counts evidence records, not incidents: related records sharing no identity stay separate (a Display 4101 and a LiveKernelEvent 141 of one TDR are two records; a Kernel-Power 41 with a BugcheckCode and the System-log 1001 are two records) and the manifest says counts must not be summed into an incident count.

### C04-R06 — Typed results, completeness and failure kinds

ToolCallResult carries additive init-only FailureKind and Completeness (Unspecified by default): runtime-owned failures are classified structurally, packages may report environmental failure and complete, partial or unavailable evidence, and the runtime propagates the typed values to the step and the audit without parsing package JSON; validation, authorization, timeout, internal and environmental failures stay distinguishable from successful-but-partial evidence; bounds and completeness are never inferred by parsing descriptions or package JSON in the runtime and invalid arguments are never clamped. For the System event/crash/stability tools: results are deterministic JSON; sources use the inventory vocabulary (available, partial, unavailable, unsupported, notApplicable); a source unreadable for permissions, a missing log service or an I/O failure is unavailable — never an empty healthy result; status is unavailable when no applicable source could be read and partial when some could not; truncated is true when a limit, byte budget or scan ceiling cut the result; complete = (status == complete) AND (truncated == false) AND (coverage.state == complete), so an empty result is trustworthy only when complete is true; ToolCallResult.Completeness stays derived from the emitted JSON (a scan cut by ceiling/time/limit/byte budget or an unreadable source is Partial, no readable source is Unavailable, a store whose history starts after the requested start or whose oldest record is undeterminable is Partial); Complete never hides a retention gap and coverage complete never makes a truncated result Complete; status keeps meaning source state so the two dimensions stay distinguishable. Unknown levels and providers stay explicit; raw XML, journald field bags and native metadata are not returned; messages are bounded; there is no elevation request and a host without privileges reports a gap, never an empty log.

### C04-R07 — Retention coverage and time horizons

system.events, system.crashes and system.stability each return a coverage object that answers only how far back each store actually reaches compared with what was asked (never whether the read succeeded): stores with basis eventLog/journal/directory, oldestAvailableUtc, logMaximumBytes (integer or null; always null for journald) and state complete|partial|unknown; an eventLog or journal store is complete when oldestAvailableUtc <= requestedFromUtc, partial when later and unknown when undeterminable (null, never an estimate); directory stores (WER directories, the minidump directory) are always unknown (absence of older files proves nothing) and never change the global state; the global state is partial if any retention-bearing store is partial, else unknown if any unknown or none, else complete; each source carries examinedFromUtc, the oldest instant this call's scan actually reached (null if not read); coverage probes share the call's 20-second bound and a probe that does not finish leaves oldestAvailableUtc null and state unknown. A non-elevated Windows identity normally cannot read the minidump directory, so that source is unavailable, status partial and the result Partial, never Complete; a category count of 0 is trustworthy only when complete is true and a category whose sources could not be read has count null, never 0. Aggregation modes: system.events and system.crashes each have ONE optional mode argument (raw|aggregate), the single aggregation switch (no boolean aggregate argument or second switch); system.events defaults to raw, system.crashes defaults to aggregate (intentional default change versioned by schema 2); aggregate returns one group per aggregation key with count, firstSeenUtc and lastSeenUtc; every filter applies before aggregation; limit bounds groups in aggregate and rows in raw; the result states its mode. Minute arguments keep their manifest bounds (1-10080); long horizons use a separate day argument (windowDays for events, sinceDays for crashes, integer 1-180) valid only in aggregate mode; mode resolves first (explicit, else the tool default); the cross-field rules are enforced once in the shared reader before collection as ToolFailureKind.Validation naming the rule, in fixed order (minute and day argument together; day argument in raw mode; the rest); nothing is clamped, the tool never switches mode itself, every numeric bound stays a manifest constraint and aggregate over a long horizon runs under the same scan ceilings and time bounds (a hit ceiling is reported truncated with the instant actually reached).

### C04-R08 — Source filtering is disclosed: excludeSources and sourceFilter

system.events accepts an optional String excludeSources (comma-separated, trimmed non-empty entries, each at most 128 UTF-16 units, the source character set, at most 8 entries, at most 1,024 characters in total), valid in both modes and every horizon; absent means no exclusion; an empty entry, more than 8 entries, an oversized entry, a forbidden character, two entries equal under OrdinalIgnoreCase or an entry equal to source is rejected as Validation (nothing clamped or corrected); a syntactically valid name matching nothing is accepted and echoed (existence is not knowable before the read). A record is excluded when its canonical source (the value shown in its source field) equals an entry under OrdinalIgnoreCase, with no second matching rule; on Windows exclusion is native before the scan ceiling via a Provider[@Name!=...] XPath predicate built only from registered-spelling or validated names AND the shared post-filter is also applied; if the construct is not honoured on real Windows, implementation stops and returns to architecture rather than silently post-filtering; on Linux the canonical source is SYSLOG_IDENTIFIER, else _SYSTEMD_UNIT, else _COMM, else unknown, and exclusion is the shared post-filter only. Exclusion applies before grouping, limit and the byte budget; observedEvents counts matched records after exclusion; no excluded-record count is reported; every successful result carries an always-present top-level excludeSources array right after window (sorted OrdinalIgnoreCase then Ordinal, byte-identical for permuted input), part of the envelope the byte budget never removes; complete:true with an exclusion means complete for the filtered question and an excluded source is never read as absent. sourceFilter (ADR-0061): a new top-level key of every system.events result in both modes, immediately after excludeSources and before coverage, always present (null without a source argument), with requested (validated caller spelling, at most 128 characters), matching ('exactCaseInsensitive', whole-string OrdinalIgnoreCase, a closed set), matchedFields (Windows ["source"], Linux ["source","unit"]), registrationStatus (registered|notRegistered|unknown: a statement about the host registry, never events — Windows only; unknown always on Linux and on Windows when the catalog could not be enumerated), observedMatch (whether at least one record read satisfied the whole query, computed before grouping, limit and the byte budget, equal to observedEvents > 0) and caution (null|noMatchSourceNotRegistered|noMatchSourceUnverified, a pure function of the two: observedMatch true -> null; false + registered -> null; false + notRegistered -> noMatchSourceNotRegistered; false + unknown -> noMatchSourceUnverified) plus a fixed English semantics constant that names no domain; the dimensions never alter status, complete, truncated, sources, coverage or ToolCallResult.Completeness (a notRegistered or unverifiable name does not make a result Partial); no fact carries sourceFilter and no zero-count fact is ever added; the audit summary gains {registrationStatus, observedMatch, caution} without the requested name; windows reads the provider catalog once per call; the envelope fits the 4,096-byte floor (stop and return to architecture if the worst-case envelope exceeds 3,584 bytes); schemaVersion stays 2; Linux verification of names via journalctl listing, fuzzy suggestions, aliases and hardware-specific mappings are not part of the contract.

### C04-R09 — system.events / system.crashes / system.dump_analyze result contracts (principles)

The event, crash and kernel-dump tools are Read tools with one cross-platform result shape. Collection mechanics are fixed in code and never model-influenced: Windows reads Event Log channels through EventLogReader with an XPath built only from validated values, only channels the identity can read (no elevation, no identity switch, no PowerShell, no wevtutil), an unreadable record skipped and making its source partial, a 20-second collection bound shorter than the 30-second default tool timeout; Linux starts journalctl directly (UseShellExecute=false, fixed switches, every value its own ArgumentList item, fixed environment, stdout read to a scan ceiling of 10,000 records per source, the child killed on cancellation or timeout), source and text filtering after parsing, and a ceiling hit with an unsatisfied filter marks the result truncated. System.crashes: records merge only on a shared WER report GUID; aggregate keys never mix occurred and reported times; the dump file is never opened by system.crashes (only a path string); bounded records, directories, bytes and duration. system.dump_analyze (Read, Windows only, one 'path' argument, gated by the package-owned capability windows.debugger.kd) runs kd.exe (optionally preceded by dumpchk.exe) with one fixed source-controlled command sequence between per-run nonce markers, no shell, the process tree killed on timeout, output bounded, debugger environment scrubbed, paths limited to .dmp/.mdmp under %SystemRoot%\Minidump or %SystemRoot%\LiveKernelReports or exactly %SystemRoot%\MEMORY.DMP with no reparse point; status is complete (every section closed, PDB-backed kernel symbols, a bugcheck code and a resolved module, no timeout/cut/DumpChk failure), partial (some evidence with a limitation), unavailable (not-found, access-denied, debugger-unavailable, timeout or debugger-failure) or invalid (DumpChk failed and KD found no evidence); a missing black box or preflight is a warning and black-box available:false is absence of data, never evidence of health; a symbol problem is symbols.status partial/unavailable, never invalid; a timeout with nothing parsed is ToolOutcome.Timeout, after some evidence a successful partial result with failure 'timeout'; the analysis carries the qualifier 'debugger-attribution' and states that attribution is not a proven root cause; the audit summary holds aggregates only and never the path, frames, modules, device identifiers or debugger text. ### C04-R10 — system.stability: contract, bounds and boundaries

system.stability is a Read tool with no VerificationSpec, contributed by the System.Windows and System.Linux packages with manifest, argument reading, category table, aggregation, bucketing, coverage evaluation, ordering, bounds, JSON and audit summary in System.Core and only collection per OS; every provider name, event id, journal match and message pattern is a constant of the OS package, none named by the core and none supplied by the caller. Arguments: only optional windowDays (1-180, default 30) and limit (1-200, default 50, bounds groups), rejected from manifest constraints and never clamped; unknown arguments are rejected; there is no mode, no category filter and no argument naming a provider, event id, channel, journal field, message text, path or query (no event query language). Eight categories in fixed order (unexpectedShutdown, kernelCrash, kernelFault, hardwareError, displayFault, storageError, memoryExhaustion, minidump), all listed on both platforms as applicable, notApplicable (the platform has no typed evidence and bOps does not infer one) or notCollected (related evidence exists that this version does not read); a category count is exact only when available, a lower bound when partial and null when unavailable; displayFault is Display 4101 and LiveKernelEvent 0x117, 0x141, 0x193 (graphics-stack fault evidence, not proof of a reset) and never 0x1a1. Bounds: 5,000 records per Windows Event Log source, minidump enumeration stops at 256 entries, 10,000 Linux kernel records, one shared 20-second bound for every read of a call incl. coverage probes; a source that hits a ceiling is partial and the result truncated; unreadable or malformed records are skipped and make their source partial and a value failing its pattern becomes null; the result is a schemaVersion-1 JSON of at most 32,768 UTF-8 bytes whose envelope always fits; strings are pattern-matched or null with no message text anywhere. Security: read-only, no elevation or identity change, no PowerShell, wevtutil, shell or WMI; dump files are enumerated for name/size/time only and never opened, read, parsed, hashed or uploaded; no raw event XML, journald field bag or message text; the result carries no hint, pre-built argument set or suggested call for another tool; the audit summary holds only aggregates (never a group component, minidump file name or directory, message or native field). Tool boundaries: system.events answers what a log recorded, system.crashes what crashed or hung (one record per crash), system.stability whether the machine is stable (category totals, signatures, timeline, minidump inventory); the two deliberate overlaps (bugchecks; display live dumps) are stated in both manifests and served by one package-internal normalizer; the model must not add counts across the two tools. Adding a category, provider tuple, Linux rule or bucket width needs an amendment and a schemaVersion bump when the shape changes.

### C04-R11 — The evidence-limitations digest

The runtime lists in every step prompt the steps for which the requested result was not obtained or only partially available (evidence reads and actions alike), built only from typed ToolCallResult fields and persisted step data (never package JSON, tool text, arguments, observation or model text): from the task's persisted steps of all attempts in ascending Index considering only steps with a ToolCall and a Result, a step is listed when (1) Completeness is Partial or Unavailable, (2) Outcome is not Success and FailureKind is not Validation, (3) Outcome is not Success, FailureKind is Validation and the step is not superseded, or (4) the result is shortened (Outcome Success, Output non-empty and (Observation ?? '').StartsWith(Output, Ordinal) is false; persisted data only, so identical live and on resume). The only supersession rule: a resolved-tool Validation failure at step i is superseded when a later step j has the same ToolCall.ToolName (ordinal) with Outcome Success; non-validation failures are never superseded; an unknown-tool rejection (Description 'Denied', FailureKind Validation — 'Denied' is a reserved description token) is never superseded and is listed as the fixed token '(unknown tool)', never the caller-supplied name. Entries are '- step <index>: <tool> — <facts>' with the tool as the canonical name when at most 128 characters of letters/digits/./_/- else '(tool name omitted)', ascending index, the newest 16 entries plus one fixed line counting earlier unlisted steps, entry at most 256 characters, fixed text at most 512, digest at most 4,608. It is a versioned template (EvidenceLimitations/v2 after the Diagnostic amendment) between the markers <<<BOPS_EVIDENCE_LIMITATIONS>>> and <<<END_BOPS_EVIDENCE_LIMITATIONS>>> appended to the STEP system prompt after the plan section (not plan/replan prompts) with one fixed sentence that it is authored by bOps from typed results; WrapToolOutput neutralizes both markers in tool output; it is byte-identical for the same persisted steps and rebuilt on every step call so a resumed attempt sees the same digest; compaction does not change it and a compacted step is not a limitation by itself; reading an evidence range never erases a partial/shortened limitation. HARDEN-9 acquires no evidence (the runtime never executes a tool on its own) and does not change the 4,000-character observation budget. Typed metadata only selects fixed runtime-authored tokens (completeness/outcome/failure-kind values select their enum names; integers are step indexes and lengths) and never changes the goal, tool list, policy or budgets; free tool text never enters any runtime-authored block.

### C04-R12 — Limitation disclosure in the final answer

The heading detector is deterministic: split into lines; skip fenced code blocks (opened by three or more backticks or tildes after at most three leading spaces, closed by at least as many of the same character; an unclosed fence runs to the end) and tab/4-space indented lines; normalize each remaining line (trim; remove one leading ATX prefix of 1-6 '#' followed by a space or tab; one trailing ':'; one surrounding pair of ** or __; one trailing ':'); a heading is a line equal to 'Evidence limitations' under OrdinalIgnoreCase. The heading stays English on purpose. When the persisted digest is non-empty, the role is not the delegated Diagnostic one, Agent:EvidenceDisclosureEnabled (default true) is on and the detector finds no heading in the final answer, the runtime appends — with no model call — the answer + (a closing fence line only if the answer ends inside an unclosed fence) + a blank line + '## Evidence limitations' + a fixed line stating that the section was added by bOps from typed tool results (EvidenceDisclosure/v2) and the answer above is unchanged + the digest's listed entry lines exactly as rendered from typed fields + the omission line when entries are not shown; never any tool output, error, observation, argument or model text, and at most the digest bound. The original answer is an exact byte-identical prefix of the persisted final; an answer with a valid heading is persisted byte-identical; no listed limitations means nothing is appended; the section is a pure function of the persisted steps, persisted once and never recomputed on resume; the disclosure never executes, authorizes or audits a tool call, creates no step, replan or status change, and the model's text is never rewritten or truncated. The final step's Description records the outcome through fixed runtime-written markers (the two historical re-ask markers remain readable, and only they reconstruct a re-ask logical call); every consumer recognizes a final-response step through one shared predicate (an exact ordinal marker AND ToolCall == null). Agent:EvidenceDisclosureRetries is deprecated (0 disables, 1 changes nothing, any other value fails validation, it never causes a model call). Residual: 'not contradicted' is not 'fully supported'; a general claim-support checker is a separate task. The original model re-ask design (EvidenceDisclosure/v1) is superseded; its guarantees (original answer exact prefix; status never changes; no tool executed) are retained.

### C04-R13 — Delegated Diagnostic: structured output and typed limitation metadata

A delegated Diagnostic final reply is exactly one JSON object {"findings":[...]} and cannot carry an 'Evidence limitations' heading, so for that role (selected by the typed predicate delegation is not null && delegation.Correlation.Agent?.Role == AgentRoleKind.Diagnostic, never a text heuristic) there is no disclosure step: the original JSON is persisted unchanged; the digest still exists with template EvidenceLimitations/v2 whose structured-role sentence says: keep exactly the required structured JSON payload; add no prose, heading or code fence outside it; this instruction replaces the separate Evidence limitations section requirement; qualify only findings a listed limitation materially affects; never create or alter a finding merely to encode a limitation. A runtime limitation is not a finding: a materially affected, otherwise supported finding's summary may be qualified (existing supporting evidenceIds only; no invented or changed evidenceIds; no severity change solely to carry a limitation; no attaching to an unaffected finding; no dropping a supported finding because of an unrelated limitation); a limitation affecting no finding stays outside the payload and recoverable from the persisted role task. E1-E7 govern the Diagnostic role unchanged. Delegated runs have no prose parent model, so typed limitation metadata is persisted: DelegationRoleRun carries EvidenceLimitations (null = not recorded, [] = none recorded), EvidenceLimitationsOmitted and, for Diagnostic, FindingsReply (DiagnosticReplyOutcome {Status Valid|Absent|Malformed, Problem None|NoJsonObject|InvalidJson|DuplicateProperty|TooLarge|NotAnObject|MissingFindingsArray|TooManyFindings, DiscardedFindings}); EvidenceLimitation {StepIndex, ToolName (canonical, shape-checked, or null), UnknownTool, Outcome, FailureKind, Completeness, ShortenedFromCharacters, EvidenceId (null when none — never manufactured)}; computed by the RUNTIME ONLY, deterministically, when a Discovery or Diagnostic role ends, from the same typed-field classification as the digest; no tool output, error text, argument or model text enters it; it covers only that role's model-loop evidence collection; at most 64 entries per role (most recent kept, rest counted); persisted before plan approval is requested; the runtime never decides materiality (a view marks a Finding restsOnLimitedEvidence only by exact join of its evidenceIds with a limitation's EvidenceId, computed in the view, and false means only 'cites no Evidence item itself marked limited', not 'unaffected'); a limitation never creates, removes or edits a Finding, evidence id or severity; before an operator approves a plan the approval surface (API view, UI, console) must display the persisted limitation metadata and a failure to load or a null field is shown as 'limitations unavailable / not recorded', never 'no limitations'. Strict Diagnostic JSON: the reply is parsed strictly (AllowDuplicateProperties=false) from the first '{' to the last '}' (prose or a fence around ONE object is tolerated, two objects are invalid); a repeated property at any depth is Malformed/DuplicateProperty with zero findings decided structurally (never from exception text, never first/last-wins); a reply over 65,536 UTF-16 code units is Malformed/TooLarge without parsing, maximum depth 16, more than 64 findings is Malformed/TooManyFindings (zero findings); a finding without a summary or with an unrecorded evidence id is discarded and counted; every failure outcome yields zero findings with no exception, and a malformed reply is a completed diagnosis with zero findings and a visible findingsReply.

### C04-R14 — Evidence-grounded final synthesis (grounding guard)

The runtime never edits, truncates, appends to or annotates the model's text apart from the C04-R12 appended section. For answers of ordinary tasks (not the delegated Diagnostic payload) the guard works from typed EvidenceFacts only: an EvidenceFact grounds an answer only when, from persisted state, it is on a persisted step with ToolCall and Result (all attempts, ascending Index), Result.Outcome is Success and the step is not an unknown-tool rejection, ExecutionClassification is null or Matched, Completeness is not Unavailable, and the fact list passes validation again when read back (a failing list contributes nothing); nothing else is read (no Output, Observation, ErrorMessage, argument, request/response JSON, model or exception text); Type and Key stay opaque ordinal identifiers and the runtime never parses tool output to obtain or check a fact. The ledger is a pure function of persisted steps and plan revisions (byte-identical live and after resume): fact id F<step>.<position>; selection: facts an Activation of a persisted plan revision refers to first (newest step first), then the step-diverse round-robin (steps with a non-referenced fact ordered newest to oldest, one fact per step per pass) until 12 are shown; a fact whose entry would exceed 512 characters is dropped before selection and counted as omitted; at most 12 facts shown, in ascending (step, position) order, with the fixed omission line; entries 'F<id> step <index> <tool>: type <T> key <K> = <ValueType> <value>' (' (from partial evidence)' for Partial) where <T>, <K> and string/path values are rendered as JSON string literals with the default System.Text.Json encoder, a value over 160 characters shown as '(value of <N> characters not shown)'; the Unknown line lists the newest 16 digest-listed steps; the block (EvidenceGrounding/v1, a fixed paragraph stating that quoted values are data, an observed fact must never be stated as absent/zero/false/different, partial counts are minimums, an unlisted fact is not an absence) sits between <<<BOPS_EVIDENCE_GROUNDING>>> and <<<END_BOPS_EVIDENCE_GROUNDING>>> in every step prompt (a step call is the final synthesis whenever it calls no tool) only when at least one fact is shown, within 7,168 UTF-16 code units, neutralized in tool output; fact Type/Key/string values may appear in a runtime-authored block only inside this delimited block and the correction instruction, as escaped JSON literals labelled as data. Natural-language contradiction detection is not deterministic and bOps does not pretend otherwise: the model judges; the runtime deterministically owns the ledger, the closed shape of the judgement, that a flagged candidate is never persisted as Completed unless replaced by an accepted correction, and the outcome transitions. Check: no operator switch (the guard cannot be configured off); triggered after disclosure handling, when the ledger has at least one fact, the answer is not the Diagnostic payload and the budget allows; the request is the step's request + the candidate as an assistant turn + one fixed user turn asking only for a JSON object {"contradictions":[{"fact":"<id>","quote":"<exact words>"}]} of at most 8 entries; an accepted reply has no tool call, parses (duplicate names rejected at every level) as an object whose only member is contradictions; any other shape or a model failure/timeout is 'check unavailable'; within shape an entry is a CITATION only when fact is a shown fact id and the quote (1-512 units, not blank) occurs in the candidate (whitespace runs collapsed, otherwise ordinal); an entry within the closed shape that is not a citation (fact id not shown, quote blank, over 512 units or not found in the candidate) is ignored, so a valid citation is never discarded because a sibling entry was wrong (an entry outside the closed shape — not an object with exactly the string members fact and quote — makes the whole reply 'check unavailable'); after that validation: no entries originally = 'no contradiction cited' (a model judgement, never 'verified'); at least one citation = contradicted; entries originally present but none a citation = 'check unavailable', never 'no contradiction cited', because the checker's non-empty claim could not be recognised; 'check unavailable' is never a positive verification that no contradiction exists, and a reply above 8 entries is 'check unavailable' as a whole. Correction: on at least one citation, one restatement request lists the cited facts as ledger entries (never the quotes) and asks for the complete answer agreeing with the observed facts; accepted only with no tool call, non-empty, not a TerminalProtocolArtifact, not check-shaped, containing none of the cited quotes and carrying the disclosure heading if the candidate did; not checked again. Outcomes: no fact/Diagnostic/budget exhausted = persisted without a check; no contradiction cited = persisted with marker, Completed; check unavailable = persisted with a marker saying the check did not happen, Completed; accepted correction = persisted, Completed; a correction repeating a quote, tool call, artifact, check-shaped reply or dropping the heading = Failed RuntimeFailure; empty correction = Failed EmptyResponse; correction model failure/timeout = Failed ModelFailure with its kind; cancellation or attempt-duration budget propagates; the flagged candidate is never stored as an answer; once a citation exists no path leads back to 'check unavailable' or the original answer. Package side: a package that wants grounding emits bounded facts about its own output (system.events: at most 12 facts of type system.events.matched-count keyed 'source=<source>;eventId=<id>' with the matched count, plus a final unlisted-groups fact; keys over 128 characters skipped, never cut; no zero-count fact is ever emitted). Residual risk: a contradiction the check misses or cites by paraphrase, a contradiction of an omitted fact, an E4 violation against unknown evidence and one the correction reintroduces in different words.

### C04-R15 — Final-response pipeline and validity

One fixed pipeline with no callbacks: model reply -> bounded EvidenceRead resolution -> empty-reply retries -> terminal protocol validation + one correction (failure -> Failed) -> empty check (-> Failed EmptyResponse) -> disclosure phase (never fails the task) -> grounding check (at most one) -> grounding correction (at most one; failure -> Failed) -> persist the final step; disclosure runs before grounding so the text the check judges is the text persisted; at most two added logical model calls per final answer, each subject to ADR-0039 attempts and budget; none creates a step, consumes step or replan budget, executes, authorizes or audits a tool or alters the plan cursor; tokens count in TokensUsed; the final step's Description is 'Final response' + an optional disclosure suffix + an optional grounding suffix (fixed strings recognized by the one predicate; written by the runtime only so no model or tool text can set it; legacy strings read back unchanged); logical calls are reconstructed from the end (a record with ModelAttempt 1 or null starts a new logical call); telemetry spans carry counts only, never content. Terminal validity: a final response is valid only if non-empty, not a tool call and not a protocol/control artifact (a <tool_call>/<function=> markup or a serialized {name, arguments} call object as the whole shape); an invalid original is never persisted or used as a fallback and gets one bounded terminal correction (no new step, no extra retry budget): a valid correction proceeds, a failed, empty or repeated-artifact correction ends the task Failed (RuntimeFailure for an artifact, EmptyResponse for empty, the model failure kind for a provider error); prose that merely mentions a function name is unaffected. A control function is valid only when advertised in the model-call control view of that turn.

### C04-R16 — EvidenceRead, evidence ids and immutability of persisted evidence

Raw evidence is persisted by bOps and never modified: Observation and Result.Output are never rewritten, a compacted view never replaces the persisted step, and reading a range never erases a partial or shortened limitation. Evidence ids are derived, never persisted: ev1:<lowercase N-format task id>:<non-negative PlanStep.Index>; the current task id is supplied by the runtime, never trusted from model text; the resolver rejects another task id, an absent index, a step without a tool call and non-canonical ids; exactly one persisted tool-call step must match. runtime.evidence_read (EvidenceRead/v1) is a bOps control-plane function for exceptional exact drill-down, not conversational memory: a runtime control function (declared by the runtime, never in the ToolRegistry, the runtime. namespace reserved so no package can register a tool in it, passing no policy/entitlement/approval, granting no operational authority) with typed arguments step, source (result|observation), offset and length, the current task taken from the runtime context; the legacy text form is one JSON object with exactly five case-sensitive keys (runtime, evidenceId, source, integer offset, integer length) in assistant text, never a provider tool call, and converges on the same handler; fences or prose invalidate it; a response mixing tool calls and an evidence-read claim is invalid; source=result reads exactly the persisted ToolCallResult.Output, source=observation exactly PlanStep.Observation (a null source is UnavailableSource); offsets are UTF-16 units, length 1-4000, offset == length is EndOfEvidence, negative/past-end/surrogate-splitting is OutOfRange; errors disclose no contents; replies use fixed markers and existing escaping with at most 256 units of overhead; a fragment lives only in that logical call and is never copied into future history. It is offered beside the step tool whenever an executed tool step with readable persisted output or observation exists and the logical call's read budget is not exhausted; it never completes a planned step, never advances the cursor, spends no correction, writes no PlanStep and counts against the read budget (four served reads per logical call; provider retries and overflow recovery do not reset it). Exhaustion is soft: the function is no longer offered for the rest of the logical call, the model is told so by a runtime-authored line, the ExpectedTool surface is unchanged and the task continues; valid reads and rejected control requests are counted separately and rejected requests stay bounded as a protocol failure; EvidenceRead exhaustion never owns the terminal state. A response carrying a control read gets the read served and no other call of that response executes (each other call id answered Not executed) so at most one operational execution per turn holds; an unrecognised runtime.* name is a control protocol error (audited Malformed); a call to an un-offered function is NotOffered (nothing read, no step, cursor unmoved). One metadata-only EvidenceReadAuditEvent per attempted read (task, nullable step index and plan revision, bounded evidence id, source, offset, requested and returned length, closed ResultCode Success|EndOfEvidence|Malformed|InvalidId|CrossTaskRejected|MissingStep|UnavailableSource|OutOfRange|LimitExceeded|NotAllowedInPhase|AttemptBudgetInterrupted) is audited before continuation or termination and never contains retrieved evidence. New tool-call steps persist a nullable PlanStep.VerificationStatus taken directly from the verification outcome (never parsed from Observation).

### C04-R17 — Tool output is data in every tool result

Whatever a tool returns — container logs, event messages, process titles and command lines, build output, labels, fetched web text, dump-analysis fields — is untrusted data: it crosses the tool boundary only as data inside the delimited tool-result turn (S5), never alters runtime state, never reaches audit summaries or telemetry as message text, and no tool result applies an additional prompt-injection transformation beyond the standing S5 delimiter and neutralization boundary. Audit records redacted arguments plus the opt-in aggregate summary and never a message or complete output. Fixed-shape fields that carry attacker-influenceable text are bounded (for example a process command line at most 2,048 characters). Inter-role values (Evidence, Finding, ExecutionPlan, VerificationReport) reach a later delegated role only as delimited tool-result data.

### C04-R18 — Skill evidence vocabulary

A Skill report is structured data, never free model narrative. Evidence has a kind (Fact, Inference, Recommendation, ExecutedAction, Verification) and an id, description, redacted data (redacted by whoever assembles it before construction), source tool and observed time; an Inference or a Recommendation is explicitly not a Fact. Finding.EvidenceIds cannot be empty (enforced by the constructor; citing evidence never recorded is checked at report validation). SkillReport(Evidence, Findings, Plan?) is assembled from what was actually recorded and has no unstructured-narrative field; a prepared report's findings are produced by the Skill's own code (interpreting Evidence into Findings is domain logic only a Skill can do); the stricter Diagnostic JSON parse can only drop findings, never add them.
